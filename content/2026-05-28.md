### 1. Claude Code Agent Teams: The Practical Guide to Multi-Agent Development

**URL:** https://claudefa.st/blog/guide/agents/agent-teams
**Time:** ~5 min read
**Category:** Multi-Agent Orchestration

**Why it's relevant:** Agent Teams let one Claude Code session act as a "team lead" that spawns independent teammates, each with its own context window and tool access. Teammates communicate through a mailbox system and coordinate via a shared task list. For consulting, the sweet spot is complex deliverables that span multiple files or disciplines: one agent cleans and validates data, another researches benchmarks, a third drafts the narrative — all running in parallel. Unlike the split-and-merge subagent pattern you saw on May 24, Agent Teams let agents *talk to each other* mid-task, which matters when findings from one workstream should redirect another. The feature is experimental (requires `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` in settings.json) and has limitations around session resumption and cleanup, but for the right tasks it's a force multiplier.

**Key Takeaway:** Enable Agent Teams and try it on your next multi-part deliverable. Describe the task and team structure in natural language — Claude creates the team, spawns teammates, and coordinates. Start small: a two-agent team (one researches, one writes) before scaling to three or four.

### 2. Connect Claude Code to GitHub, Slack, and Databases with MCP

**URL:** https://www.codevelocity.academy/en/blog/claude-code-mcp-integrations
**Time:** ~5 min read
**Category:** Tool Integration

**Why it's relevant:** MCP (Model Context Protocol) is how Claude Code talks to external systems. This guide walks through connecting the tools a consultant actually uses: GitHub (read issues, review PRs, create branches), Slack (read channel context, post updates), and databases (query client data directly). The practical sweet spot is 3-5 servers — more than that and tool counts get unwieldy. For consulting, the immediate win is GitHub + your project management tool (Linear, Jira): Claude can read the ticket, check the relevant code, write a fix, and open a PR without you context-switching between browser tabs. The security guidance is critical: use read-only tokens, narrowest possible permissions, and keep secrets out of `.mcp.json` (which gets committed to the repo). Run `claude mcp list` to verify what's connected, and `claude mcp test <n>` to debug.

**Key Takeaway:** Start with one MCP server — GitHub is the highest-value first choice. Create a fine-grained personal access token with only the permissions you need, add the server config to your settings, and try asking Claude to "list open issues in [repo]" or "review the latest PR." Once that works, add your second server (Slack or your database).

## Quick Win: Add a Force-Push Safety Hook

**Apply this in 2 minutes:**

Add this to your `.claude/settings.json` (project-level) or `~/.claude/settings.json` (global):

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "if echo \"$CLAUDE_TOOL_INPUT\" | grep -qE 'push.*--force|push.*-f|reset --hard'; then echo 'BLOCKED: Destructive git operation detected. Use the non-force alternative or confirm with the user first.' >&2; exit 1; fi"
          }
        ]
      }
    ]
  }
}
```

This hook intercepts any Bash command containing `push --force`, `push -f`, or `reset --hard` and blocks it before execution. In consulting, one accidental force-push to a client's main branch can cost hours of recovery and trust. This 2-minute setup eliminates that risk entirely.

**Why this matters:** You've learned about hooks conceptually — this is your first production safety hook. Once it's in place, you'll feel the difference: Claude will still suggest force-pushes when it thinks they're needed, but the hook catches them and forces a safer alternative.
