## Resource 1: MLflow + Claude Code — The Self-Improving Agent Loop

**Source:** [Ship LLM Agents Faster with Coding Assistants and MLflow Skills — MLflow Blog](https://mlflow.org/blog/self-improving-agent-loop)
**Also:** [Testing and Refining Claude Code Skills with MLflow — MLflow Blog](https://mlflow.org/blog/evaluating-skills-mlflow/)
**Also:** [Rapidly Prototype and Evaluate Agents with Claude Agent SDK and MLflow — MLflow Blog](https://mlflow.org/blog/mlflow-autolog-claude-agents-sdk/)
**Also:** [Tracing Claude Code — MLflow Docs](https://mlflow.org/docs/latest/genai/tracing/integrations/listing/claude_code/)
**Time:** ~6 min read (self-improving agent loop blog post + skim the skills evaluation post)
**Category:** Quality — From Output-Level Evals to Trace-Level Diagnosis

### Why This Is Relevant

Yesterday's Skills 2.0 evals (Digest #37) test whether your skill's *output* meets criteria — "Does the JSON contain API contracts? Does the dependency map include transitive dependencies?" That's necessary but insufficient. When an eval fails, you know *what* failed but not *why*. Was it because the agent read the wrong file? Called the wrong tool? Got confused by a large context window? You're guessing.

MLflow's Claude Code integration eliminates the guessing. It traces every action Claude Code takes during a skill execution — every file read, every shell command, every tool call — with full inputs, outputs, and timestamps. The trace is a ground-truth record: not what Claude *said* it did, but what it *actually did*, in order, with exact parameters.

**The self-improving loop has four steps:**

| Step | What Happens | Your Pipeline Example |
|------|-------------|----------------------|
| **Trace** | MLflow records every tool call during skill execution | Run `/reverse-engineer` on billing cluster, get full span tree |
| **Analyze** | Claude reads the trace and identifies execution gaps | "Agent read 12 files but missed `billing-gateway/config.yaml` which contains the API contract definitions" |
| **Score** | LLM judges and rule-based scorers evaluate specific aspects | Judge 1: "API contracts present?" Judge 2: "Dependency map complete?" Judge 3: "Correct tool sequence?" |
| **Fix** | Claude makes targeted edits based on trace evidence | Update skill prompt to explicitly include config files in the scan pattern |

**How it differs from Skills 2.0 evals:**

| Capability | Skills 2.0 Eval | MLflow Trace Eval |
|-----------|----------------|-------------------|
| Tests output quality | Yes | Yes |
| Records execution trace | No | Yes — full span tree |
| Diagnoses *why* failures happen | No — you read the output | Yes — you read the trace |
| Custom scoring criteria | Basic (pass/fail assertions) | Rich (LLM judges + rule-based scorers) |
| Regression detection | Manual re-run | Automated — compare traces across versions |
| Works with Agent SDK | No | Yes — `autolog` for SDK agents |

**Setup is one command:**

```bash
mlflow autolog claude /path/to/isp-project
```

This instruments every Claude Code session in that project directory. Every session gets a trace in MLflow's UI — a visual span tree showing the exact sequence of tool calls, their inputs, and their outputs. No code changes, no prompt modifications.

**The judge pattern for your ISP pipeline:**

Each judge evaluates one specific aspect of the trace:

- **Artifact judge:** "Did the agent create `output/billing-cluster.json`?"
- **Sequence judge:** "Did the agent read source files before writing the analysis?"
- **Schema judge:** "Does the output JSON conform to the API contract schema?"
- **Coverage judge:** "Did the agent visit all files in the `billing/` directory?"

If all judges pass, the skill worked correctly. If any judge fails, the rationale points directly at the failing span in the trace — not a vague "output was wrong" but "the agent skipped `billing-gateway/` at span 47 and never recovered the API contract definitions."

**The connection to your Agent SDK rebuild:** MLflow's `autolog` works with the Agent SDK too. When you rebuild your pipeline as a standalone Python application (Digests #34–36), `autolog` instruments every agent turn automatically. You get production traces from day one — no separate observability setup needed. This replaces the Langfuse/Opik decision from Digest #32 with a single, integrated solution that covers both Claude Code skills and Agent SDK agents.

### Key Takeaway

Run `mlflow autolog claude` in your ISP project directory, then execute your `/reverse-engineer` skill once. Open MLflow's trace UI and read the span tree. You'll see exactly what your skill does — every file it reads, every command it runs, every tool call in order. This trace is the foundation for writing judges that catch regressions automatically. It's also the observability layer for your Agent SDK rebuild. One command, two problems solved.

## Resource 2: The Plugin Marketplace — Package `/reverse-engineer` for Your Team

**Source:** [Claude Code Plugin Marketplace: Complete Guide (2026) — Agensi](https://www.agensi.io/learn/claude-code-plugin-marketplace-guide)
**Also:** [Discover and Install Prebuilt Plugins Through Marketplaces — Claude Code Docs](https://code.claude.com/docs/en/discover-plugins)
**Also:** [A Mental Model for Claude Code: Skills, Subagents, and Plugins — Dean Blank, Level Up Coding](https://levelup.gitconnected.com/a-mental-model-for-claude-code-skills-subagents-and-plugins-3dea9924bf05)
**Also:** [Claude Code Plugin Marketplace — Thoughtworks Technology Radar](https://www.thoughtworks.com/en-us/radar/tools/claude-code-plugin-marketplace)
**Time:** ~5 min read (Agensi guide — the clearest end-to-end walkthrough)
**Category:** Distribution — From Personal Skill to Team Capability

### Why This Is Relevant

Your `/reverse-engineer` skill exists as files in your project's `.claude/` directory. It works for you. Nobody else can use it without copying those files, understanding the agent configuration, and setting up the same MCP servers. The plugin system solves this: it wraps your skill, its agent definitions, its hooks, and its MCP server dependencies into a single installable package that a colleague installs with one command.

**What a plugin packages:**

| Component | What It Contains | Your Pipeline Example |
|-----------|-----------------|----------------------|
| **Skills** | `.claude/skills/*.md` files | Your `/reverse-engineer` skill prompt and frontmatter |
| **Subagents** | Agent definitions with roles and tools | Your 5 teammate agent configurations |
| **Hooks** | Pre/PostToolUse automation | Your JSON validation hook from Digest #36 |
| **MCP servers** | Tool server configurations | Any custom MCP servers your pipeline uses |
| **Slash commands** | Custom commands | `/reverse-engineer` as a registered command |

**Three distribution paths:**

**1. Team Marketplace (Private — Best for BCG)**

A team marketplace is a Git repo with a `marketplace.json` file. Your team clones the repo, and Claude Code discovers all plugins in it. This is the enterprise path — no public registry, full version control, access controlled by your existing Git permissions.

```
your-team-marketplace/
├── marketplace.json
├── reverse-engineer/
│   ├── plugin.json
│   ├── skills/
│   ├── agents/
│   └── hooks/
└── other-plugins/
```

Colleagues install with: `claude plugin install reverse-engineer --marketplace ./team-marketplace`

**2. `--plugin-url` (New in v2.1.129 — Shipped Today)**

The `--plugin-url` flag loads a plugin from a URL for the current session. This means you can host your plugin as a `.zip` archive on an internal server, SharePoint, or even a GitHub release, and colleagues load it without installing anything permanently:

```bash
claude --plugin-url https://internal.bcg.com/plugins/reverse-engineer.zip
```

This is ideal for testing and demos — share the URL in a Slack message, and anyone can try your skill immediately.

**3. Public Marketplace (Open Source)**

If you ever want to open-source your ISP analysis approach, the public marketplace (4,200+ skills as of this week) gives you distribution to 120,000+ monthly visitors. Not relevant now, but good to know the path exists.

**The Thoughtworks signal:** The Claude Code plugin marketplace appeared on the Thoughtworks Technology Radar in 2026 — a strong enterprise adoption signal. For your GenAI in SDLC presentation, citing the Technology Radar validates that the plugin ecosystem isn't just a developer toy but an enterprise-recognized distribution mechanism.

**LiteLLM for governance:** If BCG needs centralized control over which plugins are available, LiteLLM AI Gateway acts as a registry where admins govern approved plugins and engineers discover them from a single source. This is the enterprise governance story for your presentation's "team scale" slide.

### Key Takeaway

Create a `plugin.json` in your `/reverse-engineer` skill directory that declares the skill, its agent configurations, and its hooks as a single installable package. Then test it with `--plugin-url` by zipping the directory and loading it in a fresh Claude Code session. If it works end-to-end — skill fires, agents run, hooks validate output — you have a distributable capability that any colleague can use. This is the "team scale" slide for your presentation: "We don't just build AI skills — we package and distribute them like software."

## Resource 3: Today's Release — v2.1.129 and What It Means for Your Workflow

**Source:** [Claude Code Changelog — Official Docs](https://code.claude.com/docs/en/changelog)
**Also:** [Claude Code Updates May 2026 — Releasebot](https://releasebot.io/updates/anthropic/claude-code)
**Also:** [Claude Code Releases — GitHub](https://github.com/anthropics/claude-code/releases)
**Time:** ~4 min read (changelog entry + Releasebot summary)
**Category:** Platform — What Shipped Today

### Why This Is Relevant

Claude Code v2.1.129 shipped today (May 6, 2026) with two features that directly affect your workflow and one stability fix that matters for your Agent Teams pipeline.

**1. `--plugin-url` — Remote Plugin Loading**

Already covered in Resource 2, but worth highlighting the mechanics: this flag fetches a plugin `.zip` archive from a URL and loads it for the current session only. The plugin is not permanently installed — it's session-scoped.

**Why this matters for your ISP pipeline:** You can host your `/reverse-engineer` plugin on an internal URL and include it in your Routines configuration. Each scheduled pipeline run fetches the latest version of the plugin automatically — no manual update step, no version drift between runs.

**For headless/Routines execution:**
```bash
claude -p "Run ISP reverse-engineering analysis on billing cluster" \
  --plugin-url https://internal.bcg.com/plugins/reverse-engineer.zip \
  --output-format stream-json
```

**2. `CLAUDE_CODE_FORCE_SYNC_OUTPUT` — Synchronized Terminal Output**

This environment variable force-enables synchronized output on terminals where auto-detection fails. If you've ever seen garbled or flickering output during long Agent Teams runs (especially over SSH or in tmux), this fixes it.

**Set it in your shell profile:**
```bash
export CLAUDE_CODE_FORCE_SYNC_OUTPUT=1
```

**3. Sub-Agent Summary Fix — No More Repeated Summaries**

A bug was fixed where sub-agent summaries fired repeatedly while a sub-agent's transcript was static. In your Agent Teams pipeline, this means the lead agent no longer gets flooded with duplicate progress summaries from teammate agents that have finished their work and are idle. Cleaner lead agent context = better synthesis quality.

**Also in recent releases worth noting:**

- `CLAUDE_CODE_PACKAGE_MANAGER_AUTO_UPDATE`: Set this on Homebrew or WinGet installations to auto-update Claude Code in the background and prompt to restart. Ensures you're always on the latest version without manual `brew upgrade`.
- Plugin update detection fix: npm-sourced plugins now correctly detect when new versions are available. If you publish your team's plugin to a private npm registry, this ensures colleagues get update notifications.

### Key Takeaway

Set two environment variables in your shell profile today: `CLAUDE_CODE_FORCE_SYNC_OUTPUT=1` (fixes terminal rendering during long Agent Teams runs) and `CLAUDE_CODE_PACKAGE_MANAGER_AUTO_UPDATE=1` (auto-updates Claude Code). Together, they eliminate two sources of friction — garbled output and stale versions — that accumulate into workflow drag over time. The sub-agent summary fix is automatic; you'll notice cleaner lead agent behavior on your next Agent Teams run without changing anything.

## Quick Win: Instrument Your `/reverse-engineer` Skill with MLflow Tracing (5 min)

**Time: 5 minutes**

**Step 1:** Install MLflow if you haven't already:
```bash
pip install mlflow
```

**Step 2:** Enable auto-tracing for your ISP project:
```bash
mlflow autolog claude /path/to/isp-project
```

**Step 3:** Run your `/reverse-engineer` skill on one cluster (the smallest one for speed):
```
/reverse-engineer the provisioning service cluster
```

**Step 4:** Open the MLflow UI:
```bash
mlflow ui
```

Navigate to the trace for your run. You'll see a span tree: every file read, every shell command, every tool call, in order, with full inputs and outputs.

**What you'll learn in 5 minutes:** The exact execution path your skill takes. You'll likely discover that the agent reads files you didn't expect, skips files you thought it would read, or calls tools in an order you didn't anticipate. These surprises are your optimization targets — and they're invisible without traces.

**Why now:** Digest #37 introduced Skills 2.0 evals for testing output quality. This Quick Win adds the execution-level visibility that makes those evals diagnostic rather than just pass/fail. When an eval says "dependency map incomplete," the trace tells you *exactly which files the agent missed and why*. Five minutes of setup, permanent visibility into your skill's behavior.
