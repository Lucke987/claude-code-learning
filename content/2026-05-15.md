## Resource 1: Agent Teams Dry-Run Playbook — tmux Split Panes for a Compelling London Demo

**Source:** [Orchestrate teams of Claude Code sessions — Claude Code Docs](https://code.claude.com/docs/en/agent-teams)
**Also:** [Watch Claude Code Agents Work Side by Side: A tmux Setup Guide — Karan Singh](https://ksingh7.medium.com/watch-claude-code-agents-work-side-by-side-a-tmux-setup-guide-1ef3ba1531c4)
**Also:** [Setting Up Claude Code Agent Teams with WSL2 and tmux — Steve Smith (Ardalis)](https://ardalis.com/setting-up-claude-code-agent-teams-with-wsl2-and-tmux-on-windows/)
**Time:** ~6 min read (official docs team section + skim the tmux guide)
**Category:** Demo Preparation — Make Your Pipeline Visually Impressive

### Why This Is Relevant

Your dry run today has two goals: (1) verify the pipeline runs end-to-end, and (2) practice the demo flow you'll show at London. A pipeline running in a single terminal window is invisible — the audience sees a cursor blinking and hears you narrate. A pipeline running in tmux split panes shows 5 agents working simultaneously, each in its own pane, with the observability dashboard in a sixth pane. That's the difference between "trust me, it works" and the audience leaning forward in their seats.

**Setting up the demo layout:**

```bash
# Enable agent teams
export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1

# Set tmux as the display mode (in ~/.claude/settings.json)
# "teammateMode": "tmux"

# Start a tmux session for the demo
tmux new-session -s london-demo

# Your pipeline's conductor spawns teammates in split panes automatically
# Each domain agent (API, billing, auth, infra) + synthesis agent gets its own pane
```

**Three things to verify during today's dry run:**

**1. Split-pane layout scales to 5 agents.**

The official docs confirm: "each teammate gets its own pane where you can see everyone's output at once." But 5 agents + the lead = 6 panes. On a standard 1080p display, that's tight. Test with your actual screen resolution. If it's too cramped, consider dropping to 3 visible panes (conductor + 2 active specialists) and cycling the rest with `Shift+Down`.

**2. The observability dashboard runs alongside tmux.**

Your disler dashboard (Digest #45) runs at `localhost:5173`. During the demo, you need both the tmux panes AND the dashboard visible. Two approaches:
- **Dual monitor:** tmux on one screen, dashboard browser on the other. Preferred for live presentations.
- **Single screen:** tmux takes 60% width, dashboard browser takes 40%. Use tmux's split-window to dedicate one pane to a browser-based terminal showing the dashboard URL.

**3. Permission prompts don't interrupt the flow.**

The docs warn: "Teammate permission requests bubble up to the lead, which can create friction. Pre-approve common operations in your permission settings before spawning teammates." During a live demo, a permission prompt halting the pipeline kills the momentum. For the dry run, note every permission prompt that fires — then add those to your allow list before London.

**Key demo choreography:**

| Moment | What the Audience Sees | What You Say |
|--------|----------------------|-------------|
| Pipeline start | Conductor pane analyzes the cluster | "The conductor is reading the service cluster and deciding how to decompose the problem" |
| Agent spawn | 4 new panes appear simultaneously | "Four domain specialists launch in parallel — API contracts, billing, auth, infrastructure" |
| Parallel work | All 4 panes scrolling with analysis | "Each agent has its own context window and sees only its domain — no cross-contamination" |
| Dashboard pulse | Live pulse chart showing activity | "The observability dashboard tracks every tool call in real time" |
| Synthesis | 5th agent pane activates | "The synthesis agent merges all four analyses into structured documentation" |
| Output | Final structured output appears | "From cluster definition to complete API contracts in under 10 minutes" |

**What to watch for during the dry run:**

- Which agent takes longest? That's your bottleneck — and your answer to "how long does this take in production?"
- Do any agents fail and require restart? The docs note: "Teammates may stop after encountering errors instead of recovering." Have a recovery script ready.
- Does the task list (`Ctrl+T`) accurately reflect progress? The docs warn: "teammates sometimes fail to mark tasks as completed, which blocks dependent tasks."

### Key Takeaway

Run your pipeline in tmux split-pane mode today. Note the total runtime, identify the slowest agent, and count every permission prompt. Fix permission issues before London. Practice the 6-moment demo choreography above until you can narrate without looking at notes. The split-pane visualization is your strongest demo asset — it turns an invisible AI process into a visible multi-agent system the audience can follow in real time.

## Resource 2: Week 19 Features You Should Activate Before London

**Source:** [Week 19 Digest (May 4–8) — Claude Code Docs](https://code.claude.com/docs/en/whats-new/2026-w19)
**Also:** [Hooks reference — Claude Code Docs](https://code.claude.com/docs/en/hooks)
**Also:** [Claude Code Releases — GitHub](https://github.com/anthropics/claude-code/releases)
**Time:** ~5 min read (Week 19 digest + relevant settings docs)
**Category:** Pipeline Hardening — Three Features That Strengthen Your Demo

### Why This Is Relevant

Week 19 (May 4–8) shipped three features that directly apply to your pipeline's governance and cost layers. You should activate them before the dry run so they're battle-tested by London. Each one addresses a specific gap in your current setup.

**Feature 1: `$CLAUDE_EFFORT` in hooks and Bash**

Your PostToolUse governance hooks already use `$CLAUDE_EFFORT` to calibrate validation depth. What's new: hooks now also receive `effort.level` in the JSON input object, not just the environment variable. This means your hook scripts can branch on effort level without parsing environment variables — cleaner, more portable.

```json
// What your hook now receives in the input JSON:
{
  "tool_name": "Write",
  "tool_input": { "file_path": "..." },
  "tool_response": "...",
  "effort": { "level": "xhigh" }
}
```

**Update your PostToolUse hooks** to read `effort.level` from the JSON input instead of (or in addition to) `$CLAUDE_EFFORT`. The JSON path is the canonical source going forward.

**Feature 2: `autoMode.hard_deny` rules**

Your governance layer uses hard deny rules to block dangerous actions. The new `settings.autoMode.hard_deny` makes these rules unconditional — they can't be overridden by broader allow rules. This is critical for your demo: you want to show that the pipeline runs autonomously (auto mode) BUT certain actions are absolutely forbidden regardless of context.

```json
// In settings.json
{
  "settings": {
    "autoMode": {
      "hard_deny": [
        { "tool": "Bash", "command_pattern": "rm -rf" },
        { "tool": "Bash", "command_pattern": "DROP TABLE" },
        { "tool": "Write", "file_pattern": "*.env" }
      ]
    }
  }
}
```

**For your presentation:** This is the governance slide's strongest proof point. "Even in fully autonomous mode, hard deny rules are unconditional. The pipeline cannot delete production data, drop tables, or write to environment files — no matter what the agent decides."

**Feature 3: Sub-agent cache savings (~3x)**

Sub-agent progress summaries now hit the prompt cache, reducing `cache_creation` token cost by roughly 3x. Your pipeline spawns 5 sub-agents per run — this directly reduces your per-run cost. For your London Q&A prep (Netflix/Datadog cost control question), you now have a concrete data point: "Anthropic shipped a 3x cache cost reduction for sub-agent coordination in v2.1.128."

**Other Week 19 wins relevant to you:**

- `CLAUDE_CODE_SESSION_ID` in Bash subprocess environment — your hooks can now correlate which agent's Bash commands are running, useful for per-agent cost tracking in the observability dashboard.
- `Ctrl+R` history search across all projects — during the dry run, if you need to recall a command from a previous session, `Ctrl+R` now searches globally (not just current project).

### Key Takeaway

Update your `settings.json` today with `autoMode.hard_deny` rules before the dry run. Switch your PostToolUse hooks to read `effort.level` from the JSON input. These two changes harden your governance layer AND give you concrete talking points for your presentation's guardrails slide. The sub-agent cache savings are automatic — just verify you're on v2.1.128+ with `claude --version`.

## Quick Win: Set Up Your London Demo Terminal Layout (5 min)

**Time: 5 minutes**

Before running the full pipeline dry run, set up the exact terminal layout you'll use at London. This separates "does my pipeline work?" from "does my demo look good?" — solve the visual problem first.

```bash
# 1. Install tmux if not already present
sudo apt-get install tmux  # or brew install tmux on macOS

# 2. Create a named session for the demo
tmux new-session -s london-demo -d

# 3. Split into a 2x3 grid (conductor + 4 agents + dashboard)
tmux split-window -h -t london-demo
tmux split-window -v -t london-demo:0.0
tmux split-window -v -t london-demo:0.1
tmux split-window -v -t london-demo:0.2
tmux split-window -v -t london-demo:0.3

# 4. Label each pane (helps during narration)
tmux select-pane -t london-demo:0.0 -T "Conductor"
tmux select-pane -t london-demo:0.1 -T "API Contracts"
tmux select-pane -t london-demo:0.2 -T "Dependencies"
tmux select-pane -t london-demo:0.3 -T "Auth & Billing"
tmux select-pane -t london-demo:0.4 -T "Synthesis"
tmux select-pane -t london-demo:0.5 -T "Dashboard"

# 5. Attach and verify the layout
tmux attach -t london-demo
```

**Note:** You don't need to manually manage the panes for agent teams — Claude Code's `teammateMode: "tmux"` handles pane creation automatically. The script above is for **previewing and practicing the layout** before running the actual pipeline. When you launch agent teams with tmux mode enabled, Claude creates panes for each teammate automatically.

**The real setup for the dry run:**

```json
// In ~/.claude/settings.json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  },
  "teammateMode": "tmux"
}
```

Then start Claude Code inside a tmux session and trigger your pipeline. The split panes appear automatically as teammates spawn.

**After setting up**, run the full pipeline once and time it. Write down: total runtime, which agent was slowest, how many permission prompts fired, and whether the observability dashboard captured all 5 agents' events. These four numbers are your dry-run baseline — compare them against a second run after applying the Week 19 `autoMode.hard_deny` and `effort.level` updates from Resource 2.

**Why now:** Tomorrow (Day 5) is question refinement day. If your dry run surfaces new questions — "why does the auth agent take 4 minutes when the others take 90 seconds?" — those become better London questions than the ones you've pre-written. The dry run isn't just rehearsal; it's discovery.
