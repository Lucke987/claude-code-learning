## Resource 1: Managed Agents — Dreaming, Outcomes, and Multiagent Orchestration

**Source:** [New in Claude Managed Agents: dreaming, outcomes, and multiagent orchestration — Anthropic](https://claude.com/blog/new-in-claude-managed-agents)
**Also:** [Anthropic introduces "dreaming," a system that lets AI agents learn from their own mistakes — VentureBeat](https://venturebeat.com/technology/anthropic-introduces-dreaming-a-system-that-lets-ai-agents-learn-from-their-own-mistakes)

**Time:** ~7 min read (Anthropic blog post + skim VentureBeat for context + API docs for technical detail)
**Category:** Platform — Anthropic Just Productized What You Built By Hand

### Why This Is Relevant

On May 7, 2026 — yesterday — Anthropic announced three features for Managed Agents that map directly to capabilities you've been assembling from separate tools across the last 10 digests. This isn't a coincidence; you've been building the right architecture. The question is whether to adopt the native versions or keep your custom stack.

**The three features and how they map to your work:**

| Managed Agents Feature | What It Does | Your Current Equivalent | Digest |
|----------------------|-------------|------------------------|--------|
| **Dreaming** | Reviews past session transcripts, extracts patterns, curates memory. Agents learn from mistakes across sessions. | MLflow trace analysis + manual CLAUDE.md updates | #38 |
| **Outcomes** | You write a rubric; a separate grader evaluates output in its own context window. Agent iterates until the grader approves. | Skills 2.0 evals + MLflow LLM judges | #37–38 |
| **Multiagent orchestration** | Lead agent delegates to up to 20 subagents, each with its own model/prompt/tools. Parallel execution on shared filesystem. | Your 5-agent Agent Teams pipeline | #22–30 |

**Dreaming is the headline feature.** It's a scheduled process that reads an existing memory store alongside batches of past session transcripts, then produces a reorganized memory layer — duplicates merged, stale entries replaced, new patterns surfaced. The critical detail: *a dream agent can see what individual session agents can't.* Your pipeline agent in session 47 doesn't know it's made the same API contract extraction error 12 times across the past month. Dreaming detects the pattern and writes a targeted memory update.

**How it differs from your MLflow self-improving loop:**

| Capability | Your MLflow Loop | Dreaming |
|-----------|-----------------|----------|
| Trace visibility | Full span tree (tool calls, inputs, outputs) | Session transcripts (higher-level) |
| Pattern detection | Manual — you read traces and identify issues | Automated — dreaming surfaces recurring mistakes |
| Memory update | Manual — you edit CLAUDE.md or skill prompts | Automated — dreaming produces a new memory store |
| Human control | Full — you decide what to change | Configurable — auto-update or review-before-deploy |
| Scope | Single project | Cross-session, cross-agent |
| Available now? | Yes (MLflow is open source) | Research preview |

**The strategic read:** Dreaming automates the pattern-detection step you currently do manually by reading MLflow traces. But it operates on session transcripts, not tool-level traces. Your MLflow setup gives you *deeper* visibility (exact file reads, exact tool calls); dreaming gives you *broader* visibility (patterns across dozens of sessions). They're complementary, not competing.

**Outcomes** is the grading loop you've been building with Skills 2.0 evals and MLflow judges. The key difference: the grader runs in a *separate context window* from the agent, so it isn't influenced by the agent's reasoning chain. When something isn't right, the grader pinpoints what needs to change and the agent takes another pass. This is the blind evaluation pattern from Skills 2.0's A/B testing (Digest #37), but built into the execution loop rather than being a post-hoc evaluation.

**Multiagent orchestration** in Managed Agents now supports up to 20 specialist subagents running in parallel on a shared filesystem, each with its own model, prompt, and tools. This is your Agent Teams architecture — but hosted, managed, and with Anthropic handling the coordination infrastructure. For your Agent SDK rebuild (Digests #34–36), this means you may not need to build coordinator logic from scratch.

**For your presentation:** "Anthropic just shipped the three features that validate our architecture" is the most powerful enterprise adoption signal you can give. You built dreaming (self-improving traces), outcomes (eval grading), and multiagent orchestration (5-agent pipeline) from first principles. Anthropic then productized all three as native platform features. That's not luck — it's proof that the architecture patterns you chose are the patterns the platform converges on.

### Key Takeaway

Read the [Dreams API docs](https://platform.claude.com/docs/en/managed-agents/dreams) and the [Multiagent sessions docs](https://platform.claude.com/docs/en/managed-agents/multi-agent). Your Agent SDK rebuild now has two paths: (1) build custom coordination with circuit breakers and MLflow tracing, or (2) adopt Managed Agents' native multiagent orchestration with dreaming and outcomes. Path 2 gives you less control but eliminates the coordination infrastructure you'd need to build. The right answer is probably hybrid: use Managed Agents' multiagent orchestration for coordination, keep MLflow tracing for tool-level diagnosis that dreaming can't see, and layer outcomes on top of your existing eval criteria. One afternoon of reading the API docs now saves you a week of building coordination logic that Anthropic just shipped for you.

Addy Osmani (Google Chrome engineering leadership) published a framework for multi-agent coding that maps perfectly onto your ISP pipeline — and gives you presentation-grade vocabulary from a name that carries weight with senior technical stakeholders.

**The three reference patterns:**

| Pattern | How It Works | Your Pipeline | When to Use |
|---------|-------------|--------------|-------------|
| **Subagents** | One orchestrator spawns children. Simplest model. | Your Agent Teams lead + teammates | Bounded tasks with clear delegation |

**The headline insight:** "Three focused agents consistently outperform one generalist agent working three times as long." This validates your 5-agent architecture from an independent, respected voice. **The conductor-to-orchestrator shift:**

```
Old model: One developer + one AI → synchronous → context window is your ceiling
```

This is your maturity arc (Digest #35) restated in Osmani's language: you went from one-shot prompts (the "conductor" playing every instrument) to a 5-agent pipeline (the "orchestrator" directing an ensemble). The audience gets it immediately.

**The specialization principle:** Each agent only sees the files it owns. An agent that only knows about billing services writes better analysis than one juggling the entire 47-microservice codebase. This is precisely the file-ownership pattern you implemented in your Agent Teams configuration — and now you have Osmani's framing to explain *why* it works.

## Resource 3: Multiagent Sessions API — The Technical Reference for Your Agent SDK Rebuild

**Source:** [Multiagent sessions — Claude API Docs](https://platform.claude.com/docs/en/managed-agents/multi-agent)
**Also:** [Orchestrate teams of Claude Code sessions — Claude Code Docs](https://code.claude.com/docs/en/agent-teams)
**Also:** [Claude Code Agent Teams, Subagents, and MCP: The 2026 Playbook — Developers Digest](https://www.developersdigest.tech/blog/claude-code-agent-teams-subagents-2026)
**Time:** ~3 min read (API docs — the canonical technical reference)
**Category:** Architecture — The API You'll Build Against

### Why This Is Relevant

Resource 1 explained *what* Managed Agents' multiagent orchestration does. This resource is *how* — the API surface you'll use when rebuilding your pipeline with the Agent SDK. The docs are now public (shipped to public beta on May 7), and reading them now shapes your architectural decisions before you write code.

**Key architectural details from the docs:**

**Coordinator-subagent model:** A lead agent decomposes a task, delegates to up to 20 specialist subagents running in parallel. Each subagent gets its own model, system prompt, and tool configuration. This maps 1:1 to your current architecture: lead agent + 4 domain cluster agents + 1 synthesis agent.

**Shared filesystem:** Subagents work on a shared filesystem and contribute to the lead agent's overall context. This is the same model as your Agent Teams setup — but with one important difference: Managed Agents handles file-locking and coordination infrastructure that you'd otherwise build yourself.

**Per-subagent model selection:** Each subagent can use a different model. This connects to the effort-level optimization from Digest #37: your domain cluster agents (structured extraction) could run on a smaller/cheaper model, while the lead agent (cross-cluster synthesis) runs on Opus 4.7 at `xhigh` or `max` effort.

**How this changes your Agent SDK rebuild plan:**

| Architecture Decision | Your Original Plan (Digests #34–36) | With Managed Agents Multiagent |
|----------------------|-------------------------------------|-------------------------------|
| Coordination logic | Build custom with circuit breakers | Native — Managed Agents handles it |
| Subagent spawning | Code SDK calls per agent | Declarative — define subagents in config |
| Parallel execution | Worktree isolation + manual sync | Native parallel on shared filesystem |
| Cost control | Custom per-task caps | Platform-level cost tracking |
| Observability | MLflow autolog | Native traces + MLflow for depth |
| State persistence | Custom Postgres/Redis layer | Platform-managed sessions |

**What you still need to build:** Domain-specific skill logic (your `/reverse-engineer` prompt and agent roles), output schema validation (your PostToolUse hooks), and deep tracing (MLflow for tool-level spans that platform traces don't capture).

**What you no longer need to build:** Coordinator infrastructure, parallel execution management, state persistence between agents, and the basic retry/circuit-breaker layer. Managed Agents handles all of this.

### Key Takeaway

Read the multiagent sessions API docs. Map your 5-agent pipeline's current configuration (lead agent + 4 domain specialists) onto the coordinator-subagent model. Identify which pieces of your Agent SDK rebuild plan (Digests #34–36) are now handled natively by Managed Agents, and which remain custom. The goal is to ship a working Managed Agents prototype in days rather than weeks — by letting the platform handle coordination while you focus on the domain logic that makes your pipeline valuable.

## Quick Win: Compare Your Self-Improving Loop to Dreaming (5 min)

**Time: 5 minutes**

Your self-improving agent loop from Digest #38 has four steps: Trace → Analyze → Score → Fix. Dreaming, announced yesterday, automates steps 2 and 3 (Analyze and Score) across sessions. Here's how to evaluate whether to adopt it:

**Step 1:** Open the [Dreams API docs](https://platform.claude.com/docs/en/managed-agents/dreams) and read the "How dreaming works" section (~2 min).

**Step 2:** Write a quick comparison note in your project:

```markdown
## Self-Improving Loop: MLflow vs. Dreaming

### What MLflow gives me that Dreaming doesn't:
- Tool-level span trees (exact file reads, shell commands, tool call order)
- Custom LLM judges per eval criterion
- Local, open-source, full control

### What Dreaming gives me that MLflow doesn't:
- Cross-session pattern detection (recurring mistakes across dozens of runs)
- Automated memory curation (no manual CLAUDE.md edits)
- Native platform integration (no separate infra)

### Decision:
- Keep MLflow for tool-level diagnosis (WHY did an eval fail?)
- Add Dreaming for cross-session pattern learning (WHAT keeps failing?)
- Layer both: MLflow traces feed your manual analysis; Dreaming feeds your agent's memory
```

**Why now:** Yesterday's Managed Agents announcement validated your architecture — you built dreaming, outcomes, and multiagent from first principles before Anthropic shipped them as features. But validation isn't adoption. Five minutes of structured comparison now prevents you from either (a) rebuilding what the platform already ships, or (b) abandoning custom tooling that gives you deeper visibility than the platform can. The right answer is the hybrid stack: platform for breadth, custom for depth.
