## Resource 1: Anthropic's "Multi-Agent Coordination Patterns: Five Approaches" — The Taxonomy That Sharpens Your Boris Cherny Question

**Source:** [Multi-agent coordination patterns: Five approaches and when to use them — Anthropic Blog](https://claude.com/blog/multi-agent-coordination-patterns)
**Also:** [When to use multi-agent systems (and when not to) — Anthropic Blog](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
**Also:** [Common workflow patterns for AI agents — Anthropic Blog](https://claude.com/blog/common-workflow-patterns-for-ai-agents-and-when-to-use-them)
**Time:** ~6 min read (coordination patterns article + skim the "when to use" companion)
**Category:** Question Refinement — Give Your London Questions Anthropic's Own Vocabulary

### Why This Is Relevant

Your Boris Cherny question (Digest #47) asks about the roadmap for asynchronous inter-agent coordination. That question is good but generic — it could come from anyone who's read the Agent Teams docs. Anthropic published their canonical 5-pattern taxonomy on April 14, and it gives you the precise vocabulary to ask a question that shows you've done the homework.

**The five patterns and where your pipeline sits:**

| Pattern | How It Works | Your Pipeline's Use |
|---------|-------------|-------------------|
| **1. Generator-Verifier** | One agent produces, another evaluates against criteria | Your PostToolUse hooks are a lightweight version — governance validates domain agent output |
| **2. Orchestrator-Subagent** | Lead decomposes, delegates bounded subtasks, synthesizes | **Your primary pattern.** Conductor → 4 domain agents → synthesis agent |
| **3. Agent Teams** | Parallel long-running agents with peer-to-peer messaging | You use Agent Teams for orchestration, but your agents don't message each other mid-run |
| **4. Message Bus** | Publish/subscribe event-driven coordination | **The gap in your pipeline.** Agents can't signal each other when discoveries emerge |
| **5. Shared State** | Agents coordinate through a persistent store | The shared task list (`~/.claude/tasks/`) partially implements this |

**The critical insight:** Anthropic recommends starting with orchestrator-subagent (Pattern 2) because "it handles the widest range of problems with minimal coordination overhead." But they also note that "production systems often combine patterns — using orchestrator-subagent for overall workflow with shared state for collaboration-heavy subtasks."

Your pipeline is Pattern 2 with elements of Pattern 3. The inter-agent steering limitation you identified (Digest #45: "the dependency mapper can't tell the API contract agent to adjust mid-run") is the gap between Pattern 3 and Pattern 4. The message bus pattern — where agents publish discoveries and other agents subscribe to relevant topics — is exactly what you need.

**How this reshapes your Boris Cherny question:**

Old question: "What's on the roadmap for asynchronous inter-agent coordination?"

**New question:** "Our pipeline uses orchestrator-subagent (Pattern 2 from your coordination taxonomy) with Agent Teams. We hit the Pattern 3→4 boundary: when our dependency mapper discovers an unexpected API pattern, it can't publish that event to the API contract agent mid-run. Your taxonomy describes message bus coordination (Pattern 4) as suited to 'event-driven pipelines where the workflow emerges from events.' Is there a roadmap for bringing message bus primitives into Agent Teams — so agents can publish/subscribe to discoveries without routing everything through the orchestrator?"

**Why this is a better question:** It uses Anthropic's own taxonomy, demonstrates you've read and applied the canonical patterns, identifies the exact boundary you've hit (Pattern 3→4), and asks about a specific architectural evolution rather than a vague "what's next." Boris will recognize you've done the work.

**Bonus insight for your presentation:** The 5-pattern taxonomy replaces the MindStudio 5-pattern taxonomy from Digest #45. Both have five levels, but Anthropic's is the canonical source — it comes from the people who built the platform. Update your slides to reference Anthropic's taxonomy: Generator-Verifier → Orchestrator-Subagent → Agent Teams → Message Bus → Shared State. Your pipeline's journey maps to patterns 2→3, with your governance hooks implementing a lightweight Pattern 1 (generator-verifier).

### Key Takeaway

Rewrite your Boris Cherny question using the five-pattern taxonomy from Anthropic's own blog. Reference the specific Pattern 3→4 boundary your pipeline hits. The question shifts from "what's on the roadmap?" (passive) to "here's the exact architectural boundary we've hit, here's what we need" (active). Boris built Claude Code — he'll engage with a question that demonstrates deep use of the product and references his team's published patterns.

## Resource 3: Agent Teams Coordination Deep Dive — SendMessage, TaskCreate, and What Your Pipeline Could Use Today

**Source:** [Orchestrate teams of Claude Code sessions — Claude Code Docs](https://code.claude.com/docs/en/agent-teams)
**Also:** [Claude Code Agent Teams Deep Dive: Parallel Agents and Shared State — MindStudio](https://www.mindstudio.ai/blog/claude-code-agent-teams-parallel-shared-task-list)
**Also:** [From Tasks to Swarms: Agent Teams in Claude Code — alexop.dev](https://alexop.dev/posts/from-tasks-to-swarms-agent-teams-in-claude-code/)
**Time:** ~4 min read (official docs coordination section + MindStudio shared state deep dive)
**Category:** Pipeline Enhancement — Coordination Primitives You May Not Be Using Yet

### Why This Is Relevant

Your pipeline uses Agent Teams for orchestration, but you may be underusing the coordination primitives that already exist. Before asking Boris about message bus patterns at London, verify that you've exhausted the current capabilities. Agent Teams ships three coordination primitives — and the third one partially solves the inter-agent steering problem you identified.

**Primitive 1: SendMessage — Typed inter-agent messaging**

SendMessage supports four message types: `direct` (one-to-one), `broadcast` (one-to-all), `shutdown` (terminate a teammate), and `plan_approval` (request lead sign-off). Direct messages are stored as JSON in `~/.claude/teams/{team-name}/inboxes/` and picked up automatically.

**What this means for your pipeline:** Your dependency mapper agent *can* send a direct message to the API contract agent. The mechanism exists — it's `SendMessage` with `type: "direct"` and the target teammate's name. The limitation isn't that agents can't communicate; it's that they don't *automatically* check for new messages during a long-running task. The agent checks its inbox at natural breakpoints (between tool calls), not in real time.

**Experiment to run today:**

```
# In your conductor's prompt, add:
"When you discover an unexpected API pattern, send a direct message 
to the api-contracts agent describing the pattern. Use SendMessage 
with type 'direct'."

# In your api-contracts agent's prompt, add:
"Periodically check your inbox for messages from other agents. 
If you receive a message about an unexpected API pattern, 
adjust your analysis accordingly."
```

This is a manual implementation of Pattern 4 (message bus) using Pattern 3 (agent teams) primitives. It's not event-driven — the receiving agent polls rather than subscribes — but it may be "good enough" for your dry run and demo.

**Primitive 2: TaskCreate — Shared work queues with dependencies**

Tasks live at `~/.claude/tasks/{team-name}/` with three states: pending, in progress, and completed. Tasks can declare dependencies on other tasks. The shared task list is the coordination layer — no direct messaging required.

**What this means for your pipeline:** If your dependency mapper discovers an unexpected pattern, it can create a new task: "Re-analyze API contracts for service X using gRPC pattern instead of REST." The API contract agent picks up this task when it finishes its current work. This is shared state coordination (Pattern 5) — the dependency mapper doesn't need to know *who* will handle the task, just that it needs handling.

**Primitive 3: Worktree isolation — Safe parallel file editing**

Each teammate gets its own git worktree, preventing merge conflicts when multiple agents edit files simultaneously. The lead merges worktrees when teammates complete their tasks.

**What this means for your pipeline:** Your 4 domain agents can write to the same output directory without conflicts. Each agent's worktree contains its own copy of the output files, and the synthesis agent merges them. This eliminates the race condition where two agents try to write to `api-contracts.md` simultaneously.

**The practical heuristic from MindStudio:**

"If you can describe each worker's task completely without referencing what other workers are doing, use subagents. If workers need to ask each other questions, share intermediate results, or coordinate their changes, use agent teams."

Your pipeline is in the transition zone: you started with subagent-style delegation (each domain agent gets a complete, independent task), but you've discovered that agents *do* benefit from sharing intermediate results (the dependency mapper's discovery). The SendMessage + TaskCreate experiment above moves you from the subagent side to the agent teams side of this heuristic.

### Key Takeaway

Before London, try the SendMessage experiment: have your dependency mapper send a direct message to the API contract agent when it discovers an unexpected pattern, and have the API contract agent check its inbox between tool calls. If this works — even imperfectly — you can demo it at London and ask Boris: "We implemented a polling-based inter-agent signal using SendMessage. What would it take to make this event-driven — a push notification instead of inbox polling?" That's a question grounded in real experimentation, not theoretical architecture.
