The paper identifies **7 safety systems** in Claude Code's architecture, and your three-tier governance model (hard_deny, auto mode, PostToolUse hooks) maps directly to three of them. The paper also traces every design choice back through **13 design principles** to **5 foundational human values** — giving you a framework for explaining *why* your governance rules exist, not just *what* they do.

## Resource 2: The Complete Claude Code Hooks Reference — 32+ Events You Should Know About

**Source:** [Claude Code Hooks: The Complete 2026 Production Reference (32+ Events, 5 Handler Types, Exit Code Semantics) — The Prompt Shelf](https://thepromptshelf.dev/blog/claude-code-hooks-complete-reference-2026/)
**Also:** [Claude Code Hooks Guide 2026: Automate Your Workflow — Serenities AI](https://serenitiesai.com/articles/claude-code-hooks-guide-2026/)
**Also:** [Claude Code HTTP Hooks × GitHub Actions Integration Guide — Claude Lab](https://claudelab.net/en/articles/claude-code/claude-code-http-hooks-cicd-github-actions-guide)
**Also:** [7 Claude Code Hooks Most Developers Overlook — Joe Njenga](https://medium.com/@joe.njenga/7-claude-code-hooks-most-developers-overlook-especially-beginners-78ca29902b19)
**Time:** ~5 min read (The Prompt Shelf reference + Joe Njenga hooks article)
**Category:** Pipeline Enhancement — New Hook Events for Your Observability Layer

### Why This Is Relevant

Your pipeline uses PostToolUse hooks for governance validation and feeds events to your disler observability dashboard. But Claude Code v2.1.141+ now exposes **32+ lifecycle events** — and several new ones are directly relevant to your 5-agent pipeline's observability and governance layers.

**New events since your pipeline was built:**

| Event | What It Does | How You'd Use It |
|-------|-------------|-----------------|
| **SubagentStart** | Fires when a subagent is spawned | Track when each of your 5 domain agents starts — feed to dashboard for agent timeline |
| **SubagentStop** | Fires when a subagent completes | Measure per-agent runtime, detect hung agents, calculate per-agent cost |
| **TeammateIdle** | Fires when an Agent Teams member has no work | Detect when domain agents finish early — trigger synthesis sooner |
| **TaskCreated** | Fires when a new task enters the shared queue | Track your SendMessage polling experiment — see when agents create tasks for each other |
| **TaskCompleted** | Fires when a task is marked done | Completion tracking without relying on `/goal` — lightweight completeness verification |
| **PreCompact** / **PostCompact** | Fires before/after context compaction | Monitor when agents hit context limits — critical for long-running ISP analysis |
| **WorktreeCreate** / **WorktreeRemove** | Fires on git worktree operations | Track parallel file editing across your 5 agents' isolated worktrees |

**The critical exit code distinction:**

> **Exit code 2 blocks the action. Exit code 1 does NOT.**

This is the most common hooks mistake. If your PostToolUse hooks use `exit 1` to signal a governance violation, **the action still proceeds**. Only `exit 2` actually blocks. Verify your governance hooks immediately:

```bash
# Check your hooks for exit code correctness
grep -r "exit 1" .claude/hooks/ 
# If any governance hooks use exit 1, change to exit 2
```

**HTTP hooks for remote observability:**

The Claude Lab guide documents HTTP hooks — hooks that POST event data to a remote URL instead of running a local script. For your pipeline's routine-based automation (nightly runs on Anthropic's cloud), local hooks can't phone home to your disler dashboard. HTTP hooks solve this: configure your PostToolUse hook as an HTTP POST to your dashboard's event ingestion endpoint, and routine-based runs feed the same dashboard as local runs.

```json
{
  "hooks": {
    "PostToolUse": [{
      "type": "http",
      "url": "https://your-dashboard.example.com/events",
      "method": "POST",
      "timeout": 5000
    }]
  }
}
```

### Key Takeaway

Add `SubagentStart` and `SubagentStop` hooks to your pipeline — they give you per-agent timing and cost tracking without modifying your domain agents' prompts. Check all governance hooks for exit code 2 (not exit 1) — exit 1 doesn't block, which means a governance violation could silently pass. If you're running routines on Anthropic's cloud, HTTP hooks let remote runs feed your local observability dashboard.

### Why This Is Relevant

Your Angela Jiang question at London asked about dreaming's interaction with governance hooks. Now that London Day 1 is behind you, it's time to evaluate the three Managed Agents features through the lens of your pipeline's roadmap — not as theoretical questions, but as concrete next-sprint candidates.

**Feature 1: Dreaming — Background self-improvement between sessions**

Dreaming is a scheduled process that reviews past agent sessions, extracts patterns, and curates memory stores. Harvey (legal AI) saw **~6x higher task completion rates** with dreaming enabled.

**How this maps to your pipeline:**

Your domain agents currently start fresh each run — they don't learn from previous analyses of similar ISP clusters. With dreaming, your API contract agent could remember patterns from previous runs: "Service X uses gRPC for internal communication and REST for external — check for this pattern in similar clusters." This is the difference between a stateless pipeline and a learning pipeline.

**The governance question you raised at London:** Dreaming reviews past sessions, including sessions where governance hooks blocked actions. Your concern — that dreaming could learn to reformulate blocked requests — is architecturally valid. The mitigation: dreaming operates on *curated* memories, not raw session transcripts. The curation step is where security-critical patterns can be filtered. Ask at the Extended workshops today whether the curation step is configurable — can you exclude governance-blocked actions from the dreaming input?

**Feature 2: Outcomes — Rubric-driven grading loops**

Outcomes let you define success criteria, and a separate grader model evaluates agent output against those criteria. The grader runs in its own context window — it's not influenced by the agent's reasoning.

**How this maps to your pipeline:**

Outcomes is the managed-platform version of your PostToolUse hooks + golden file evals. The architectural pattern is identical — independent verification — but Outcomes automates the iteration loop: if the grader says "incomplete," the agent automatically retries. Your pipeline currently stops on PostToolUse failure; Outcomes would make it self-correct.

| Your Current Approach | With Outcomes |
|----------------------|---------------|
| PostToolUse hook validates output | Grader evaluates against rubric |
| Failure stops the agent | Failure triggers agent retry |
| Manual re-run after fix | Automatic iteration until pass |
| Custom validation scripts | Declarative rubric definition |

**Feature 3: Multiagent Orchestration — Up to 20 parallel specialists**

Managed multiagent orchestration supports up to 20 specialist subagents with 25 concurrent threads on a shared filesystem. This is your 5-agent pipeline pattern, but on the managed platform with higher scale headroom.

**The strategic decision:**

Your pipeline currently runs on Claude Code (CLI/local). Managed Agents offers the same patterns on Anthropic's hosted platform. The question for your post-London sprint: **stay on Claude Code, migrate to Managed Agents, or run both?**

| Claude Code (current) | Managed Agents (potential) |
|----------------------|---------------------------|
| Full hook control (32+ events) | Platform-managed lifecycle |
| Local + routine execution | Cloud-native execution |
| Custom observability (disler dashboard) | Built-in monitoring |
| You manage coordination | Platform manages coordination |
| 5 agents (your proven architecture) | Up to 20 agents (room to grow) |

**Recommendation:** Stay on Claude Code for your governance-heavy pipeline — the hook control and custom observability are your differentiators. Use Managed Agents for new, less governance-critical workloads where platform automation saves engineering time. Don't migrate a working pipeline to chase a feature set — extend it.

### Key Takeaway

The three Managed Agents features validate your pipeline's architecture: dreaming is the learning loop you don't have yet, outcomes is the managed version of your PostToolUse validation, and multiagent orchestration mirrors your Agent Teams pattern at higher scale. For your post-London sprint, the highest-value investigation is dreaming — a learning pipeline that improves across runs is the step change, not incremental. At today's Extended workshops, ask about dreaming's curation step and whether governance-blocked actions can be excluded from the dreaming input.

## Quick Win: Add SubagentStart/SubagentStop Hooks for Per-Agent Timing (5 min)

**Time: 5 minutes**

Your disler observability dashboard tracks PostToolUse events, but you don't have per-agent lifecycle tracking. The `SubagentStart` and `SubagentStop` events, available in v2.1.141+, give you exactly this — without changing your domain agents' prompts.

Add these to your `.claude/settings.json`:

```json
{
  "hooks": {
    "SubagentStart": [{
      "type": "command",
      "command": "echo '{\"event\":\"agent_start\",\"agent\":\"$CLAUDE_AGENT_NAME\",\"timestamp\":\"'$(date -Iseconds)'\"}' >> ~/.claude/agent-timeline.jsonl"
    }],
    "SubagentStop": [{
      "type": "command",
      "command": "echo '{\"event\":\"agent_stop\",\"agent\":\"$CLAUDE_AGENT_NAME\",\"timestamp\":\"'$(date -Iseconds)'\"}' >> ~/.claude/agent-timeline.jsonl"
    }]
  }
}
```

This appends a JSONL log of agent start/stop events. Your disler dashboard can ingest this file to render per-agent timelines — showing which agents run in parallel, which finish first, and where the bottleneck is (typically synthesis, waiting for all domain agents).

**Also check right now:** Verify your governance hooks use `exit 2`, not `exit 1`. Exit 1 doesn't block — it's the most common hooks mistake and could mean your hard_deny rules are silently passing violations.

```bash
# Quick audit
grep -rn "exit 1" .claude/hooks/ .claude/settings.json 2>/dev/null
# Change any governance exits from 1 to 2
```

**Why today:** You're at the Extended workshops with your laptop open. Add the hooks, run the pipeline once, and check the timeline output. If it works, you have a new observability primitive to show Anthropic engineers during the workshop. If it doesn't (event name mismatch, environment variable not populated), you can debug it with Anthropic's Applied AI team in the room.
