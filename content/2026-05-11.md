## Resource 1: Claude Code Routines — Put Your ISP Pipeline on Autopilot

**Source:** [Automate work with routines — Claude Code Docs](https://code.claude.com/docs/en/routines)
**Also:** [Claude Code Routines: AI Automation Replacing No-Code Tools — ClaudeFast](https://claudefa.st/blog/guide/development/routines-guide)
**Also:** [Claude Code Routines Tutorial: Schedule, API, and GitHub Triggers — Builder.io](https://www.builder.io/blog/claude-code-routines)
**Time:** ~6 min read (official docs + ClaudeFast summary)
**Category:** Automation — The Missing Layer Between Your Pipeline and Production

### Why This Is Relevant

Routines shipped in Week 16 (April 13–17) and are now stable in research preview. A routine is a saved Claude Code configuration — a prompt, repositories, and connectors — that runs on Anthropic's cloud infrastructure. This is the operational layer your ISP pipeline has been missing: your `/reverse-engineer` skill runs when *you* invoke it, but routines let it run when an *event* demands it.

**Three trigger types, each maps to a pipeline use case:**

| Trigger | How It Works | Your Pipeline Application |
|---------|-------------|--------------------------|
| **Scheduled** | Recurring cadence (hourly, daily, weekly) or one-off timestamp | Run `/reverse-engineer` nightly against newly onboarded legacy clusters — wake up to fresh API contracts and dependency maps |
| **API** | HTTP POST to a per-routine endpoint with bearer token | Wire your monitoring stack to trigger pipeline runs when a service cluster's error rate crosses a threshold — the pipeline reverse-engineers the failing cluster and opens a fix PR |
| **GitHub** | React to repository events (PRs, releases) | When a PR merges to a legacy service repo, automatically re-run the pipeline to keep documentation in sync with code changes |

**Key architectural details that matter for your setup:**

- **Routines run as full cloud sessions** — no permission prompts, no approval gates. They execute shell commands, use skills committed to the repo (including your `/reverse-engineer` skill), and call any MCP connectors you include.
- **Branch isolation by default** — routines push only to `claude/`-prefixed branches unless you explicitly unlock unrestricted pushes. This means your pipeline's output PRs land on `claude/reverse-engineer-{cluster-name}` branches for human review before merge.
- **Connectors included** — your Slack, Linear, or Jira MCP connectors work inside routines. The pipeline can post summaries to your team channel after each run.
- **Environment control** — set network access, environment variables (API keys for your MLflow instance), and setup scripts (install your pipeline's dependencies). The setup is cached so it doesn't re-run every session.

**For your presentation:** Routines are the "Level 4" of your maturity arc. Level 1: one-shot prompts. Level 2: custom skills. Level 3: multi-agent orchestration. Level 4: event-driven autonomous operation. Your audience goes from "what is Claude Code?" to "it runs without a human in the loop, with governance guardrails" in four slides.

**Setup in 2 minutes from the CLI:**

```bash
# Create a scheduled routine conversationally
/schedule nightly reverse-engineer run at 2am

# Or a one-off
/schedule tomorrow at 9am, run reverse-engineer against the payments cluster

# Manage existing routines
/schedule list
/schedule update
/schedule run
```

### Key Takeaway

Create a proof-of-concept routine this week: schedule your `/reverse-engineer` skill to run nightly against one legacy cluster. Use the CLI (`/schedule`) to set it up in under 2 minutes. Start with a scheduled trigger on a non-critical cluster — the routine pushes to a `claude/` branch so nothing merges without your review. Once validated, add a GitHub trigger so the pipeline re-runs automatically when PRs merge to that cluster's repo. This is the "Level 4 maturity" slide for your presentation, backed by a live demo.

## Resource 2: Week 19 Release — Effort-Aware Hooks and Auto Mode Hard Deny Rules

**Source:** [What's new — Week 19 digest — Claude Code Docs](https://code.claude.com/docs/en/whats-new/2026-w19)
**Also:** [Claude Code Changelog — Official Docs](https://code.claude.com/docs/en/changelog)
**Also:** [Claude Code Releases — GitHub](https://github.com/anthropics/claude-code/releases)
**Time:** ~4 min read (Week 19 digest + changelog scan)
**Category:** Platform — Two Features That Harden Your Pipeline's Governance

### Why This Is Relevant

Week 19 (May 4–8) shipped two features that directly strengthen the governance layer you've been building across the last three digests (dreaming security controls → PostToolUse output replacement → today's operational automation).

**1. Hooks now see the active effort level via `effort.level` and `$CLAUDE_EFFORT`**

Your PostToolUse hooks can now read the current effort level — `low`, `medium`, `high`, or `xhigh`. This enables effort-adaptive validation: run lightweight schema checks at `low` effort for quick iterations, and full cross-reference validation at `xhigh` effort for production runs.

**What this means for your pipeline:**

```python
import json, sys, os

hook_input = json.load(sys.stdin)
effort = os.environ.get("CLAUDE_EFFORT", "high")

if effort in ("xhigh", "high"):
    # Full validation: schema check + cross-cluster dependency resolution
    run_full_validation(hook_input)
elif effort == "medium":
    # Schema check only
    run_schema_validation(hook_input)
else:
    # Quick iteration: skip validation
    pass
```

When you're iterating on skill prompts during development, set effort to `low` — hooks step aside and you get fast feedback. When the routine runs nightly in production, effort is `xhigh` — hooks run the full validation suite. One hook configuration, two behaviors, zero manual toggling.

**2. Auto mode hard deny rules block actions unconditionally**

Auto mode (shipped Week 13) uses a classifier to handle permission prompts — safe actions run, risky ones get blocked. Hard deny rules are the new addition: they block actions *unconditionally*, regardless of what the classifier decides. No allow exceptions can override them.

**For your pipeline:** Add hard deny rules for actions your pipeline agents must never take:

- `rm -rf /` — obvious, but defense-in-depth matters
- `git push --force` to protected branches — your pipeline opens PRs, it never force-pushes
- `DROP TABLE` or `DELETE FROM` without `WHERE` — if your pipeline touches databases during reverse-engineering

Hard deny rules are the "never" layer. Auto mode's classifier handles the gray area. Your PostToolUse hooks handle the output quality. Together: a three-tier governance model (deny → classify → validate) that's presentation-ready.

**3. Plugins load from `.zip` archives and URLs**

`--plugin-dir` now accepts `.zip` files, and `--plugin-url` fetches a plugin archive for the current session. This opens a distribution path for your `/reverse-engineer` skill: package it as a plugin zip and share it with teammates via URL, no repo cloning required.

### Key Takeaway

Add `$CLAUDE_EFFORT` awareness to your PostToolUse validation hook today. The pattern: full validation at `xhigh`/`high` (production routine runs), schema-only at `medium` (code review), skip at `low` (fast iteration). Then define 2-3 hard deny rules in auto mode for actions your pipeline agents must never take. This completes your three-tier governance model: hard deny rules (unconditional blocks) → auto mode classifier (contextual permissions) → PostToolUse hooks (output quality). Add this as the "Governance Architecture" slide in your presentation.

## Resource 3: 45 Claude Code Tips — The Ops Patterns You're Not Using Yet

**Source:** [ykdojo/claude-code-tips — GitHub (45 tips)](https://github.com/ykdojo/claude-code-tips)
**Also:** [50 Claude Code Tips and Best Practices — Builder.io](https://www.builder.io/blog/claude-code-tips-best-practices)
**Time:** ~5 min (targeted scan of the 10 most relevant tips below)
**Category:** Workflow — Operational Efficiency for Daily Pipeline Development

### Why This Is Relevant

You've been building sophisticated pipeline architecture for 9 weeks. But your *daily operational workflow* — how you iterate, debug, and context-switch between pipeline agents — may have patterns worth upgrading. This curated repo (45 tips, actively maintained) surfaces techniques organized by experience level. Here are the 10 most relevant to your current work:

**Context management (your biggest constraint):**

| Tip | Technique | Your Application |
|-----|-----------|-----------------|
| Handoff documents | Create a structured summary before `/compact` or starting a new session | After a long pipeline debugging session, write a handoff doc capturing what you learned, what's broken, and what to try next — new sessions start at 80% context instead of 0% |
| Targeted file reads | Read only the lines you need, not entire files | When debugging a specific agent in your 5-agent pipeline, read only that agent's prompt section — not the entire skill file |
| `/compact` with custom prompts | Pass a focus area to compact | `/compact focus on the dependency mapper agent's output schema issues` preserves the context you need and drops the rest |

**Parallel development (accelerate pipeline iteration):**

| Tip | Technique | Your Application |
|-----|-----------|-----------------|
| Git worktrees | Spin up 3-5 worktrees, each with its own Claude session | Run each pipeline agent in its own worktree — iterate on the API contract agent in worktree 1 while the dependency mapper runs in worktree 2 |
| Containers for risky tasks | Run experimental work in Docker isolation | Test pipeline changes against production-like service clusters in a container — if the pipeline breaks something, only the container is affected |
| Background agents | Use `run_in_background` for independent tasks | Kick off a pipeline test run in the background while you continue editing skill prompts in the foreground |

**Testing and verification:**

| Tip | Technique | Your Application |
|-----|-----------|-----------------|
| TDD for skills | Write expected output first, then iterate on prompts | Define what a correct API contract looks like (golden file), then tune your agent until it matches — like unit testing for AI output |
| Write-test cycles | Establish verification after every change | After each skill prompt edit, run the pipeline against a known cluster and diff the output against your golden files |

**Distribution (preparing for your BCG presentation):**

| Tip | Technique | Your Application |
|-----|-----------|-----------------|
| Plugin packaging | Package skills as distributable plugins | With the new `--plugin-url` flag (Week 19), your `/reverse-engineer` skill can be shared as a `.zip` URL — demo it at Code with Claude London |
| Custom commands for team onboarding | Create `.claude/commands/` for common workflows | Build a `/setup-isp-pipeline` command that installs dependencies, configures MCP connectors, and runs a health check — one command to onboard a teammate |

### Key Takeaway

Start using handoff documents today. Before your next `/compact` or session end, spend 60 seconds writing: (1) what you were working on, (2) what's broken, (3) what to try next. Paste it at the start of your next session. This one habit recovers 5-10 minutes of context-rebuilding per session — across 9 weeks of daily iteration, that's hours recovered. Then try the git worktree pattern: run your API contract agent and dependency mapper in parallel worktrees to cut iteration time in half.
