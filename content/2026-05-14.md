## Resource 1: Addy Osmani's "Conductors to Orchestrators" — The Narrative Spine for Your BCG Presentation

**Source:** [Conductors to Orchestrators: The Future of Agentic Coding — O'Reilly](https://www.oreilly.com/radar/conductors-to-orchestrators-the-future-of-agentic-coding/)
**Also:** [The Code Agent Orchestra — AddyOsmani.com](https://addyosmani.com/blog/code-agent-orchestra/)
**Also:** [Orchestrating Coding Agents — O'Reilly CodeCon Talk, March 2026](https://talks.addy.ie/oreilly-codecon-march-2026/)
**Time:** ~6 min read (O'Reilly article + skim the blog post for practical patterns)
**Category:** Presentation Framework — The Story That Makes Your Pipeline Click

### Why This Is Relevant

Your presentation needs a narrative arc that a non-technical BCG audience can follow. You have the technical layers (governance, orchestration, observability) and the maturity model (Sequential → Headless). What you're missing is the **human story** — how the developer's role evolves. Addy Osmani (Google Chrome engineering lead) published exactly this framework on O'Reilly, and it maps perfectly to your journey.

**The core evolution:**

| Stage | Developer Role | Your Pipeline Stage | What Changes |
|-------|---------------|--------------------|--------------| 
| **Coder** | Writes every line manually | Pre-Claude Code | Human does all implementation |
| **Conductor** | Guides one AI through sequential steps | One-shot prompts → Custom skills | Human in the loop for every step |
| **Orchestrator** | Manages fleets of autonomous agents | Agent Teams → Routines | Human front-loads specs, back-loads review — the middle runs itself |

**Why this matters for your BCG audience:**

The conductor-to-orchestrator shift isn't just about code — it's about **how consultants will work**. Today, a consultant manually guides Claude through each analysis step (conductor). Tomorrow, a consultant defines the analysis spec, triggers a routine, and reviews the output (orchestrator). Your ISP pipeline is a live example of this transition: you don't guide each of the 5 agents step-by-step — you define the cluster, trigger the pipeline, and review the synthesized documentation.

**Three architectural insights from Osmani that strengthen your slides:**

**1. "Three focused agents consistently outperform one generalist agent working three times as long."**

This is your justification for the 5-agent design. Your pipeline doesn't use 5 agents because the problem is complex — it uses 5 agents because **parallel specialization beats serial generalism**. The API contract agent, dependency mapper, billing analyst, auth specialist, and synthesis agent each see a narrower problem with a fuller context window. This is the slide that converts skeptics.

**2. The coordination layer determines success, not individual agent quality.**

This echoes Anthropic's own finding (Digest #45: 90.2% improvement from coordination, not individual agents). Osmani's framing: "the orchestrator's job is to decompose well, delegate clearly, and synthesize rigorously." Your conductor agent's prompt — how it analyzes the cluster, assigns domains to specialists, and merges their outputs — is the highest-leverage code in your entire pipeline.

**3. Hierarchical delegation: spawn leads that spawn specialists.**

Osmani describes a pattern where feature leads spawn their own sub-specialists, giving "3x deeper decomposition without exploding anyone's context window." Your current pipeline is flat (conductor → 4 domain agents + synthesis). The next evolution — which you can tease in your "What's Next" slide — is hierarchical: the API contract agent spawns sub-agents for REST, GraphQL, and gRPC analysis. This is the roadmap that shows you've thought beyond v1.

**For your slide deck outline, use this three-act structure:**

- **Act 1 — The Problem:** Legacy ISP clusters are black boxes. Manual reverse-engineering takes weeks. (2 slides)
- **Act 2 — The Evolution:** Coder → Conductor → Orchestrator. Show the maturity arc with live pipeline examples at each stage. (5 slides, using the five workflow patterns from Digest #45)
- **Act 3 — The Implications:** What this means for BCG consulting. The 60% delegation stat. Claude Security partnership. The shift from implementer to orchestrator as a career trajectory. (3 slides)

### Key Takeaway

Use the Coder → Conductor → Orchestrator evolution as the narrative spine of your presentation. Act 1 sets the problem (legacy complexity), Act 2 shows the technical journey (five workflow patterns with your pipeline at each stage), Act 3 lands the business message (how this changes consulting). Osmani's O'Reilly credibility and the "three focused agents outperform one generalist" stat give your audience two independently verifiable data points. Draft the 10-slide outline today using this three-act structure.

**Category:** Tooling — Use Claude Code to Build the Presentation About Claude Code

### Why This Is Relevant

Today is Day 3: create your slide deck outline. You could open PowerPoint and start from scratch — or you could use Claude Code itself to generate the deck. This is meta in the best way: **demonstrating Claude Code's capability by using it to build the presentation about Claude Code.** If someone in your BCG audience asks "but can it do real work?", your answer is "it built this deck."

**Two approaches, pick the one that fits your BCG template requirements:**

**Approach A: PPTX from Layouts (template-compliant)**

The `pptx-from-layouts-skill` generates PowerPoint decks from markdown using your template's actual slide master layouts. This is the consulting-grade approach — it respects BCG's branded templates:

```bash
# Install the skill
claude skill install github:tristan-mcinnis/pptx-from-layouts-skill

# Generate from your outline
/pptx-from-layouts --template bcg-template.pptx --input outline.md --output genai-sdlc-presentation.pptx
```

The skill reads your template's slide masters, maps markdown headings to layouts (title slide, section header, content, two-column), and produces an editable `.pptx` that looks like it was built in PowerPoint. No image overlays, no weird formatting — real PowerPoint shapes and text boxes.

**Approach B: Marp (fast iteration, export later)**

If you want to iterate on content first and worry about formatting later, the Claude Code + Marp workflow from freeCodeCamp is faster:

```bash
# Install Marp CLI
npm install -g @marp-team/marp-cli

# Write slides as markdown, let Claude Code iterate on content
# Then export to PPTX when content is finalized
marp presentation.md --pptx --output genai-sdlc-presentation.pptx
```

Marp lets you write slides as markdown — which means Claude Code can edit, restructure, and refine your slides as easily as editing any code file. The feedback loop is seconds, not minutes. Once content is locked, export to PPTX and apply BCG branding manually.

**The freeCodeCamp article's key insight:** "Use Claude Code to think through your presentation structure, not just generate slides." The workflow: (1) describe the audience and goal to Claude, (2) let it draft a structure, (3) iterate on the narrative before touching any slide tool, (4) generate slides only after the story is solid. This matches your Day 3 task — outline first, deck second.

**For your pipeline demo slides specifically:** Use Claude Code to generate architecture diagrams as Mermaid code, then render them into your slides. Your 5-agent pipeline architecture, the three-tier governance model, and the routine trigger flow all map naturally to Mermaid diagrams that Claude Code can generate and iterate on.

### Key Takeaway

Install the `pptx-from-layouts-skill` today and generate a first draft of your deck from a markdown outline. Start with Approach B (Marp) for fast content iteration: write your 10-slide outline as markdown, let Claude Code refine the narrative, then export to PPTX and apply BCG branding. The meta win: open your presentation with "this deck was generated by Claude Code using the same skill system I'm about to show you" — it's the most convincing demo you can give without touching your pipeline.
