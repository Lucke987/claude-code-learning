## Resource 1: The Code Agent Orchestra — What Makes Multi-Agent Coding Work (Addy Osmani)

**Source:** [The Code Agent Orchestra — Addy Osmani](https://addyosmani.com/blog/code-agent-orchestra/)
**Also:** [O'Reilly CodeCon Talk — Orchestrating Coding Agents](https://talks.addy.ie/oreilly-codecon-march-2026/)
**Time:** ~6 min read
**Category:** Architecture — Multi-Agent Orchestration Patterns

### Why This Is Relevant

Addy Osmani (Chrome engineering lead at Google, O'Reilly author) published the most rigorous public analysis of multi-agent coding patterns to date. This isn't a Claude-specific tutorial — it's a framework for understanding *why* certain multi-agent patterns work and others don't. For your GenAI in SDLC presentation, this provides the conceptual backbone that ties your entire ISP pipeline story together.

**The three orchestration tiers directly map to your journey:**

| Tier | Pattern | Your ISP Implementation |
|------|---------|------------------------|
| 1. Subagents | Parent spawns specialized children, children report back only to parent | Your early `/reverse-engineer` skill with basic subagent spawning |
| 2. Agent Teams | Shared task list, peer-to-peer messaging, file locking | Your current 5-agent setup with structured JSON handoffs |
| 3. Orchestrator | Developer as conductor — guiding, reviewing, redirecting agents in real-time | Where you're heading: `/plan` phase gates + `/ultrareview` verification loops |

**The key finding for your presentation:** "Three focused agents consistently outperform one generalist agent working three times as long." This is the empirical backing for your Agent Teams architecture decision — it's not just faster, it's *better*. Specialization + isolation + parallel execution produces compound gains, not just linear speedup.

**The Ralph Loop pattern — a new tool for your kit:**

The Ralph Loop breaks work into atomic tasks and runs agents in a stateless-but-iterative loop: pick task, implement, validate, commit if pass, reset context and repeat. This solves your context rot problem from a completely different angle than `/compact` — instead of managing context within a long session, you *eliminate* the long session entirely. Each iteration starts fresh.

For ISP analysis, consider a hybrid: use Agent Teams for the initial architecture discovery (where cross-service context matters), then switch to a Ralph Loop for individual service deep-dives (where fresh context per service prevents cross-contamination of findings).

**For the GenAI in SDLC presentation:**

*"Multi-agent orchestration follows a maturity curve: from subagents (simple delegation) to agent teams (coordinated parallelism) to full orchestration (developer as conductor). Our ISP pipeline demonstrates this progression — each tier unlocked capabilities the previous couldn't achieve."*

### Key Takeaway

Use Osmani's three-tier framework (subagents → agent teams → orchestrator) as the narrative structure for your GenAI in SDLC presentation's "how we work" section. It gives the audience a mental model for understanding why you chose Agent Teams over single-agent execution, and where the industry is heading next.

## Resource 3: Ultraplan — Planning in the Cloud, Executing Wherever You Want

**Source:** [Claude Code Ultraplan — Steve Kinney](https://stevekinney.com/writing/claude-ultraplan)
**Also:** [Plan in the Cloud with Ultraplan — Official Docs](https://code.claude.com/docs/en/ultraplan)
**Also:** [Ultraplan: Planning in the Cloud, Executing Wherever — Mark Craddock (Medium)](https://medium.com/arckit/claude-code-ultraplan-planning-in-the-cloud-executing-wherever-you-want-f4112ccd5e3c)
**Time:** ~5 min read (Steve Kinney's practical walkthrough)
**Category:** Workflow — Cloud Planning for Complex Analysis

### Why This Is Relevant

Your April 24 digest recommended adding a `/plan` phase before each Agent Teams run. Ultraplan is the cloud-native evolution of that approach — it offloads the planning phase to a web session where you can comment on individual sections, collaborate with colleagues, and approve execution asynchronously. Your terminal stays free for other work while the plan drafts.

**Why this matters for ISP at scale:**

When you run `/plan` locally, the plan drafts in your terminal and you review it inline. For a 47-service architecture analysis, the plan itself can be substantial — service groupings, analysis order, dependency assumptions, output format specifications. Ultraplan moves this to a browser-based editor where:

- You can comment on specific plan sections ("Swap the order of billing and provisioning clusters — billing has upstream dependencies we need to map first")
- A colleague can review the analysis plan before you spend tokens executing it
- You choose where to execute: run it on the web (cloud compute, your laptop stays free) or pull it back to your terminal

**The commit-before-plan discipline:**

Steve Kinney emphasizes a critical operational detail: Ultraplan syncs via your repo's git remote. Always commit and push before running `/ultraplan` for anything important — local-only changes won't be visible to the cloud session. For your ISP workflow, this means: complete your CLAUDE.md updates and skill modifications, commit, push, *then* `/ultraplan` the analysis run.

**Integration with your existing pipeline:**

```
1. Update CLAUDE.md + skills (local)
2. Commit & push
3. /ultraplan "Analyze ISP billing cluster: 12 services, 
   map boundaries, extract API contracts, identify coupling hotspots"
4. Review plan in browser — add comments, adjust scope
5. Execute in cloud OR pull back to terminal for Agent Teams run
6. /ultrareview the results
```

This gives you a fully cloud-enabled pipeline: plan in the cloud, execute wherever makes sense, verify with /ultrareview.

### Key Takeaway

Try `/ultraplan` for your next ISP cluster analysis plan. The browser-based review surface is better than terminal for complex plans, and having the plan draft in the cloud while your terminal stays free for other work is a meaningful workflow improvement. Just remember: commit and push first.
