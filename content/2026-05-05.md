## Resource 1: Skills 2.0 — Evaluate, A/B Test, and Optimize Your `/reverse-engineer` Skill

**Source:** [Claude Code Skills 2.0: Evals, Benchmarks and A/B Testing for Skills that Actually Work — Pasquale Pillitteri](https://pasqualepillitteri.it/en/news/341/claude-code-skills-2-0-evals-benchmarks-guide)
**Also:** [How to Use Claude Code Skills 2.0: Built-In Evaluation and A/B Testing — MindStudio](https://www.mindstudio.ai/blog/claude-code-skills-2-evaluation-ab-testing)
**Also:** [Claude Code: How to Write, Eval, and Iterate on a Skill — Mager.co](https://www.mager.co/blog/2026-03-08-claude-code-eval-loop/)
**Also:** [The Complete Guide to Testing Claude Code Skills — Lathesh Karkera, Medium](https://medium.com/@karkeralathesh/the-complete-guide-to-testing-claude-code-skills-with-the-skill-creator-1ae3821bd7b8)
**Time:** ~6 min read (Pasquale's guide — the clearest end-to-end walkthrough)
**Category:** Quality — From Intuition-Driven Prompts to Data-Driven Skills

### Why This Is Relevant

You've iterated on your `/reverse-engineer` skill across 36 digests — adjusting prompts, refining agent roles, tuning output schemas. Every change was guided by intuition: "that output looks better." Skills 2.0 replaces intuition with measurement. The skill-creator now includes four modes that turn skill development into an engineering discipline:

**The four modes and what they do for your pipeline:**

| Mode | What It Does | Your Use Case |
|------|-------------|---------------|
| **Create** | Interview → research → draft → test | Already done — your skill exists |
| **Eval** | Run skill on test prompts, grade outputs against criteria | Test `/reverse-engineer` against known ISP codebases |
| **Improve** | Execute → grade → blind A/B compare → analyze → iterate | Compare prompt V1 vs V2 on the same microservice |
| **Benchmark** | Multiple runs with variance analysis | Measure consistency across 10 runs of the same cluster |

**How evals work in practice:**

1. You define test prompts — e.g., "Reverse-engineer the billing microservice in this sample repo"
2. You define grading criteria — e.g., "Output must include: API contracts (JSON schema), dependency map, coupling score, service boundaries"
3. The skill-creator runs your skill on each test prompt, grades the output against your criteria, and reports pass/fail with explanations
4. You iterate on the skill prompt and re-run evals until pass rates meet your threshold

**How A/B testing eliminates bias:**

A/B testing runs two skill versions on the same inputs. A separate Claude instance reviews both outputs *without knowing which is which*, picks a winner, and explains why. This eliminates the confirmation bias that plagues manual prompt iteration — you can't unconsciously favor the version you just wrote.

**Trigger optimization — the hidden accuracy problem:**

Your skill's frontmatter (name, description, trigger conditions) determines when Claude Code invokes it. The skill-creator's trigger optimization:
1. Splits your test queries into 60% training / 40% held-out test sets
2. Evaluates current trigger accuracy (does `/reverse-engineer` fire when it should, and not fire when it shouldn't?)
3. Proposes improved descriptions based on failure analysis
4. Re-evaluates on both training and test sets

Anthropic reports that 5 of 6 public skills showed improved trigger accuracy after optimization. If your `/reverse-engineer` skill sometimes fires on non-reverse-engineering queries (or fails to fire when it should), this fixes it automatically.

**The headline number:** One developer improved skill success rates from 67% to 94% in two optimization cycles. That's the difference between a skill that works "most of the time" and one you trust for autonomous cloud execution.

### Key Takeaway

Run the skill-creator in Eval mode on your `/reverse-engineer` skill this week. Define 3-5 test prompts (one per ISP domain cluster plus an edge case like a monolith with no clear service boundaries) and 3-4 grading criteria (API contracts present, dependency map complete, coupling score calculated, output conforms to JSON schema). The eval results will show you exactly where your skill fails — and the Improve mode will systematically fix those failures with blind A/B testing. This is the "continuous improvement" slide your presentation needs.

## Resource 2: Opus 4.7 and the xhigh Effort Level — What Changed Under Your Pipeline

**Source:** [Introducing Claude Opus 4.7 — Anthropic](https://www.anthropic.com/news/claude-opus-4-7)
**Also:** [Claude Opus 4.7: Vision, Coding Gains, and xhigh Effort — Claudefast](https://claudefa.st/blog/models/claude-opus-4-7)
**Also:** [Effort — Claude API Docs](https://platform.claude.com/docs/en/build-with-claude/effort)
**Also:** [Claude Opus 4.7 Best Practices for Claude Code — Claudefast](https://claudefa.st/blog/guide/development/opus-4-7-best-practices)
**Time:** ~4 min read (Anthropic announcement + Claudefast best practices)
**Category:** Platform — The Model Change That Already Affects Your Pipeline Cost

### Why This Is Relevant

Your Agent Teams pipeline runs 5 agents, each making multiple model calls for analysis, synthesis, and JSON generation. The model and effort level beneath those calls directly determine output quality and token cost. Two things changed recently that you may not have noticed:

**1. Opus 4.7 is now available in Claude Code**

Opus 4.7 launched in April 2026 with improvements to coding, vision, and agentic workflows. It's available via the `/model` picker in Claude Code and via `--model claude-opus-4-7` in headless mode. Key improvements relevant to your pipeline:

- **Better agentic performance:** Improved at multi-step tool use — exactly what your 5-agent pipeline does. Better at deciding when to call tools, how to interpret results, and when to stop.
- **Stronger coding benchmarks:** Higher scores on SWE-bench and other code understanding tasks — directly relevant to reverse-engineering microservices.
- **Improved vision:** If your pipeline ever analyzes architecture diagrams or screenshots, Opus 4.7 handles them better.

**2. Default effort level raised to `xhigh`**

The effort scale now has five levels: `low`, `medium`, `high`, `xhigh`, `max`. Claude Code defaults to `xhigh` for all plans. This is the level between `high` and `max` — it provides most of the deep reasoning capability of `max` without the full token cost.

**What this means for your pipeline's economics:**

| Effort Level | Thinking Tokens | Quality | Cost Impact |
|-------------|----------------|---------|-------------|
| `high` | Moderate | Good for routine tasks | Lower |
| **`xhigh` (new default)** | **Substantial** | **Strong for complex analysis** | **~20-40% more than `high`** |
| `max` | Maximum | Best for hardest problems | Highest |

If your pipeline was tuned for `high` effort (the previous default), it's now using more thinking tokens on every call. For 5 agents processing 47 microservices, that cost increase is multiplicative.

**The strategic move — differentiated effort per agent role:**

Not every agent in your pipeline needs the same reasoning depth:

```
Lead agent (synthesis, cross-cluster reasoning):  max or xhigh
Domain cluster agents (structured extraction):     high
JSON schema validation steps:                      low
```

You can set effort per agent using `--effort` in headless mode or via the `/effort` command. For your Agent SDK rebuild (Digest #34), this becomes programmatic: set effort per agent in code.

**How to check your current setting:**

In Claude Code, run `/effort` to see and change the current effort level. Or use `/config` to set a persistent default.

### Key Takeaway

Check your current effort level with `/effort` and run a cost comparison: execute one cluster analysis at `high` and one at `xhigh`, then compare output quality and token cost via `/usage`. If `xhigh` produces materially better dependency maps or API contract extraction, keep it. If the output quality is equivalent for structured extraction tasks, drop domain cluster agents to `high` and reserve `xhigh` or `max` for the lead agent's synthesis step. This is the first optimization you should make when you move to the Agent SDK — differentiated effort by agent role.

## Resource 3: `claude mcp serve` — Expose Your Pipeline to External Systems

**Source:** [Claude Code MCP Server: Complete Setup Guide — ksred](https://www.ksred.com/claude-code-as-an-mcp-server-an-interesting-capability-worth-understanding/)
**Also:** [Connect Claude Code to tools via MCP — Claude Code Docs](https://code.claude.com/docs/en/mcp)
**Also:** [Claude Code MCP Servers: How to Connect, Configure, and Use Them — Builder.io](https://www.builder.io/blog/claude-code-mcp-servers)
**Also:** [Multi-Agent Orchestration: Running 10+ Claude Instances in Parallel — DEV Community](https://dev.to/bredmond1019/multi-agent-orchestration-running-10-claude-instances-in-parallel-part-3-29da)
**Time:** ~5 min read (ksred guide — the most practical walkthrough of server mode)
**Category:** Architecture — From Closed Pipeline to Interoperable Service

### Why This Is Relevant

Your ISP pipeline is powerful but isolated — it runs inside Claude Code, triggered by you or by Routines. `claude mcp serve` flips the relationship: instead of Claude Code *consuming* tools via MCP, Claude Code *becomes* a tool that other systems consume. This is the interoperability layer that connects your pipeline to CI/CD, external agents, and team workflows.

**What `claude mcp serve` exposes:**

When you run `claude mcp serve`, Claude Code starts listening as an MCP server over stdio, exposing its built-in tools:

| Tool | What External Systems Can Do |
|------|---------------------------|
| `Bash` | Execute shell commands in your project |
| `Read` | Read files from the codebase |
| `Write` | Create or overwrite files |
| `Edit` | Make targeted edits to files |
| `GrepTool` | Search for patterns across files |
| `GlobTool` | Find files matching patterns |

**Three use cases for your ISP pipeline:**

**1. CI/CD Integration — Automated Pipeline Triggers**

A CI/CD pipeline can invoke Claude Code via MCP to run your `/reverse-engineer` skill automatically when new code is merged to an ISP repository. Instead of scheduling Routines, the pipeline triggers analysis on-demand:

```
CI detects merge → calls claude mcp serve → invokes /reverse-engineer → outputs JSON artifacts → CI stores results
```

**2. Parent Agent Delegation — Multi-System Orchestration**

If your team builds a higher-level orchestration agent (e.g., a project management agent that coordinates multiple analysis tools), it can delegate coding tasks to Claude Code via MCP. The parent agent handles planning and prioritization; Claude Code handles implementation and analysis.

**3. Team Workflow — Shared Analysis Capabilities**

Other team members using Claude Desktop or Cursor can invoke your Claude Code instance's tools. A colleague analyzing a different microservice cluster can call your pipeline's analysis tools without setting up their own Claude Code environment.

**Architecture details:**

- JSON-RPC 2.0 over stdio transport
- Each client connection spawns a new Claude Code process
- No state sharing between connections (isolation by default)
- Requires `--dangerously-skip-permissions` for headless MCP server mode (permissions can't be prompted interactively)

**The permission model matters:** Because MCP server mode runs headless, you must pre-approve all permissions. This is a security consideration — scope the permissions narrowly to what the pipeline needs (read access to ISP repos, write access to output directories, specific shell commands).

### Key Takeaway

`claude mcp serve` is the bridge between your Claude Code pipeline and external systems. You don't need to use it today — Routines and the Agent SDK are more immediate priorities. But when you're ready to integrate your ISP analysis into your team's CI/CD pipeline or let colleagues invoke your analysis tools from their own editors, this is the mechanism. File it as the next integration layer after your Agent SDK rebuild. For your presentation, it's a powerful point: "Our analysis pipeline isn't just a script — it's an interoperable service that any MCP-compatible tool can invoke."

## Quick Win: Run Skill-Creator Eval Mode on `/reverse-engineer` (10 min)

**Time: 10 minutes**

Open Claude Code in your ISP project directory and run:

```
/skill-creator eval reverse-engineer
```

The skill-creator will:
1. Ask you for test prompts — provide 3:
   - "Reverse-engineer the billing service cluster and produce API contracts"
   - "Analyze the provisioning microservices and map dependencies"
   - "Identify service boundaries and coupling scores for the network cluster"

2. Ask you for grading criteria — provide 4:
   - Output contains valid JSON conforming to your schema
   - API contracts include endpoint paths, methods, and request/response types
   - Dependency map identifies both direct and transitive dependencies
   - Coupling score is calculated with a numeric value and explanation

3. Run each test prompt through your skill and grade the output

**What you'll learn:** Where your skill passes and where it fails. The failures are your optimization targets — feed them into the Improve mode next, and the skill-creator will propose prompt changes and A/B test them blind.

**Why now:** You've spent 36 digests building this skill by intuition. In 10 minutes, you'll have your first *data point* on how well it actually performs against defined criteria. That data point is worth more than another week of intuitive tweaking — and it's the "engineering discipline" story that sets your GenAI presentation apart from every other "we used AI" talk.
