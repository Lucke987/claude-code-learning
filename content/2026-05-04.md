## Resource 1: Agent SDK Production Patterns — Circuit Breakers, Cost Caps, and State Persistence

**Source:** [Claude Agent SDK: Complete Production Patterns Guide 2026 — Digital Applied](https://www.digitalapplied.com/blog/claude-agent-sdk-production-patterns-guide)
**Also:** [Claude Agent SDK in Production: A Studio's Playbook — Autoolize](https://autoolize.com/blog/claude-agent-sdk-production-playbook/)
**Also:** [AI Agent Circuit Breakers: The Reliability Pattern Production Teams Are Missing — DEV Community](https://dev.to/waxell/ai-agent-circuit-breakers-the-reliability-pattern-production-teams-are-missing-5bpg)
**Also:** [Building Autonomous Agents with the Claude Agent SDK — CallSphere](https://callsphere.tech/blog/claude-agent-sdk-autonomous-agents)
**Time:** ~6 min read (Digital Applied guide + Autoolize playbook)
**Category:** Architecture — From Working Prototype to Reliable Production Agent

### Why This Is Relevant

Digest #34 introduced the Agent SDK as the tool to rebuild your `/reverse-engineer` pipeline as a deployable application. Digest #35 showed how worktree isolation enables parallel execution. But neither addressed the failure modes that matter in production: What happens when a teammate agent loops on the same tool call 50 times? When a single cluster analysis burns $80 in tokens instead of $20? When a transient API error crashes the lead agent mid-synthesis and you lose 4 cluster reports?

Autoolize shipped 40 production agents — three-quarters on the Claude Agent SDK — and distilled their lessons into a playbook. Their core philosophy: *"Production-grade agents look less like elaborate prompts and more like small, boring systems with aggressive guardrails."*

**The three patterns your ISP pipeline needs:**

**1. Circuit Breakers — Stop Runaway Loops**

A circuit breaker sets a hard ceiling on agent iterations per task (default recommendation: 25) and detects repetitive tool calls by hashing the last N calls. If any hash appears three times, the breaker trips.

| Metric | Without Circuit Breaker | With Circuit Breaker |
|--------|------------------------|---------------------|
| Tool calls per failed request | 47 (avg) | 3 |
| Token cost per failed request | $0.41 | $0.02 |
| Cost reduction on pathological path | — | **95%** |

For your ISP pipeline: if a domain-cluster agent can't parse a particularly complex microservice and starts looping on the same file-read/analysis cycle, the circuit breaker stops it after 3 repeated attempts instead of letting it burn through your token budget. The agent reports a partial result with the specific failure, and the lead agent can either retry with a different approach or flag it for human review.

**2. Cost Caps — Per-Task Budget Enforcement**

Every model call gets wrapped by a harness that reads current spend counters, compares against applicable caps, and raises a typed `CostCapExceeded` exception if the cap is hit. Caps operate at three levels:

```
Per-task:   $25 max per cluster analysis
Per-user:   $200 max per pipeline run
Per-tenant: $2000 max per month (ISP engagement budget)
```

For your ISP pipeline: set a per-task cap at 1.5x your baseline cluster cost (from the `/usage` exercise in Digest #32). If the billing cluster normally costs $30, cap it at $45. The cap catches anomalies — a suddenly chatty agent, an unexpected context explosion — before they double your pipeline cost.

**3. State Persistence — Survive Transient Failures**

The SDK session is ephemeral. The conversation log is the source of truth. For any agent longer than a single turn, persist state to Postgres, Redis, or object storage. For your ISP pipeline: after each cluster analysis completes, persist the structured JSON output to durable storage *before* the lead agent starts synthesis. If the lead agent crashes during the merge, you don't re-run 4 cluster analyses — you reload persisted results and retry only the synthesis step.

**The Autoolize mindset shift:**

> *"Spend an afternoon on the boring thing — a retry loop, an eval harness, a skill extraction — and buy yourself weeks of reliability."*

This is the transition from Digest #34's "build a minimal agent" to production: the agent logic is the easy part. The guardrails are the hard part. And the guardrails are what make the difference between a demo and a system your team trusts.

### Key Takeaway

When you build the Agent SDK prototype from Digest #34, add three things before your first test run: a circuit breaker (max 25 iterations, trip on 3 repeated tool calls), a per-task cost cap (1.5x your `/usage` baseline), and state persistence for cluster outputs. These aren't optimizations — they're prerequisites. A 5-agent pipeline without circuit breakers is a billing event waiting to happen. The Digital Applied guide has copy-paste Python patterns for all three.

## Resource 2: Claude Code Hooks — Automated Quality Gates for Your Pipeline

**Source:** [Claude Code Hooks: A Practical Guide to Workflow Automation — DataCamp](https://www.datacamp.com/tutorial/claude-code-hooks)
**Also:** [Claude Code Hooks: Complete Guide to All 12 Lifecycle Events — Claudefast](https://claudefa.st/blog/tools/hooks/hooks-guide)
**Also:** [Claude Code Hooks Tutorial: 5 Production Hooks From Scratch — Blake Crosley](https://blakecrosley.com/blog/claude-code-hooks-tutorial)
**Also:** [Claude Code Hooks: Automate Linting, Tests, and Commits — TeachMeIDEA](https://teachmeidea.com/claude-code-hooks-automate-linting-tests-commits/)
**Time:** ~5 min read (DataCamp tutorial — clearest walkthrough with examples)
**Category:** Operations — Deterministic Quality Control for Agent Output

### Why This Is Relevant

Your ISP pipeline produces structured JSON — API contracts, dependency maps, coupling analyses. In Digest #34, you identified "automated quality gates" as an open gap now that the pipeline runs unattended. `/ultrareview` solves the code-quality side. Hooks solve the output-quality side: deterministic validation that runs *every time*, without relying on the LLM to remember to validate.

**What hooks are and why they matter for your pipeline:**

Hooks are shell commands that execute at specific points in Claude Code's lifecycle — before a tool runs (PreToolUse), after a tool runs (PostToolUse), at session start (SessionStart), and 9 other events. The critical difference from prompting: hooks are *deterministic*. You don't ask Claude to validate JSON output — you *guarantee* it with a shell command that runs every time, regardless of what the agent decides to do.

**Three hooks that transform your ISP pipeline:**

**1. PostToolUse: Auto-validate JSON output after every file write**

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "command": "if echo \"$TOOL_INPUT\" | jq -r '.file_path' | grep -q '/output/'; then python3 validate_schema.py \"$(echo \"$TOOL_INPUT\" | jq -r '.file_path')\"; fi; exit 0"
      }
    ]
  }
}
```

Every time an agent writes to your `/output/` directory, this hook validates the JSON against your schema. If validation fails, Claude sees the error and self-corrects — without a human checking the output.

**2. PostToolUse: Auto-format JSON for consistency**

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write",
        "command": "filepath=$(echo \"$TOOL_INPUT\" | jq -r '.file_path'); if [[ \"$filepath\" == *.json ]]; then python3 -m json.tool \"$filepath\" > /tmp/formatted.json && mv /tmp/formatted.json \"$filepath\"; fi; exit 0"
      }
    ]
  }
}
```

Guarantees consistent JSON formatting across all 4 domain cluster outputs — no variation between what the billing agent and the network agent produce.

**3. PreToolUse: Block writes outside the output directory**

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Write|Edit",
        "command": "filepath=$(echo \"$TOOL_INPUT\" | jq -r '.file_path'); if [[ \"$filepath\" != /output/* ]] && [[ \"$filepath\" != *.md ]]; then echo 'BLOCK: Write only to /output/ directory'; exit 1; fi"
      }
    ]
  }
}
```

Prevents teammate agents from accidentally modifying source files in the ISP codebase. This is the file-ownership boundary from Digest #27, enforced deterministically instead of by instruction.

**Why hooks beat prompting for quality control:**

| Approach | Reliability | Cost | Speed |
|----------|------------|------|-------|
| Prompt: "Always validate JSON output" | ~90% (LLM may forget) | Extra tokens per reminder | Slow (model reasoning) |
| Hook: PostToolUse JSON validator | 100% (runs every time) | Zero tokens | Fast (shell command) |

**The key insight from DataCamp's tutorial:** Hooks have a 200ms budget per execution. If your validation script takes longer, spawn it as a background process and return immediately. For JSON schema validation against your ISP output schemas, 200ms is plenty.

**May 2026 update:** PostToolUse hooks can now *replace* tool output for all tools. This means a hook can intercept a tool's raw output, transform it, and return the transformed version to Claude. For your pipeline: a hook could strip verbose debugging output from a tool call and return only the structured data, keeping teammate agents' context windows lean.

### Key Takeaway

Add one PostToolUse hook to your `.claude/settings.json` today: the JSON schema validator for `/output/` writes. It's one JSON block in your settings file, and it guarantees that every file your Agent Teams pipeline writes to the output directory conforms to your schema — no token cost, no LLM uncertainty, 100% execution rate. Start with validation; add formatting and write-blocking hooks after you've verified the first one works.

## Resource 3: May 2026 Claude Code Updates — Session Recap, Output Replacement, and Auto-Retry

**Source:** [What's New — Claude Code Official Docs](https://code.claude.com/docs/en/whats-new)
**Also:** [Claude Code Updates May 2026 — Releasebot](https://releasebot.io/updates/anthropic/claude-code)
**Also:** [Claude Code Changelog: All Release Notes (2026) — Claudefast](https://claudefa.st/blog/guide/changelog)
**Also:** [Claude Code News May 2026 (Startup Edition) — Mean CEO](https://blog.mean.ceo/claude-code-news-may-2026/)
**Time:** ~4 min read (Releasebot summary + skim official docs)
**Category:** Operations — Platform Updates That Affect Your Daily Workflow

### Why This Is Relevant

You've been heads-down on Agent SDK architecture and presentation preparation. Meanwhile, Claude Code shipped several features in late April / early May that directly affect your ISP pipeline workflow. Three updates matter most.

**1. Session Recap — Know What Happened While You Were Away**

When you return to a Claude Code terminal that was running in the background, session recap automatically summarizes what happened while you were away. For your Agent Teams workflow, this is significant: you kick off a pipeline run, switch to another task (client work, email, presentation prep), and when you return, recap tells you exactly where things stand without scrolling through hundreds of lines of output.

- Configurable in `/config`
- Manually invoke anytime with `/recap`
- Can be forced on via the `CLAUDE_CODE_ENABLE_AWAY_SUMMARY` environment variable

**Why this matters for your ISP pipeline specifically:** A full Agent Teams run can take 30+ minutes. Today, when you return, you scroll through output trying to find where each cluster analysis finished and whether there were errors. With recap, you get a structured summary: "Billing cluster: completed, 12 services analyzed. Network cluster: completed with 1 retry on service X. Customer cluster: in progress, 14/17 services done."

**2. PostToolUse Output Replacement — Hooks Can Transform What Claude Sees**

PostToolUse hooks can now replace tool output for *all* tools, not just a subset. This is a significant expansion that arrived in the latest releases. Previously, a PostToolUse hook could only observe and react to tool output. Now it can intercept and replace it.

**The application for your pipeline:** When a teammate agent reads a large configuration file (say, a 2000-line Kubernetes manifest), the raw file contents flood the agent's context window. A PostToolUse hook on the Read tool can intercept that output, extract only the relevant sections (service ports, environment variables, dependency declarations), and return the filtered version to Claude. The agent gets exactly the data it needs — and its context window stays lean for the rest of the analysis.

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Read",
        "command": "python3 filter_large_files.py",
        "output": "replace"
      }
    ]
  }
}
```

This directly addresses the context management challenge from Digest #29 — instead of relying on `/compact` checkpoints to recover from context bloat, you prevent the bloat from happening in the first place.

**3. MCP Server Auto-Retry — Fewer Startup Failures**

MCP servers that hit a transient error during startup now auto-retry up to 3 times instead of staying disconnected. If your pipeline relies on MCP servers (file system tools, the Transcript Library connector, custom tools), this eliminates a class of silent failures where an agent starts without its tools because a network blip during MCP initialization went unrecovered.

**Additional updates worth noting:**

- **`/model` picker shows gateway models:** If you're using an Anthropic-compatible gateway (for cost tracking or routing), the model picker now lists available models from your gateway's `/v1/models` endpoint
- **`claude project purge [path]`:** Deletes all Claude Code state for a project — useful for clean pipeline reruns without accumulated session artifacts
- **Custom themes via `/theme`:** Cosmetic, but if you're demoing Claude Code in your GenAI in SDLC presentation, a clean custom theme signals polish

### Key Takeaway

Enable session recap in `/config` before your next Agent Teams run. Then, after the run completes in the background, use `/recap` to get a structured summary instead of scrolling through output. It's a small workflow change with an outsized quality-of-life improvement — especially as your pipeline runs get longer and more autonomous. The PostToolUse output replacement feature is the higher-impact change, but requires writing a filter script; session recap is free and immediate.

## Quick Win: Add a JSON Schema Validation Hook to Your Pipeline (5 min)

**Time: 5 minutes**

Open your project's `.claude/settings.json` (or create it) and add this PostToolUse hook:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "command": "filepath=$(echo \"$TOOL_INPUT\" | jq -r '.file_path' 2>/dev/null); if [[ \"$filepath\" == *.json ]] && [[ \"$filepath\" == */output/* ]]; then python3 -c \"import json, sys; json.load(open(sys.argv[1]))\" \"$filepath\" 2>&1 || echo 'WARNING: Invalid JSON written to output'; fi; exit 0"
      }
    ]
  }
}
```

**What this does:** Every time any agent (lead or teammate) writes a JSON file to your `/output/` directory, this hook validates that the file contains well-formed JSON. If it doesn't, Claude sees the warning and self-corrects. The `exit 0` ensures the hook never blocks the pipeline — it warns, it doesn't stop.

**Why now:** This is the simplest possible quality gate — valid JSON, nothing more. It catches the most common output failure (malformed JSON from a teammate agent that got cut off mid-write or mixed prose into a JSON file) with zero token cost and zero configuration complexity. Once this hook is working, you can extend it: add schema validation (check that the JSON matches your API contract schema), add formatting (pretty-print for consistency), add write-blocking (prevent writes outside `/output/`). But start with the basics — one hook, one validation, today.

**To verify it works:** Run a quick Claude Code session, ask it to write a JSON file to your output directory, and check that the hook fires (you'll see it in the session log). Then intentionally ask Claude to write invalid JSON and verify the warning appears.
