## Resource 1: Claude Code Routines — Your ISP Pipeline, Running in the Cloud

**Source:** [Introducing Routines in Claude Code — Anthropic Blog](https://claude.com/blog/introducing-routines-in-claude-code)
**Also:** [Automate work with routines — Claude Code Official Docs](https://code.claude.com/docs/en/routines)
**Also:** [Claude Code Routines Tutorial: Schedule, API, and GitHub Triggers Explained — Builder.io](https://www.builder.io/blog/claude-code-routines)
**Time:** ~6 min read (Anthropic blog + skim official docs)
**Category:** Workflow — From Local Headless to Cloud-Native Execution

### Why This Is Relevant

Your ISP pipeline progression has been: interactive → Agent Teams → headless on your laptop → observable and cost-controlled. Routines are the final step: a saved Claude Code configuration (prompt + repos + connectors) that runs on Anthropic's managed infrastructure. You configure it once, attach a trigger, and close your laptop.

**What a Routine is, concretely:**

A Routine packages three things: a **prompt** (your `/reverse-engineer` instructions), one or more **repositories** (the ISP codebase), and a set of **connectors** (Slack, GitHub, Linear, Google Drive). You save this configuration once at `claude.ai/code/routines` or via the CLI with `/schedule`. Then you attach a trigger.

**The three trigger types and how they map to your ISP pipeline:**

| Trigger | How It Works | Your ISP Application |
|---------|-------------|---------------------|
| **Scheduled** | Runs on a cadence: hourly, daily, weekly, or once at a specific time | Run a full architecture recovery every Monday morning before your standup — fresh analysis waiting in your output directory when you arrive |
| **API** | HTTP POST to a per-routine endpoint with a bearer token | Trigger an on-demand analysis from a Slack command, a webhook, or a script — "analyze this cluster now" without opening Claude Code |
| **GitHub** | Runs in response to repo events: PRs, releases, issues | Auto-analyze any new microservice added to the ISP repo — when a PR introduces a new service, your pipeline runs automatically and adds it to the architecture map |

**The execution model matters for your pipeline:**

Routines run autonomously — no permission-mode picker, no approval prompts during the run. They execute shell commands, access skills (like your `/reverse-engineer`), and call connectors and MCP servers. This is headless mode without the laptop dependency.

**From Dispatch to Routines — the evolution:**

| Feature | Dispatch (Digest #30) | Routines (Today) |
|---------|----------------------|-------------------|
| Runs on | Your machine | Anthropic's cloud |
| Trigger | Manual or script | Schedule, API, or GitHub event |
| Laptop required | Yes (machine must be on) | No |
| Connectors | MCP servers only | Slack, Linear, GitHub, Google Drive + MCP |
| Setup | CLI configuration | Web UI at claude.ai/code/routines or `/schedule` |

**Availability:** Pro, Max, Team, and Enterprise plans with Claude Code on the web enabled. Research preview — expect rough edges, but functional.

### Key Takeaway

Go to `claude.ai/code/routines` and create your first Routine: package your `/reverse-engineer` prompt for one domain cluster (start with the smallest — e.g., the network cluster with 8 services) with a scheduled trigger for a one-time run. Verify the output matches what you get from a local headless run. Once validated, you can schedule recurring full-pipeline runs — your ISP architecture map stays current without you touching a terminal.

## Resource 2: Auto Mode — The Safety Classifier That Enables Unattended Execution

**Source:** [Claude Code Gets Auto Mode — No More Permission Prompts — Awesome Agents](https://awesomeagents.ai/news/claude-code-auto-mode-research-preview/)
**Also:** [Claude Code Auto Mode: Autonomous Permission Guide — Digital Applied](https://www.digitalapplied.com/blog/claude-code-auto-mode-autonomous-permission-decisions-guide)
**Also:** [Claude Code Auto Mode: Now on Max, Team, and Enterprise — Claudefast](https://claudefa.st/blog/guide/development/auto-mode)
**Time:** ~5 min read
**Category:** Operations — Removing the Permission Bottleneck

### Why This Is Relevant

Every autonomy feature you've adopted — headless mode, Dispatch, now Routines — hits the same wall: permission prompts. When your Agent Teams pipeline runs unattended and a teammate needs to write a file, execute a shell command, or access an MCP server, a permission prompt stalls the entire pipeline until a human responds. Auto Mode replaces those prompts with an AI safety classifier.

**How the safety classifier works:**

Instead of prompting you, Auto Mode routes each proposed action through a built-in classifier that evaluates three things: the action against the active permission policy, the current working directory (is this file in scope?), and the `.claudeignore` file (is this path excluded?). Safe actions proceed automatically. Dangerous actions — deleting files, running destructive commands, accessing paths outside scope — are blocked without execution.

**The practical impact on your ISP pipeline:**

```
Before Auto Mode (headless):
  Agent tries to write /output/billing/services.json
  → Permission prompt → Pipeline stalls → You approve manually
  → Multiply by 47 services × 5 agents = dozens of interruptions

After Auto Mode:
  Agent tries to write /output/billing/services.json
  → Classifier: write to /output/ (in scope, non-destructive) → Auto-approved
  Agent tries to rm -rf /src/
  → Classifier: destructive operation outside output directory → Blocked
```

**Security considerations you need to know:**

Anthropic is explicit that prompt injection protection is incomplete. The recommendation: run Auto Mode in isolated environments — not on a machine with production credentials or live API access. For your ISP pipeline, this means:

- **Local development:** Auto Mode is fine — your ISP analysis reads code and writes output files, both low-risk
- **Routines (cloud):** Auto Mode is built into Routines' execution model (no permission prompts by design), and the cloud environment provides natural isolation
- **Production systems with credentials:** Don't enable Auto Mode in environments with database access, API keys to production services, or deployment permissions

**The cost nuance:** Every action requires additional classifier reasoning, so the bill is higher than standard mode. For Agent Teams pipelines that are already token-intensive, monitor the incremental cost via `/usage` (the baselining workflow from Digest #32).

**Rollout timeline for context:**
- March 24: Research preview launched
- April 16: GA on Max, Team, and Enterprise — beta flag dropped
- Today: Available to you with no gatekeepers

### Key Takeaway

Enable Auto Mode for your next local Agent Teams run to experience the difference: `Settings > Auto Mode` or use the `/auto` command. Watch the pipeline run without permission interruptions. Then check `/usage` to measure the classifier's token overhead. The productivity gain from zero-interruption execution needs to justify the incremental cost — for a 5-agent pipeline with dozens of file operations, it almost certainly does.

## Resource 3: "Dive into Claude Code" — The Academic Architecture Analysis

**Source:** [Dive into Claude Code: The Design Space of Today's and Future AI Agent Systems — arXiv](https://arxiv.org/abs/2604.14228)
**Also:** [In-Depth Research Analysis of Agent Harness Architecture — Mervin Praison](https://mer.vin/2026/04/dive-into-claude-code-in-depth-research-analysis-of-agent-harness-architecture/)
**Also:** [VILA-Lab/Dive-into-Claude-Code — GitHub](https://github.com/VILA-Lab/Dive-into-Claude-Code)
**Time:** ~4 min read (Mervin Praison's summary — skip the full 50-page paper)
**Category:** Presentation — Academic Credibility for Your GenAI in SDLC Talk

### Why This Is Relevant

Researchers at VILA Lab (Mohamed bin Zayed University of AI) and University College London reverse-engineered Claude Code's TypeScript source code (v2.1.88) and published a peer-reviewed analysis of its architecture. For your GenAI in SDLC presentation, this provides the academic credibility that complements your practitioner experience and Anthropic's C compiler case study.

**The paper's central thesis — and why it matters for your presentation:**

> *"As foundation models converge in baseline reasoning capabilities, the critical differentiator for autonomous system reliability becomes the deterministic engineering harness surrounding the model."*

Translation for your stakeholder audience: the AI model matters, but what makes Agent Teams reliable in production is the *engineering around the model* — the permission system, context management, tool orchestration, and observability. This is exactly the story your ISP pipeline tells: you didn't just prompt an AI; you built a harness (CLAUDE.md, JSON schemas, `/compact` checkpoints, file ownership boundaries, observability hooks) that makes the AI reliable.

**The five architectural layers the paper identifies:**

1. **Core loop:** A simple while-loop — call the model, run tools, repeat. The simplicity is the point.
2. **Permission system:** Seven modes plus an ML-based classifier (Auto Mode). Your pipeline uses this for safe unattended execution.
3. **Compaction pipeline:** Five-layer context management. Your `/compact` checkpoint workflow leverages this directly.
4. **Extensibility mechanisms:** MCP servers, plugins, skills, hooks — the four ways to extend Claude Code without modifying its core. Your `/reverse-engineer` skill and Transcript Library MCP are examples.
5. **Subagent orchestration:** The delegation mechanism that powers Agent Teams. Your 5-agent pipeline is a production instance of this architecture.

**The presentation slide this enables:**

```

┌─────────────────────────────────────┐
│         Core Agent Loop             │ ← Simple: call model, run tools, repeat
├─────────────────────────────────────┤
│    Permission & Safety Layer        │ ← Auto Mode classifier
├─────────────────────────────────────┤
│    Context Management (Compaction)  │ ← /compact checkpoints
├─────────────────────────────────────┤
│    Extensibility (MCP, Skills,      │ ← /reverse-engineer, MCP servers
│    Hooks, Plugins)                  │
├─────────────────────────────────────┤
│    Multi-Agent Orchestration        │ ← Agent Teams (your ISP pipeline)
└─────────────────────────────────────┘

"The model provides intelligence. The harness provides reliability."
  — Adapted from VILA Lab, arXiv:2604.14228
```

**The "build your own agent" guide:** The GitHub repo includes a practical guide (`docs/build-your-own-agent.md`) that walks through building a custom agent using the architectural patterns identified in the paper. For after the presentation — if stakeholders ask "could we build our own agent system?", you can point to this as a starting blueprint.

### Key Takeaway

Add the VILA Lab architecture diagram to your GenAI in SDLC presentation as the "how it works under the hood" slide. The paper's thesis — that the engineering harness, not the model, is the differentiator — directly supports your ISP pipeline story. Cite it as: *VILA Lab et al., "Dive into Claude Code," arXiv:2604.14228, April 2026.* Academic credibility from an independent research group analyzing the same tool you're using in production.

## Quick Win: Create Your First Routine with `/schedule` (5 min)

**Time: 5 minutes**

Open Claude Code and run:

```
/schedule
```

Or navigate to `claude.ai/code/routines` in your browser.

Create a minimal Routine:
1. **Name:** `ISP Network Cluster Analysis`
2. **Prompt:** `Analyze the network cluster microservices. Output findings as structured JSON to /output/network/. Focus on API contracts, dependencies, and coupling patterns.`
3. **Repository:** Your ISP codebase repo
4. **Trigger:** One-time scheduled run (set it for 30 minutes from now)
5. **No connectors needed** for the first test

Wait for it to run. Check the output.

**Why now:** You've spent five digests building toward autonomous execution — headless mode, production hardening, observability, cost control. Routines are where it all comes together. But the first run should be small and verifiable: one cluster, one-time trigger, output you can compare against your local pipeline results. If the cloud output matches your local output, you've validated that your entire ISP pipeline can run without your laptop. That's the milestone.

**What to look for:** Does the Routine produce the same JSON structure your local Agent Teams run produces? Are the API contracts and dependencies identified correctly? Is the cost (check the Routine's usage metrics) in line with your `/usage` baseline from Digest #32? If yes to all three, you're ready to schedule recurring runs.
