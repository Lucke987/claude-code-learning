## Resource 1: Designing CLAUDE.md Correctly — The 2026 Architecture That Makes Claude Code Work

**Source:** [Designing CLAUDE.md correctly: The 2026 architecture that finally makes Claude Code work — ObviousWorks](https://www.obviousworks.ch/en/designing-claude-md-right-the-2026-architecture-that-finally-makes-claude-code-work/)
**Also:** [Best Practices for Claude Code — Official Docs](https://code.claude.com/docs/en/best-practices)
**Time:** ~5 min read
**Category:** Architecture — CLAUDE.md Design for ISP

### Why This Is Relevant

Yesterday's Quick Win told you to feed `/reverse-engineer` output into CLAUDE.md. Today's resource tells you *how to do it right* so the file doesn't become bloated and ignored.

**The core problem:** CLAUDE.md instructions are followed about 70% of the time. A bloated CLAUDE.md drops that rate further because Claude loses signal in the noise. For your ISP codebase with 47 microservices, dumping all architecture findings into a single flat file would be counterproductive.

**The solution — the WHAT/WHY/HOW framework with @imports:**

1. **WHAT** — Tech stack, project structure, key abstractions. For ISP: "This is a Java/Python microservices system with 47 services organized into 5 domain clusters."
2. **WHY** — Why certain patterns exist. "We use event sourcing in the billing domain because X" prevents Claude from suggesting refactors that break the architecture.
3. **HOW** — Commands to build, test, analyze. Your `/reverse-engineer` invocation and verification hooks go here.

**The modular structure that scales:**

```
CLAUDE.md                          # Root: WHAT/WHY/HOW overview (~50 lines)
  @docs/architecture-overview.md   # Service map, domain boundaries
  @docs/api-flows.md              # Critical end-to-end flows
  @docs/coupling-hotspots.md      # Known coupling risks
  @.claude/git-conventions.md     # Team conventions
```

Each `@import` only loads when Claude works in the relevant directory or context. Your architecture findings from `/reverse-engineer` go into the `@docs/` files — not the root CLAUDE.md. The root stays concise (<200 lines), and the detailed knowledge loads on demand.

**The 4-layer test for critical rules:** CLAUDE.md gets ~70% compliance. For rules that *must* be followed 100% of the time (like "never push to main" or "always run the verification hook after analysis"), use hooks instead. Your Stop verification hook is already doing this correctly — the article validates your approach.

### Key Takeaway

**Structure your ISP repo's CLAUDE.md as a thin root file with @imports for architecture knowledge.** The `/reverse-engineer` output should flow into modular `@docs/` files that load on demand, not a monolithic root file. This is how you scale Nick Tune's "living documentation" concept from yesterday to a 100K-line codebase without drowning Claude in context.

## Resource 2: Agent Teams for Parallel Architecture Analysis — Analyze 47 Microservices in Hours, Not Weeks

**Source:** [Orchestrate teams of Claude Code sessions — Official Docs](https://code.claude.com/docs/en/agent-teams)
**Also:** [Claude Code Agent Teams: How to Run Multiple AI Agents in Parallel — MindStudio](https://www.mindstudio.com/blog/claude-code-agent-teams-parallel-workflows)
**Also:** [Collaborating with Agent Teams in Claude Code — Heeki Park, Medium](https://heeki.medium.com/collaborating-with-agents-teams-in-claude-code-f64a465f3c11)
**Time:** ~5 min (skim docs + one article)
**Category:** Execution Speed — Parallel Analysis at Scale

### Why This Is Relevant

You've used subagents for focused, delegated tasks within your `/reverse-engineer` skill. But subagents report back to the parent — they don't talk to each other. For analyzing an entire ISP codebase, you need **Agent Teams**: multiple Claude Code instances that coordinate, share findings, and challenge each other's conclusions in real time.

**The ISP use case:**

Imagine analyzing the 47 ISP microservices. With your current sequential approach, Claude analyzes one service cluster at a time. With Agent Teams:

- **Agent 1 (Team Lead):** Coordinates the analysis, maintains the master architecture map, synthesizes cross-cluster findings
- **Agent 2:** Analyzes the billing domain cluster (services 1-12)
- **Agent 3:** Analyzes the provisioning domain cluster (services 13-24)
- **Agent 4:** Analyzes the customer management cluster (services 25-36)
- **Agent 5:** Analyzes the network operations cluster (services 37-47)

Each agent works independently in its own context window, but they communicate findings: "I found that billing-service calls provisioning-service via a synchronous REST endpoint — Agent 3, can you verify the receiving side?" This cross-agent verification is something subagents can't do.

**Practical constraints:**

- **Team size:** 3-5 agents is the sweet spot. Beyond 5, coordination overhead eats into the parallelism benefit.
- **Tasks per agent:** Aim for 5-6 tasks per teammate to keep them productive without context switching.
- **Cost:** Token costs scale linearly — each agent has its own context window. A 5-agent team analyzing for 1 hour costs ~5x a single session.
- **Setup:** Agent Teams are experimental. Enable with `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` in settings.json or environment.
- **v2.1.114 fix:** The April 18 release fixed a crash in the permission dialog when an Agent Teams teammate requested tool permission — make sure you're on the latest version.

**Agent Teams vs. subagents decision tree:**

- **Subagents:** Quick, focused tasks that report back. Your current `/reverse-engineer` delegation model.
- **Agent Teams:** Complex investigations where agents need to share findings, challenge hypotheses, and coordinate independently. Architecture recovery across multiple interrelated service clusters.

**For the ISP presentation:**

This is your "speed of execution" slide. *"Using Agent Teams, we analyze an entire enterprise microservices codebase in parallel — 5 agents, each analyzing a domain cluster, sharing findings in real time. What takes a team of consultants weeks takes the AI team hours."*

### Key Takeaway

**Agent Teams turn your sequential reverse engineering pipeline into a parallel analysis engine.** Enable Agent Teams, set up a 5-agent team with domain-based partitioning, and run a proof-of-concept on 2-3 ISP service clusters this week. The cross-agent verification pattern — where agents fact-check each other's findings — produces more reliable architecture maps than sequential analysis.

## Resource 3: Claude Code v2.1.113-114 — Native Binary, Security Controls, and What They Mean for ISP Deployment

**Source:** [Claude Code Releases — GitHub](https://github.com/anthropics/claude-code/releases)
**Also:** [Claude Code Changelog — Official Docs](https://code.claude.com/docs/en/changelog)
**Also:** [Claude Code Changelog: All Release Notes 2026 — ClaudeFast](https://claudefa.st/blog/guide/changelog)
**Time:** ~5 min (scan release notes + test the new settings)
**Category:** Platform Updates — Deployment & Security

### Why This Is Relevant

Two releases shipped this week that directly affect your ISP work:

**v2.1.113 — Native binary CLI (April 17):**

The CLI now spawns a native Claude Code binary instead of bundled JavaScript. What does this mean for you?

- **Faster startup:** The native binary loads faster than the Node.js runtime, which matters when you're spawning multiple subagents or Agent Teams instances. If you're running 5 parallel agents for ISP analysis, each one starts up faster.
- **Lower memory footprint:** Native binaries use less RAM than Node.js processes. With 5 Agent Teams instances, this adds up.
- **No action needed:** The update is automatic. Just ensure you're on v2.1.113+ (`claude --version`).

**v2.1.113 — `sandbox.network.deniedDomains` setting:**

This new setting lets you block specific domains from the sandbox network. For ISP deployment, this is a security control you should highlight in your presentation:

- Block agents from reaching production endpoints during analysis
- Restrict network access to only the repos and docs the agent needs
- Demonstrate to ISP security teams that the AI analysis is sandboxed

**Configuration:**

```json
// .claude/settings.json
{
  "sandbox": {
    "network": {
      "deniedDomains": [
        "production-api.isp-client.com",
        "*.internal.isp-client.com"
      ]
    }
  }
}
```

**v2.1.114 — Agent Teams permission fix (April 18):**

Fixed a crash when an Agent Teams teammate requested tool permission. If you hit issues with Agent Teams in the past, this release resolves the most critical bug. Update before starting your parallel analysis proof-of-concept.

### Key Takeaway

**Update to v2.1.114 before experimenting with Agent Teams, and add `sandbox.network.deniedDomains` to your ISP security story.** The native binary improves multi-agent performance, and the network domain blocking gives ISP security teams confidence that AI analysis stays within approved boundaries. Both are concrete technical controls you can present in your GenAI in SDLC deck.

## Quick Win: Create a Modular CLAUDE.md with @imports for the ISP Repo (10 min)

Yesterday's Quick Win was "feed reverse engineering output into CLAUDE.md." Today, do it properly with the modular @imports pattern from the ObviousWorks article:

```bash
# In your ISP project directory

# 1. Create the docs directory for architecture knowledge
mkdir -p docs

# 2. Create the modular architecture files (populate from your last /reverse-engineer run)
cat > docs/architecture-overview.md << 'EOF'
# ISP Architecture Overview
<!-- Auto-updated by /reverse-engineer runs -->

## Domain Clusters
- Billing (services 1-12): [brief description]
- Provisioning (services 13-24): [brief description]
- Customer Management (services 25-36): [brief description]
- Network Operations (services 37-47): [brief description]

## Technology Stack
- Backend: Java (Spring Boot), Python (FastAPI)
- Messaging: [Kafka/RabbitMQ/etc.]
- Data: [PostgreSQL/MongoDB/etc.]
EOF

cat > docs/api-flows.md << 'EOF'
# Critical API Flows
<!-- Auto-updated by /reverse-engineer runs -->

## Flow 1: [Name]
- Entry point → Service A → Service B → Response
- Protocol: REST/gRPC/async
- Known issues: [coupling hotspots]
EOF

# 3. Create a concise root CLAUDE.md with @imports
cat > CLAUDE.md << 'EOF'
# ISP Codebase

## WHAT
Java/Python microservices system with ~47 services across 4 domain clusters.
See @docs/architecture-overview.md for the full service map.
See @docs/api-flows.md for critical end-to-end flows.

## WHY
Legacy system under modernization assessment. Architecture recovery is the primary task.
Event sourcing in billing domain — do not suggest refactoring to CRUD.
Service boundaries are intentional — do not suggest merging services.

## HOW
- Run `/reverse-engineer` for architecture analysis
- Verification hooks enforce analysis quality checks
- Output feeds back into @docs/ files to keep architecture knowledge current
EOF

echo "Done — CLAUDE.md + @docs/ structure created"
```

Then fill in the actual findings from your most recent `/reverse-engineer` run. Every future Claude Code session in the ISP repo will start with structured architectural context, and each new analysis run updates the modular docs without bloating the root file.

**Why this is today's Quick Win:** It takes 10 minutes, it directly implements yesterday's Nick Tune insight with the correct architecture from today's ObviousWorks article, and it creates the foundation for the Agent Teams parallel analysis you'll set up next. Each agent in your team will automatically load the relevant `@docs/` context for its assigned domain cluster.
