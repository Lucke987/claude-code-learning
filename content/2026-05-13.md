## Resource 1: Multi-Agent Observability Dashboard via Claude Code Hooks

**Source:** [disler/claude-code-hooks-multi-agent-observability — GitHub](https://github.com/disler/claude-code-hooks-multi-agent-observability)
**Also:** [agent-observability plugin — Nexus Labs](https://github.com/nexus-labs-automation/agent-observability)
**Also:** [Claude Code Hooks: Complete Guide to All 12 Lifecycle Events — ClaudeFast](https://claudefa.st/blog/tools/hooks/hooks-guide)
**Time:** ~6 min read (README + architecture overview)
**Category:** Observability — See Your Pipeline Run in Real Time

### Why This Is Relevant

Your pipeline has governance (deny → classify → validate), automation (routines), and production hardening (checkpoints, golden evals). What it doesn't have is **visibility**. When your 5 agents run against a legacy cluster, you can't see which agent is active, which tool calls are firing, where time is being spent, or where failures occur. For a London demo, this is the difference between "trust me, it works" and "watch it work."

This open-source project builds a real-time observability dashboard for Claude Code agents using the hooks system you're already using for governance. The data flow:

```
Claude Agents → Hook Scripts → HTTP POST → Bun Server → SQLite → WebSocket → Vue Dashboard
```

**All 12 hook events are captured:**

| Hook Event | What It Captures | Your Pipeline Application |
|------------|-----------------|--------------------------|
| `SessionStart` / `SessionEnd` | Agent lifecycle boundaries | Track when each of your 5 agents starts and finishes |
| `SubagentStart` / `SubagentStop` | Multi-agent coordination | Visualize your conductor delegating to domain specialists |
| `PreToolUse` / `PostToolUse` | Every tool call with inputs/outputs | See which files each agent reads, which commands it runs |
| `PostToolUseFailure` | Failed tool executions | Spot which agent is struggling with a service cluster |
| `PreCompact` | Context compaction events | Detect when an agent's context is overflowing — a sign it needs a smaller scope |
| `UserPromptSubmit` | Prompt capture | Trace the initial prompt through to final output |
| `Stop` | Session completion with transcript | Full chat transcript accessible from the dashboard |

**The dashboard shows:**

- **Event Timeline** — color-coded by session, with emoji badges per tool type. Each of your 5 agents gets a distinct color, so you can visually track parallel execution.
- **Live Pulse Chart** — canvas-based activity visualization showing real-time agent activity. During a demo, this is your "mission control" screen.
- **Multi-criteria Filtering** — filter by agent (application), session ID, or event type. Isolate your dependency mapper agent's activity from the noise of other agents.
- **Chat Transcript Viewer** — click into any completed session to see the full conversation. Debug exactly what an agent was "thinking" when it made a decision.

**Setup is non-destructive — it layers on top of your existing hooks:**

```bash
# Clone the observability system
git clone https://github.com/disler/claude-code-hooks-multi-agent-observability.git

# Copy the hook scripts into your pipeline repo's .claude/hooks/
# They POST events to localhost:4000 — your existing hooks are unaffected

# Start the server + dashboard
./scripts/start-system.sh
# Dashboard at http://localhost:5173
```

**The key insight:** You already use PostToolUse hooks for governance (output validation). This system uses the *same hook mechanism* for observability — they coexist. Your hooks validate output quality; these hooks stream events to a dashboard. No conflicts, no rewiring.

### Key Takeaway

Clone the observability dashboard and run it alongside your pipeline this week. During your Day 4 dry run (May 15), have the dashboard open on a second monitor. You'll see your 5 agents' activity in real time — which one is slow, which one fails, which one produces the most tool calls. For London, this dashboard *is* the demo: show the audience a live pipeline run with the observability dashboard visible. It transforms your presentation from slides about architecture to a live system with visible intelligence.

## Resource 2: Anthropic's Multi-Agent Research System — Architecture Validation from the Source

**Source:** [How we built our multi-agent research system — Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system)
**Also:** [Anthropic's Multi-Agent Blueprint: What Production Adds — FountainCity](https://fountaincity.tech/resources/blog/anthropic-multi-agent-blueprint-production/)
**Also:** [Multi-Agent Research System Deep Reflections — LLM Multi Agents](https://llmmultiagents.com/en/blogs/anthropic-multi-agent-system-reflection)
**Time:** ~5 min read (FountainCity analysis + LLM Multi Agents reflections)
**Category:** Architecture — Validate Your Design Against Anthropic's Own

### Why This Is Relevant

You've been building a multi-agent orchestrator-worker pattern for 9 weeks. Anthropic published how they built the *same pattern* for their Research feature — the one that powers deep research in Claude. This is direct architecture validation from the people who built the platform you're building on.

**Their architecture mirrors yours:**

| Anthropic's Research System | Your ISP Pipeline |
|----------------------------|-------------------|
| Lead agent plans research, delegates to subagents | Conductor agent analyzes cluster, delegates to domain specialists |
| Subagents search in parallel across data sources | Domain agents (API, billing, auth, infra) analyze in parallel |
| Lead synthesizes subagent results into a report | Synthesis agent combines outputs into structured documentation |
| Orchestrator-worker pattern with synchronous execution | Agent Teams with conductor coordination |

**Three architectural lessons that apply directly to your pipeline:**

**1. Coordination complexity grows faster than agent count**

Anthropic found that multi-agent systems have a "rapid growth in coordination complexity" — the lead agent spends an increasing percentage of its context budget on managing subagents rather than doing useful work. Their current approach: synchronous execution where the lead waits for each batch of subagents to complete before proceeding.

**What this means for you:** Your conductor agent manages 4 domain specialists + 1 synthesis agent. If you add more domain agents (e.g., a networking specialist, a security auditor), coordination overhead grows quadratically, not linearly. The implication: keep your agent count at 5-7 maximum, and let each agent handle broader scope rather than adding narrow specialists.

**2. The coordination layer matters more than individual agent quality**

Anthropic's 2026 Agentic Coding Trends Report identifies a shift: "multi-agent architectures become the standard pattern for complex tasks, making the coordination layer — rather than the individual agent — the primary focus of engineering attention." Their system achieved a 90.2% performance improvement over single-agent approaches — not by making individual agents smarter, but by improving how they coordinate.

**What this means for you:** Your next optimization isn't better prompts for your domain agents — it's better orchestration logic in your conductor. Specifically: how does the conductor decide what to delegate? How does it handle partial failures (one domain agent succeeds, another fails)? How does it merge conflicting information from different agents? These coordination questions have more leverage than any single-agent prompt improvement.

**3. Current limitation: subagents can't steer each other**

Anthropic acknowledges a key gap: "the lead agent can't steer subagents, subagents can't coordinate, and the entire system can be blocked while waiting for a single subagent to finish." This is a synchronous bottleneck they're actively working to solve.

**What this means for you:** If your dependency mapper agent discovers that a service has an unexpected API pattern, it can't tell the API contract agent to adjust its analysis mid-run. Each agent runs to completion, then the conductor synthesizes. For your London presentation, frame this as a known limitation with a roadmap: "Today our agents run in parallel but independently. The next evolution is inter-agent communication — where the dependency mapper can signal the API contract agent in real time."

**For your presentation:** This is your credibility slide. "Our pipeline uses the same orchestrator-worker pattern that Anthropic uses internally for their Research feature. Here's where our architecture aligns, and here's where we've made different choices based on our domain constraints." Anthropic validating the pattern removes the "did you just make this up?" objection.

### Key Takeaway

Add a "Architecture Validation" slide to your presentation showing the parallel between Anthropic's Research system and your pipeline. The 90.2% improvement stat and the coordination-over-individual-quality insight are your two strongest data points. Then, address the known limitation (no inter-agent steering) honestly — it shows architectural maturity to identify constraints rather than hiding them.

## Resource 3: The 5 Workflow Patterns — A Presentation Framework Your Audience Already Understands

**Source:** [Beyond One-Shot Prompts: 5 Claude Code Workflow Patterns Explained — MindStudio](https://www.mindstudio.ai/blog/claude-code-agentic-workflow-patterns)
**Also:** [Orchestrate teams of Claude Code sessions — Claude Code Docs](https://code.claude.com/docs/en/agent-teams)
**Also:** [Claude Code Workflow Patterns That Actually Ship — shuvo.dev](https://shuvo.dev/blogs/claude-code-workflow-patterns-that-actually-ship)
**Time:** ~4 min read (MindStudio overview + skim official docs)
**Category:** Presentation — The Taxonomy That Makes Your Maturity Arc Click

### Why This Is Relevant

Your presentation's maturity arc (one-shot → skills → multi-agent → event-driven) is strong but custom. MindStudio mapped Claude Code's official workflow patterns into a five-level taxonomy that the broader developer community already uses. Aligning your arc with this taxonomy means your BCG audience can Google the terms afterward and find consistent definitions — your presentation becomes the entry point to an ecosystem, not an isolated case study.

**The five patterns, mapped to your journey:**

| Pattern | How It Works | Your Pipeline Stage | Your Maturity Level |
|---------|-------------|--------------------|--------------------|
| **1. Sequential** | One Claude instance, all steps in order | Your early experiments — single prompts analyzing one service | Level 1: One-shot |
| **2. Operator** | A controlling Claude plans work and delegates subtasks | Your conductor agent planning the analysis and delegating | Level 2-3: Skills + Orchestration |
| **3. Split-and-Merge** | Multiple subagents run in parallel, results merged | Your 4 domain agents analyzing in parallel, synthesis agent merging | Level 3: Multi-agent |
| **4. Agent Teams** | Multiple sessions coordinate, one as team lead | Your full pipeline with conductor + specialists + inter-session context | Level 3-4: Orchestrated teams |
| **5. Headless** | No human in the loop — trigger, task, automated result | Your routines running nightly with golden file validation | Level 4: Event-driven autonomous |

**The presentation power move:** Replace your custom maturity arc labels with these five pattern names. Your audience hears "Sequential → Operator → Split-and-Merge → Agent Teams → Headless" and each term maps to official documentation they can reference. Your pipeline demonstrates levels 2-5, and you can show code for each transition.

**The key principle from MindStudio:** "Pick the simplest pattern that gets the job done." This is your consulting message — don't jump to Agent Teams when Sequential solves the problem. Your pipeline uses Agent Teams because the problem *requires* parallel domain analysis. The maturity arc isn't about complexity for its own sake; it's about matching pattern complexity to problem complexity.

**For each pattern, one slide:**

1. **Sequential** — "Where everyone starts. One prompt, one task. Good for: ad-hoc analysis, quick scripts, simple automation."
2. **Operator** — "The prompt becomes a plan. Claude delegates subtasks. Good for: multi-step workflows, code generation with tests."
3. **Split-and-Merge** — "Parallel execution, merged results. Good for: analyzing multiple data sources, cross-referencing information."
4. **Agent Teams** — "Coordinated sessions with a team lead. Good for: complex systems analysis, our ISP reverse-engineering pipeline."
5. **Headless** — "No human in the loop. Trigger-based, fully automated. Good for: nightly pipelines, CI/CD integration, monitoring responses."

### Key Takeaway

Restructure your presentation's maturity arc to use the five official workflow pattern names. This does three things: (1) it gives your audience searchable terms they can explore after the talk, (2) it positions your pipeline within a recognized framework rather than a custom taxonomy, and (3) it makes the "pick the simplest pattern" principle your consulting recommendation — sophistication should match problem complexity, not ego. Draft the five slides this week as part of your Day 3 prep (May 14).

## Quick Win: Install the Agent Observability Plugin and Audit Your Pipeline (3 min)

**Time: 3 minutes**

Before you build a full observability dashboard, assess what instrumentation your pipeline already has — and what's missing.

**Step 1:** Install the agent-observability plugin:

```bash
claude plugin install agent-observability@caleb-davis-plugins
```

**Step 2:** Open Claude Code in your ISP pipeline repo and run:

```
/audit
```

The plugin scans your codebase for observability coverage gaps and anti-patterns. It checks for: untraced LLM calls, tool executions without span tracking, missing error context, agent handoffs without parent-child relationships, and cost tracking gaps.

**Step 3:** Review the report. You'll get a file-by-file assessment with specific gaps. The most likely findings for your pipeline:

- **No distributed tracing** — your 5 agents run in parallel but there's no parent-child span linking the conductor's delegation to each domain agent's execution
- **No cost tracking per agent** — you can't tell which domain agent is the most expensive per run
- **No error context** — when a domain agent fails, you know *that* it failed but not *why* (what tool call, what input, what error)

**Step 4:** Run `/instrument` to get a prioritized implementation plan, starting from foundation (basic tracing) through evaluation (quality metrics). You don't need to implement it all — just knowing the gaps informs your London demo preparation and your presentation's "what's next" slide.

**Why now:** Your Day 4 dry run (May 15) is in 2 days. Running `/audit` today gives you 48 hours to address the most critical observability gaps before you test the full pipeline. And for your presentation, "we instrumented our pipeline with distributed tracing, per-agent cost tracking, and error context" is the slide that makes enterprise buyers comfortable. They've been burned by black-box AI systems — observability is the antidote.
