## Resource 1: The Deny Rules Bypass and Subagent Permissions Gap — Real Attack Vectors for Your Security Slides

**Source:** [Critical Claude Code vulnerability: Deny rules silently bypassed — Adversa AI](https://adversa.ai/blog/claude-code-security-bypass-deny-rules-disabled/)
**Also:** [Claude Code bypasses safety rule if given too many commands — The Register](https://www.theregister.com/2026/04/01/claude_code_rule_cap_raises/)

**Also:** [Claude Code Permissions Guide — Claude Directory](https://www.claudedirectory.org/blog/claude-code-permissions-guide)
**Time:** ~6 min read (Adversa AI vulnerability report + GitHub issue #25000)
**Category:** Governance Slides — Concrete Threat Models That Justify Your Architecture

### Why This Is Relevant

Your Day 6 task is building the "Security at Two Layers" and "Governance Architecture" slides. The strongest security slides don't describe what *could* go wrong — they reference what *actually* went wrong and show how your architecture addresses it. Two real-world Claude Code security findings from April 2026 give you exactly this.

**Vulnerability 1: The 50-Subcommand Deny Rules Bypass (CVE-level, patched v2.1.90)**

In April 2026, security researchers at Adversa AI discovered that Claude Code's legacy command parser stopped evaluating deny rules when a compound Bash command exceeded 50 subcommands (joined by `&&`, `||`, or `;`). Instead of rejecting the command, the system fell back to a generic user approval prompt — which in CI/CD environments could be auto-approved.

| What Happened | Why It Matters for Your Pipeline |
|---------------|----------------------------------|
| Deny rules silently bypassed above 50 subcommands | Your pipeline agents execute complex Bash sequences during service analysis |
| Fallback to generic prompt instead of rejection | In auto mode, generic prompts are auto-approved — no human gate |
| Patched in v2.1.90 (April 6, 2026) | Verify you're on v2.1.128+ (Week 19) — you are, but confirm during your slide prep |

**How your governance model addresses this:**

Your three-tier model (hard deny → auto mode classifier → PostToolUse hooks) has defense in depth that survives this class of vulnerability:

1. **`autoMode.hard_deny` (Tier 1)** — Unconditional blocks that can't be overridden by broader allow rules. Even if a deny rule parser fails, hard_deny rules are evaluated separately. This is your "belt" for the belt-and-suspenders metaphor.
2. **PostToolUse hooks (Tier 3)** — Your hooks inspect *outputs*, not inputs. Even if a dangerous command bypasses input-level deny rules, the PostToolUse hook catches the effects: unauthorized file writes, unexpected network calls, or forbidden patterns in output. This is your "suspenders."

**For your slide:** Show the attack path and how each tier blocks it:

```
Attack: Prompt injection crafts 51-subcommand Bash sequence containing `curl`
├── Tier 1: hard_deny blocks `curl` pattern unconditionally ✓
├── Tier 2: auto mode classifier evaluates each subcommand independently ✓
└── Tier 3: PostToolUse hook detects network output artifacts ✓
```

**Vulnerability 2: Subagent Permission Inheritance Gap (GitHub #25000)**

A separate finding reported that subagents don't inherit deny rules from `settings.local.json`. Users who carefully configured deny rules had a false sense of security — their subagents bypassed those rules entirely.

| What Happened | Why It Matters for Your Pipeline |
|---------------|----------------------------------|
| Subagents skip `settings.local.json` deny rules | Your 5 agents are subagents of the conductor |
| Users' carefully configured rules silently ignored | Without mitigation, your domain agents could bypass governance |

**How your governance model addresses this:**

Your PostToolUse hooks are configured at the *project level* (`.claude/settings.json`), not in `settings.local.json`. Project-level hooks apply to all agents in the project, including subagents. This is an architectural decision you may have made accidentally — but it's the right one, and it's worth highlighting in your slide.

**The slide narrative:** "We don't rely solely on deny rules — because deny rules have been bypassed. Our governance model has three independent tiers: unconditional hard_deny rules, a contextual auto mode classifier, and PostToolUse hooks that validate outputs regardless of how they were produced. If any single tier fails, the other two catch it. Here are two real CVE-level examples where deny rules were bypassed — and our pipeline's output validation would have caught both."

### Key Takeaway

Build your "Security at Two Layers" slide around these two real vulnerabilities. The deny rules bypass (patched v2.1.90) and the subagent permissions gap (GitHub #25000) are concrete proof that single-tier security fails. Your three-tier governance model — hard_deny + auto mode + PostToolUse hooks — is defense in depth that survives parser bugs and inheritance gaps. Reference the specific vulnerability IDs in your slide notes for credibility. This also directly strengthens your Angela Jiang question: "If deny rules have already been bypassed by parser bugs, could dreaming learn to craft similar evasion sequences?"

## Resource 2: The Hooks Governance RFC — Why "Necessary but Insufficient" Is Your Strongest Slide Argument

**Source:** [RFC: Deterministic tool gate — hooks are necessary but insufficient for governance enforcement — GitHub Issue #45427](https://github.com/anthropics/claude-code/issues/45427)
**Also:** [AI agent hooks: the interface for governing AI agents — Speakeasy](https://www.speakeasy.com/resources/ai-agent-hooks)
**Also:** [Claude Code Hooks: The Deterministic Control Layer for AI Agents — Dotzlaw](https://www.dotzlaw.com/insights/claude-hooks/)
**Also:** [Claude Code Hooks: PreToolUse, PostToolUse & Stop Production Patterns — Pixelmojo](https://www.pixelmojo.io/blogs/claude-code-hooks-production-quality-ci-cd-patterns)
**Time:** ~5 min read (GitHub RFC discussion + Speakeasy governance framing)
**Category:** Governance Architecture — The Architectural Argument for Your Three-Tier Model

### Why This Is Relevant

A community RFC on the Claude Code repo (issue #45427) argues that PreToolUse hooks — the only hook that can block actions — are "necessary but insufficient" for governance enforcement. The RFC identifies three failure modes:

1. **Silent failure** — hooks can fail without surfacing errors, letting blocked actions through
2. **Subagent bypass** — subagents may not trigger parent-level hooks
3. **Model self-modification** — the model can potentially rewrite hook configurations

This RFC validates your entire governance architecture. You built three tiers *because* no single tier is sufficient. The RFC proves that the community has independently reached the same conclusion.

**How the RFC maps to your tiers:**

| RFC Failure Mode | Your Mitigation |
|-----------------|-----------------|
| Hooks fail silently | Tier 1 (`hard_deny`) operates independently of hooks — it's evaluated in the permission system, not the hook system |
| Subagents bypass hooks | Your hooks are in `.claude/settings.json` (project-level), and your `hard_deny` rules apply to all agents in the project |
| Model rewrites hooks | Your `.claude/settings.json` is in version control with a pre-commit hook that rejects modifications — the model can't commit changes to governance rules |

**The Speakeasy article frames hooks as "the interface for governing AI agents":**

Their key insight: hooks are the boundary between probabilistic (model-driven) and deterministic (rule-driven) behavior. Everything inside a hook is deterministic — it runs your code, not the model's reasoning. Your PostToolUse hooks with `updatedToolOutput` are a concrete example: the hook runs a Python validation script against agent output, and if validation fails, the hook rewrites the output with an error message. The model never sees the invalid output — the hook replaces it before it enters the context.

**The Dotzlaw framing — "The Deterministic Control Layer":**

This article positions hooks as the layer that makes AI agents enterprise-safe. Their argument: "Prompts are suggestions. Permissions are defaults. Hooks are guarantees." This is a one-sentence version of your governance slide.

**For your "Governance Architecture" slide, use this three-column layout:**

| Layer | Mechanism | Guarantee |
|-------|-----------|-----------|
| **Prompts** | CLAUDE.md rules, system prompts | Advisory (~70% followed) — the model interprets and may deviate |
| **Permissions** | deny/ask/allow rules, `hard_deny` | Structural — enforced by the runtime, not the model |
| **Hooks** | PreToolUse gates, PostToolUse validators | Deterministic — your code runs, not the model's reasoning |

**The punchline for your BCG audience:** "We govern our AI agents the same way we govern production software: with automated tests (PostToolUse hooks), access controls (deny rules + hard_deny), and code review (pre-commit hooks on governance config). The AI is powerful — but it operates inside a deterministic boundary that we control."

**Enterprise governance features to mention:**

Anthropic ships managed-policy options for enterprise: `allowManagedHooksOnly`, `allowManagedMcpServersOnly`, and `allowManagedPermissionRulesOnly`. These prevent user and project settings from expanding trust in unauthorized ways. For your BCG audience, mention that BCG is a named Claude Security deployment partner — these enterprise controls are being co-developed with firms like yours.

### Key Takeaway

Use the RFC's "necessary but insufficient" framing as your slide's thesis. Each governance mechanism alone is insufficient: prompts can be ignored, deny rules can be bypassed, hooks can fail silently. Your three-tier model makes each tier a fallback for the others. The Dotzlaw one-liner — "Prompts are suggestions. Permissions are defaults. Hooks are guarantees." — is your slide's headline. The enterprise managed-policy features (`allowManagedHooksOnly`) are your "what's available at scale" proof point.

## Resource 3: Last-Minute Pipeline Updates — `claude agents` Flags and Fast Mode on Opus 4.7

**Source:** [Claude Code Updates May 2026 — Releasebot](https://releasebot.io/updates/anthropic/claude-code)
**Also:** [What's new — Claude Code Docs](https://code.claude.com/docs/en/whats-new)

**Category:** Pipeline Polish — Two Features to Activate Before London

### Why This Is Relevant

Two features shipped in the last 10 days that could improve your London demo and pipeline performance. Neither requires architectural changes — they're configuration flags you can activate today.

**Feature 1: `claude agents` CLI flags for dispatching configured background sessions**

New flags for `claude agents`: `--add-dir`, `--settings`, `--mcp-config`, `--plugin-dir`, `--permission-mode`, `--model`, `--effort`, and `--dangerously-skip-permissions`.

**What this means for your pipeline:** You can now dispatch background agent sessions with explicit configuration — settings path, MCP config, model selection, and effort level — all from the CLI. For your routine-based automation (nightly pipeline runs), this means each dispatched agent can carry its own settings bundle:

```bash
# Dispatch a domain agent with explicit governance config
claude agents dispatch \
  --settings .claude/settings-governance.json \
  --mcp-config .claude/mcp-isp.json \
  --model claude-opus-4-6 \
  --effort xhigh \
  "Analyze API contracts for payments cluster"
```

This replaces the current approach where agents inherit the parent's settings implicitly (with the inheritance gaps identified in Resource 1). By explicitly passing `--settings`, you guarantee each agent gets the governance config you intend.

**For your London demo:** If your demo involves dispatching agents from the CLI, these flags make the governance explicit in the command — the audience can *see* that each agent is launched with a specific settings file. More visible governance = more confidence.

**Feature 2: Fast mode on Opus 4.7**

Fast mode now uses Opus 4.7 by default (previously Opus 4.6), with significantly faster output token generation. If your pipeline's bottleneck is output generation speed (rather than reasoning), fast mode on Opus 4.7 could reduce your per-agent runtime.

**Tradeoffs for your pipeline:**
- **Speed gain:** Faster output generation means your 5 agents complete sooner — important for a live demo where the audience is watching
- **Cost increase:** Fast mode carries premium pricing. For nightly routine runs, this may not be cost-effective. For a live demo, the speed is worth it
- **Quality consideration:** Opus 4.7 fast mode optimizes for speed, not depth. Your domain analysis agents need deep reasoning (analyzing legacy service clusters), so fast mode may produce shallower analysis. Test with one agent before enabling pipeline-wide

**Recommendation for London:** Enable fast mode for your synthesis agent only. The synthesis agent merges outputs from the 4 domain agents — it needs speed (the audience is waiting for the final output) more than it needs deep reasoning (the domain agents already did the analysis). Keep domain agents on standard Opus for analysis quality.

```json
// In your synthesis agent's settings
{
  "model": "claude-opus-4-7",
  "speed": "fast"
}
```

**Also notable:** Rate limits on Claude Code were doubled across Pro, Max, Team, and Enterprise plans, and the peak-hours reduction on Pro/Max was removed. If your pipeline has ever hit rate limits during multi-agent runs, this gives you 2x headroom.

### Key Takeaway

Use `claude agents` explicit flags (`--settings`, `--effort`) to make governance visible in your demo dispatch commands. Consider fast mode (Opus 4.7) for the synthesis agent only — speed for the audience-facing output, standard mode for deep domain analysis. The doubled rate limits give your 5-agent pipeline room to breathe during the live London demo.
