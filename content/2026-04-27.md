## Resource 1: 30 Tips for Claude Code Agent Teams (John Kim)

**Source:** [30 Tips for Claude Code Agent Teams — John Kim, Push to Prod](https://getpushtoprod.substack.com/p/30-tips-for-claude-code-agent-teams)
**Time:** ~6 min read
**Category:** Operations — Agent Teams Tuning for Production Pipelines

### Why This Is Relevant

You've built the Agent Teams architecture. John Kim's article is the operational playbook you need to tune it. Kim runs Agent Teams in production and distills 30 specific tips — not architecture patterns (you have those), but the *operational details* that determine whether your 5-agent ISP pipeline runs cleanly or produces coordination overhead.

**The tips most directly applicable to your ISP pipeline:**

**Task sizing: 5-6 tasks per teammate.** Fewer tasks underutilize parallelism; more tasks increase coordination overhead. For your ISP pipeline with 47 services across 4 domain clusters, this means ~10-12 services per teammate (at 2 tasks per service: discovery + analysis), which aligns with your current 5-agent partitioning. If you have uneven cluster sizes, Kim's advice is to rebalance by complexity, not count.

**File ownership boundaries prevent merge conflicts.** When multiple teammates analyze services that share configuration files, dependency manifests, or shared libraries, you get silent overwrites. Kim's fix: declare file ownership in the team lead's instructions. For ISP: each teammate owns its domain cluster's output directory exclusively. Shared files (the master architecture map, cross-cluster dependency graph) are written only by the lead agent after synthesis.

**Model mixing per teammate.** You can assign different models per teammate role. Kim suggests: the lead orchestrator runs on Opus for synthesis quality, analysis teammates run on Opus xhigh for depth, and any lightweight validation agents run on Sonnet for speed and cost. For your pipeline: if you add a validation agent that checks JSON schema conformance of teammate reports before the lead synthesizes them, Sonnet is sufficient and saves tokens.

**Error recovery patterns.** When a teammate agent stalls or hits an error, the lead agent can reassign the task to another teammate. Kim's recommendation: include explicit "if you cannot complete analysis within 3 attempts, output a partial report with a `gaps` field" instructions in teammate CLAUDE.md. You already have a `gaps` field in your JSON schema — Kim's tip is to make the failure-to-partial-report path explicit, not just hoped for.

### Key Takeaway

Add explicit file ownership boundaries and a failure-to-partial-report instruction to your Agent Teams CLAUDE.md. These two operational changes prevent the most common Agent Teams failure modes — silent file conflicts and stalled teammates — without changing your architecture.

## Resource 2: Dispatch + Headless Mode — Run Your ISP Pipeline Hands-Free

**Source:** [What Is Claude Code Dispatch? — MindStudio](https://www.mindstudio.ai/blog/what-is-claude-code-dispatch)
**Also:** [Claude Code Headless Mode — MindStudio](https://www.mindstudio.ai/blog/claude-code-headless-mode-autonomous-agents)
**Also:** [Channels vs Dispatch vs Remote Control — MindStudio](https://www.mindstudio.ai/blog/claude-code-channels-vs-dispatch-vs-remote-control)
**Time:** ~5 min read (skim all three; the Dispatch article is the core one)
**Category:** Workflow — Autonomous Pipeline Execution

### Why This Is Relevant

Your ISP pipeline currently requires you at the terminal: launch `/reverse-engineer`, monitor progress via the new Monitor tool, review teammate reports, run `/ultrareview`. Dispatch and headless mode let you decouple yourself from the terminal entirely — launching, monitoring, and steering your pipeline from your phone or a thin web client while doing other engagement work.

**The three autonomy primitives and how they map to your workflow:**

| Feature | What It Does | Your ISP Application |
|---------|-------------|---------------------|
| **Headless mode** (`-p` flag) | Runs Claude Code without interactive input, outputs to stdout, exits | Launch a `/reverse-engineer` run as a background job in CI or on a server |
| **Dispatch** | Queues jobs programmatically with observability; integrates with Channels for streaming | Queue multiple cluster analyses as Dispatch jobs; monitor progress from Telegram |
| **Remote Control** | Connect to a running session from outside the terminal via REST API + WebSocket | Steer a long-running analysis — adjust scope, approve phase gates — from your phone during a client meeting |

**The practical progression for your pipeline:**

Start with headless mode — it's the simplest. Instead of opening a terminal and typing `/reverse-engineer billing-cluster`, run:

```bash
claude -p "Run /reverse-engineer on the billing cluster. Output findings as structured JSON to /output/billing-cluster.json. Use Agent Teams with 3 teammates."
```

This runs autonomously, no terminal needed. You can wrap it in a shell script that runs all 4 domain clusters sequentially or in parallel background jobs.

Once headless mode is comfortable, upgrade to Dispatch for queuing and observability — you get job status, progress streaming via Channels, and the ability to manage multiple concurrent pipeline runs. This is where your ISP pipeline becomes a *service* rather than a *session*.

**For the GenAI in SDLC presentation:**

*"The maturity progression: from AI-assisted coding (single agent) to AI-orchestrated analysis (Agent Teams) to AI-autonomous pipelines (Dispatch). At the highest tier, the developer defines the task and reviews the output — the execution is fully autonomous."*

This completes your maturity narrative: subagents → Agent Teams → orchestrator → autonomous execution.

### Key Takeaway

Try headless mode (`claude -p`) for a single-cluster ISP analysis run. It requires zero architecture changes — just wrap your existing `/reverse-engineer` command in a headless invocation. If it works, you've proven the pipeline can run unattended, which unlocks Dispatch and Routines for fully autonomous scheduled analysis.

## Resource 3: SDLC for Agentic AI Engineering — A Stakeholder-Ready Framework

**Source:** [SDLC for Agentic AI Engineering — Brett Luelling, Medium](https://medium.com/@brettluelling/sdlc-for-agentic-ai-engineering-5813abfdbc12)
**Also:** [Claude Code in 2026: Practical End-to-End SDLC Workflow — DevelopersVoice](https://developersvoice.com/blog/ai/claude_code_2026_end_to_end_sdlc/)
**Time:** ~4 min read (Luelling article is the core one)
**Category:** Presentation — SDLC Framework for Your GenAI Talk

### Why This Is Relevant

Your GenAI in SDLC presentation has all the stories — speed, quality, collaboration, productization, orchestration, and now autonomy. What it needs is a *framework* that organizes these into a stakeholder-friendly narrative. Luelling's article provides exactly that: a structured SDLC model for agentic AI that maps each phase to concrete capabilities.

**Luelling's agentic SDLC phases mapped to your ISP pipeline:**

| SDLC Phase | Traditional | Your Agentic Approach |
|-----------|------------|----------------------|
| **Spec** | Requirements docs written manually | Ultraplan drafts analysis scope in the cloud; colleagues comment and approve |
| **Architect** | Senior architect draws service maps | `/reverse-engineer` with Agent Teams auto-discovers architecture |
| **Implement** | Developers write code | Agent Teams execute parallel analysis with structured JSON output |
| **Verify** | Manual code review | `/ultrareview` multi-agent cloud review |
| **Reflect** | Post-mortem meeting | `/reflect` skill reviews what was found vs. what was expected |
| **Productize** | Documentation + handoff | `/team-onboarding` packages the pipeline for replication |

**The key narrative insight:** The SDLC doesn't change — spec, architect, implement, verify, reflect, productize. What changes is *who does the mechanical work at each phase*. The developer's role shifts from implementer to conductor: defining scope, reviewing plans, approving execution, and verifying results. The AI handles the mechanical execution at each phase.

**The Deloitte proof point for stakeholder credibility:**

Deloitte deployed Claude to 470,000+ employees with a Claude Center of Excellence and 15,000+ certified GenAI practitioners. For a BCG audience, this is the "enterprise-scale precedent" your presentation needs. Luelling references this as evidence that agentic AI in the SDLC isn't a research experiment — it's operational at the largest professional services firms.

### Key Takeaway

Structure your GenAI in SDLC presentation around the unchanged SDLC phases (spec → architect → implement → verify → reflect → productize), showing how each phase is AI-accelerated in your ISP pipeline. This makes the story accessible to non-technical stakeholders: the process they know hasn't changed — the execution speed and reliability have.

## Quick Win: Add File Ownership Boundaries to Your Agent Teams CLAUDE.md (3 min)

**Time: 3 minutes**

Add explicit file ownership rules to your Agent Teams lead agent instructions to prevent the most common multi-agent failure mode — silent file conflicts.

Add this to your team lead CLAUDE.md:

```markdown
## File Ownership Rules

Each teammate agent owns its domain cluster output exclusively:
- Teammate 1 (billing): writes ONLY to /output/billing/
- Teammate 2 (provisioning): writes ONLY to /output/provisioning/
- Teammate 3 (network): writes ONLY to /output/network/
- Teammate 4 (customer): writes ONLY to /output/customer/

Shared files are written ONLY by the lead agent after synthesis:
- /output/master-architecture.json (lead only)
- /output/cross-cluster-dependencies.json (lead only)
- /output/coupling-hotspots.json (lead only)

If a teammate needs to reference another cluster's findings, it reads 
the other teammate's output directory — it never writes to it.
```

**Why now:** From John Kim's tips (Resource 1), file ownership is the single highest-impact operational change for Agent Teams stability. Without it, two teammates analyzing services that share a config file can silently overwrite each other's findings. With it, the merge-to-master-map step happens exactly once, in the lead agent's synthesis phase, with full cross-cluster context.

This takes 3 minutes to add and eliminates an entire class of Agent Teams failure modes.
