## Resource 1: Agent View — Anthropic's Native Answer to Your Observability Problem

**Source:** [Manage multiple agents with agent view — Claude Code Docs](https://code.claude.com/docs/en/agent-view)
**Also:** [Claude Code Agent View: the CLI Dashboard That Unifies All Sessions — Pasquale Pillitteri](https://pasqualepillitteri.it/en/news/2384/claude-code-agent-view-cli-dashboard-sessions-2026)
**Also:** [How to Manage Multiple AI Agents Without Terminal Chaos — MindStudio](https://www.mindstudio.ai/blog/claude-code-agent-view-manage-multiple-agents)
**Also:** [Claude Code agent view is a better dashboard. So why aren't developers convinced? — The New Stack](https://thenewstack.io/claude-code-agent-view/)
**Time:** ~5 min read (official docs + skim The New Stack analysis)
**Category:** Pipeline Evolution — The Feature That Complements Your Observability Layer

### Why This Is Relevant

You built your observability dashboard (Digest #45) using disler's hooks-based approach — a custom React dashboard at `localhost:5173` that tracks every tool call and agent timeline via PostToolUse hooks. Agent View, which shipped May 11 in v2.1.139, is Anthropic's native solution to the same problem: a single CLI screen showing every running session, which ones need input, and which are done.

**What Agent View does:**

| Capability | How It Works |
|-----------|-------------|
| **Unified session list** | `claude agents` opens a table of all sessions — running, blocked on input, or completed |
| **Peek panel** | Press Space on any row to see the session's latest output or pending question |
| **Reply without switching** | Type a reply from the peek panel — no need to attach to the session |
| **Attach/detach** | Press Enter to attach (full interactive session), ← to detach back to the list |
| **Background dispatch** | Start new sessions directly from Agent View — they appear as rows immediately |

**How Agent View relates to your existing observability:**

Your disler dashboard and Agent View solve overlapping but different problems:

| Your Dashboard (disler hooks) | Agent View (native) |
|-------------------------------|-------------------|
| Tracks *tool-call-level* granularity | Tracks *session-level* status |
| Custom metrics (token cost, effort level, validation results) | Status only (running/blocked/done) |
| Persistent history (stores events for post-run analysis) | Live view only (current sessions) |
| Requires custom setup (hooks + React app) | Built-in (`claude agents`) |
| Web-based (shareable URL) | Terminal-only |

**The strategic conclusion:** Agent View doesn't replace your dashboard — it complements it. Agent View is your **control plane** (which sessions are running? which need attention?), while your disler dashboard is your **data plane** (what did each agent do? how much did it cost? did governance hooks fire?). For London, this distinction is a strong talking point: "Anthropic ships the control plane. We built the data plane."

**For your London demo:** If you were planning to demo with tmux split panes (Digest #47), consider demoing with Agent View instead — or alongside it. Agent View solves the 6-pane cramming problem you identified: instead of 5 agents + dashboard competing for screen space, Agent View shows all 5 sessions in a clean list, and you attach to whichever one the audience wants to see. Your disler dashboard runs in a browser on the second monitor showing the deep analytics.

**Post-London experiment:** Run your pipeline with Agent View as the primary interface and your disler dashboard on a second screen. Note what information you look for in Agent View vs. the dashboard. If Agent View handles 80% of your real-time needs, simplify your hooks to focus on post-run analytics rather than real-time display.

### Key Takeaway

Agent View (`claude agents`) gives your 5-agent pipeline a native control plane — session status, quick replies, attach/detach — without tmux complexity. Keep your disler hooks dashboard for deep observability (token cost, governance hook firings, per-agent timelines). At London, frame it as: "Anthropic ships the session control plane. Our hooks-based dashboard is the agent data plane. Together they give us full observability from dispatch to output validation." Update to v2.1.139+ today so Agent View is available for your demo tomorrow.

## Resource 2: `/goal` — Autonomous Completion Loops That Could Replace Your Pipeline's Manual Checkpoints

**Source:** [Keep Claude working toward a goal — Claude Code Docs](https://code.claude.com/docs/en/goal)
**Also:** [Claude Code 2.1.139 adds /goal command: set completion conditions and let agents work across multiple turns — explainx.ai](https://explainx.ai/blog/claude-code-goal-command-long-running-agents-2026)
**Also:** [What Is the /goal Command in Claude Code? Autonomous Long-Running Tasks Explained — MindStudio](https://www.mindstudio.ai/blog/claude-code-goal-command-autonomous-tasks)
**Also:** [Introduction to Claude Code goal mode — Apiyi.com](https://help.apiyi.com/en/claude-code-goal-mode-keep-working-until-done-guide-en.html)
**Time:** ~5 min read (official docs + MindStudio explainer)
**Category:** Pipeline Architecture — A New Primitive for Your Domain Agents

### Why This Is Relevant

Your pipeline's domain agents (API contracts, billing, auth, infrastructure) currently run until they decide they're done — the agent itself judges completion. Your PostToolUse hooks validate *output quality*, but nothing validates *task completeness*. Did the API contract agent find all endpoints, or did it stop after the obvious ones? Your governance layer catches bad output but can't catch incomplete output.

`/goal` solves this. It adds a **separate evaluator model** that checks a completion condition after every turn. The evaluator is independent — it's not the agent that did the work. This is the same architectural principle as your PostToolUse hooks (independent verification), applied to completion rather than quality.

**How `/goal` works:**

```
/goal Analyze all API contracts in the payments cluster until:
  1. Every service endpoint is documented with request/response schemas
  2. All inter-service dependencies are mapped
  3. Authentication patterns are identified for each endpoint
```

After every turn, a fresh evaluator model checks whether conditions 1-3 are met. The agent keeps working until the evaluator says "done" — or until constraints (token budget, turn count) are reached.

**How this maps to your pipeline:**

| Current Approach | With `/goal` |
|-----------------|-------------|
| Agent decides when it's done | Independent evaluator checks completion criteria |
| PostToolUse hooks validate output quality | `/goal` validates task completeness |
| Manual checkpoint review between stages | Automated completion verification |
| "Did the agent produce valid output?" | "Did the agent finish the job?" |

**The architectural insight:** Your governance model has three tiers for *safety* (hard_deny, auto mode, PostToolUse hooks). `/goal` adds a tier for *completeness*. Together, they answer two independent questions:

1. **Safety (your governance):** "Is the output safe and valid?"
2. **Completeness (`/goal`):** "Is the task actually done?"

**Integration with your pipeline:**

Your conductor currently decomposes the problem and dispatches agents. With `/goal`, each dispatched agent gets both a task and a completion condition:

```
# Conductor dispatches API contract agent with /goal
claude --goal "All endpoints in payments-cluster documented with schemas" \
  --settings .claude/settings-governance.json \
  --effort xhigh \
  "Analyze API contracts for the payments cluster"
```

The `--goal` flag (or `/goal` in interactive mode) ensures the agent doesn't prematurely stop. The `--settings` flag (from the new `claude agents` flags in Resource 3 of yesterday's digest) ensures governance applies. The `--effort xhigh` calibrates both the domain analysis and your PostToolUse validation depth.

**Important caveat:** `/goal` is optimized for software development tasks (refactoring, feature work, testing, migration). Your ISP pipeline's domain analysis is non-standard — the evaluator may struggle to judge whether "all endpoints are documented" without domain knowledge. Test with one agent before enabling pipeline-wide. Consider adding concrete, verifiable markers to your completion conditions: "the output file contains at least 10 endpoints" rather than "all endpoints are documented."

**For your London questions:** `/goal`'s independent evaluator strengthens your Angela Jiang question about dreaming. The evaluator is another model judging the working agent — if dreaming can learn to fool PostToolUse hooks, can it also learn to fool the `/goal` evaluator? The attack surface expands with each independent verification layer. This is a nuanced security question that shows you understand the architecture.

### Key Takeaway

`/goal` adds a completeness verification layer to your pipeline — an independent evaluator that checks whether each agent finished its task, not just whether the output is valid. This is the missing fourth tier in your governance model: safety (hard_deny + auto mode + PostToolUse) plus completeness (`/goal`). Don't integrate it before London — but mention it as your post-London roadmap item. "We've built three tiers for safety. The `/goal` command gives us a fourth tier for completeness. Our next sprint adds completion verification to every domain agent."

## Resource 3: The Claude Code Pipeline Ecosystem — Where Your Architecture Sits in the Community

**Source:** [claude-pipeline: Portable Claude Code multi-agent pipeline — GitHub (aaddrick)](https://github.com/aaddrick/claude-pipeline)
**Also:** [Claude Code Agent Teams, Subagents, and MCP: The 2026 Playbook — Developers Digest](https://www.developersdigest.tech/blog/claude-code-agent-teams-subagents-2026)
**Also:** [Claude Code hooks-multi-agent-observability — GitHub (disler)](https://github.com/disler/claude-code-hooks-multi-agent-observability)
**Also:** [Claude Code Agent Monitor: real-time monitoring dashboard — GitHub (hoangsonww)](https://github.com/hoangsonww/Claude-Code-Agent-Monitor)
**Time:** ~5 min read (aaddrick pipeline README + Developers Digest playbook)
**Category:** Post-London — Community Context for Your Pipeline Architecture

### Why This Is Relevant

Tomorrow at London you'll present your pipeline to people who are building similar things. Knowing the community landscape helps you position your architecture: what's unique about your approach, what's common, and where the community has converged on different solutions.

**Three community pipeline architectures worth knowing:**

**1. aaddrick/claude-pipeline — "Portable multi-agent pipeline"**

A complete `.claude/` configuration providing skills, agents, hooks, orchestration scripts, and quality gates. Their architecture follows a three-stage pipeline: `pm-spec` (reads enhancement, writes working spec) → `architect-review` (validates design, produces ADR) → `implementer-tester` (implements + tests).

| Their Approach | Your Approach | Difference |
|---------------|---------------|-----------|
| Three sequential stages | Five parallel domain agents + synthesis | You parallelize more aggressively |
| Quality gates between stages | PostToolUse hooks during execution | Your validation is continuous, not stage-gated |
| Generic software dev pipeline | Domain-specific ISP analysis | Your pipeline is specialized |

**What you can learn:** Their stage-gating approach (don't start implementation until design passes review) could improve your pipeline's synthesis stage. Currently your synthesis agent starts when domain agents finish. What if synthesis had a pre-condition gate — "only synthesize if all 4 domain outputs pass PostToolUse validation"? This prevents the synthesis agent from merging garbage.

**2. disler/claude-code-hooks-multi-agent-observability — Your observability foundation**

You already use this (Digest #45). Worth noting: the repo has gained significant traction since you adopted it. The community is converging on hooks-based observability as the standard pattern — your dashboard isn't a custom hack, it's the emerging best practice.

**3. hoangsonww/Claude-Code-Agent-Monitor — Full-stack monitoring dashboard**

A React + SQLite + WebSocket dashboard that tracks sessions, agent activity, tool usage, and subagent orchestration. More heavyweight than disler's approach but offers persistent storage and a Kanban-style status board.

| disler dashboard (yours) | hoangsonww dashboard | Agent View (native) |
|-------------------------|---------------------|-------------------|
| Lightweight hooks → events | Full-stack (SQLite + WebSocket) | Built-in CLI |
| Real-time event stream | Persistent history + Kanban | Session status only |
| Custom React UI | Richer UI (charts, boards) | Terminal UI |

**For London conversations:** When someone asks "how do you monitor your agents?", you have a layered answer: "Agent View for session control, hooks-based dashboard for real-time observability, and PostToolUse validation for governance. Three layers, three purposes." This positions you as someone who has thought through the observability stack, not just installed a single tool.

**The Developers Digest heuristic for choosing architectures:**

"Reach for subagents first, move to skills when you want the same instructions in line, and move to Agent Teams when one specialist isn't enough and they actually need to talk through a plan." Your pipeline correctly uses Agent Teams — your 5 specialists need coordination (the inter-agent steering problem from Digest #48). The heuristic validates your architectural choice.

**The "3-4 agent maximum" warning:**

Multiple community guides recommend limiting to 3-4 subagents, arguing that more agents increase coordination overhead and reduce your ability to redirect. Your pipeline has 5. At London, if someone raises this concern, your answer is: "We tested with 3 and 5. The specialized domain agents (API, billing, auth, infrastructure) each have distinct tool needs and context requirements. Merging two agents degraded output quality more than the coordination overhead cost us. The fifth agent (synthesis) is architecturally distinct — it's the aggregator, not a domain specialist."

### Key Takeaway

Your pipeline sits at the sophisticated end of the community spectrum: 5 parallel domain agents (most use 3), continuous PostToolUse validation (most use stage gates), and a hooks-based observability dashboard (emerging best practice). At London, position your architecture as "parallel-first with continuous governance" — the inverse of the community's common "sequential-first with stage gates." Both work; yours is optimized for throughput, theirs for sequential quality assurance.
