## Resource 1: Effective Claude Code Workflows in 2026 — What Changed and What Works Now

**Source:** [Effective Claude Code Workflows in 2026: What Changed and What Works Now — Sean Moran, Medium](https://medium.com/@sean.j.moran/effective-claude-code-workflows-in-2026-what-changed-and-what-works-now-c93ebc6f8f50)
**Time:** ~5 min read
**Category:** Workflow — Context Engineering for Long Sessions

### Why This Is Relevant

Sean Moran's article (published April 2026) documents a real working session where every workflow pattern reflects actual usage within a single Claude Code conversation. The key insight: **the centre of gravity has shifted from manual context management to a richer harness around the model** — plan mode, parallel exploration, persistent project memory, structured execution, and long-session continuity.

This directly addresses what happens when you run a multi-hour ISP analysis. Your `/reverse-engineer` skill launches subagents, collects findings, and synthesizes architecture maps. But as the main session context fills up, quality degrades. Moran's article documents the 2026 approach to preventing this:

**Plan Mode as architecture phase gate:**

For a substantial rewrite of a reporting engine, Moran used `/plan` to let Claude explore the codebase, design the architecture, and produce a structured plan — covering data structures, function signatures, implementation order, and edge cases — *before any code changed*. After review and approval, it implemented 817 insertions and 260 deletions across four files.

For your ISP pipeline, this suggests a workflow refinement: before each `/reverse-engineer` run on a service cluster, use `/plan` to have Claude map the cluster's structure first. The plan becomes the structured context for the analysis phase, reducing the exploratory token spend that currently eats into your context window.

**Context harness > prompt tricks:**

The 2025 approach favoured verbose, context-heavy prompts with explicit file references. In 2026, the context machinery has become less visible, less manual, and less dominant. Moran's approach: externalize context into CLAUDE.md, plan before coding, isolate tasks through subagents, and enforce policies through hooks. You're already doing most of this — but the article's specific patterns for *session continuity* (using `/compact` strategically, JSON handoffs between work chunks) will help your multi-hour analysis sessions.

### Key Takeaway

**Add a `/plan` phase before each Agent Teams analysis run.** Instead of launching agents directly into analysis, have each agent first plan its approach to its domain cluster, get approval, then execute. This front-loads the exploration into a structured plan, reducing context waste during the analysis phase and giving you a review checkpoint before tokens are spent on execution.

## Resource 3: Claude Code 1M Context Window — Stop Context Rot in 2026

**Source:** [Claude Code 1M Context Window: Stop Context Rot in 2026 — Mejba Ahmed](https://www.mejba.me/blog/claude-code-1m-context-management)
**Also:** [Practical workflow for reducing token usage while preserving session continuity — Artem Getmann, GitHub Gist](https://gist.github.com/artemgetmann/74f28d2958b53baf50597b669d4bce43)
**Time:** ~5 min read (skim the Mejba article + the Gist)
**Category:** Operations — Context Management for Multi-Agent Analysis

### Why This Is Relevant

Context rot is the measurable degradation in model performance as input context grows. With Opus 4.7's 1M context window, it's tempting to assume you have unlimited room. You don't. Mejba Ahmed's article documents the specific patterns that cause analysis quality to drop in long sessions — and the countermeasures.

**Why this matters for your Agent Teams pipeline:**

Each of your 5 ISP analysis agents has its own context window. A single agent analyzing 12 services in the billing cluster might accumulate 200K+ tokens of file contents, analysis findings, and intermediate reasoning. At that point, even with Opus 4.7's improved comprehension, the agent starts losing track of earlier findings. The result: the architecture map from service 12 doesn't reference the coupling patterns found in service 1.

**The /compact discipline:**

The key countermeasure is strategic `/compact` usage — not waiting until the context is full, but compacting proactively at natural breakpoints:

```
Analyze service 1-3 → /compact "Preserve: billing-core boundaries, 
  API contracts found, coupling with provisioning" → Analyze service 4-6 → 
  /compact "Preserve: all prior findings + new data flow patterns" → ...
```

Each `/compact` call tells Claude exactly what to preserve from the previous analysis chunk. Without this, the automatic compaction algorithm decides what to keep — and it doesn't know that the coupling pattern between billing-core and provisioning-gateway is the most important finding in the session.

**The JSON handoff pattern for Agent Teams:**

For multi-agent setups, Artem Getmann's Gist describes a structured handoff approach: when an agent finishes a work chunk, it outputs its findings as structured JSON. The next agent (or the same agent after `/compact`) ingests that JSON as its starting context. This is more reliable than hoping the automatic compaction preserves the right details.

For your Agent Teams lead agent: instead of having teammate agents dump their findings as free-text prose, have them output structured JSON with specific fields (service_name, boundaries, api_contracts, coupling_hotspots, confidence_score). The lead agent synthesizes these structured reports into the master architecture map.

**The 200-line CLAUDE.md rule:**

Both sources confirm what the ObviousWorks article told you: keep the root CLAUDE.md under 200 lines. Instruction adherence measurably drops above this threshold. Your modular @imports approach is correct — today's resources validate it with quantitative evidence.

### Key Takeaway

**Add explicit `/compact` checkpoints to your Agent Teams analysis workflow.** After each agent finishes analyzing a service cluster sub-group (every 3-4 services), compact with explicit preservation instructions listing the key findings so far. For the lead agent, require teammate agents to report in structured JSON format instead of free-text — this survives compaction better and makes cross-agent synthesis more reliable.

## Quick Win: Add Structured JSON Output to Your Agent Teams Teammate Reports (5 min)

Update your Agent Teams CLAUDE.md teammate instructions to require structured output. This takes 5 minutes and immediately improves the quality of your lead agent's architecture synthesis.

**Add this to each teammate agent's instructions:**

```markdown
## Output Format

After analyzing your assigned service cluster, output your findings as structured JSON:

```json
{
  "cluster_name": "billing",
  "services_analyzed": ["billing-core", "billing-gateway", "invoice-service"],
  "boundaries": [
    {
      "service": "billing-core",
      "responsibility": "...",
      "inbound_dependencies": ["provisioning-gateway"],
      "outbound_dependencies": ["invoice-service", "payment-processor"]
    }
  ],
  "api_contracts": [
    {
      "from": "billing-core",
      "to": "provisioning-gateway",
      "protocol": "REST",
      "endpoint": "/api/v2/provision",
      "pattern": "synchronous"
    }
  ],
  "coupling_hotspots": [
    {
      "services": ["billing-core", "provisioning-gateway"],
      "type": "synchronous_coupling",
      "risk": "high",
      "evidence": "Direct REST call with shared DTO"
    }
  ],
  "confidence": 0.85,
  "gaps": ["Could not trace async event flows — need Kafka topic mapping"]
}
```

This structured format: survives `/compact` better than prose, enables the lead agent to merge findings programmatically, and produces a consistent schema across all 5 agents — so the master architecture map has uniform data quality regardless of which agent analyzed which cluster.

**Why this is today's Quick Win:** It takes 5 minutes to add to your teammate CLAUDE.md instructions, immediately improves the reliability of your lead agent's cross-cluster synthesis, and implements the JSON handoff pattern from today's Resource 3. The next time you run Agent Teams on the ISP codebase, every agent's findings arrive in a merge-ready format instead of unstructured prose that the lead agent has to parse and interpret.
