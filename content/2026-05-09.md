## Resource 2: Dreaming Security — The Enterprise Adoption Gate You Haven't Assessed

**Source:** [Claude Agents Can Now Dream: How AI Engineers Should Use Anthropic's New Agent Features Without Creating New Attack Paths — Ken Huang](https://kenhuangus.substack.com/p/claude-agents-can-now-dream-how-ai)
**Also:** [Dreams API Docs — Claude Platform](https://platform.claude.com/docs/en/managed-agents/dreams)
**Also:** [Dreaming Explained — BuildFastWithAI](https://www.buildfastwithai.com/blogs/claude-managed-agents-dreaming-explained)
**Also:** [Anthropic is letting Claude agents 'dream' — SiliconANGLE](https://siliconangle.com/2026/05/06/anthropic-letting-claude-agents-dream-dont-sleep-job/)
**Time:** ~6 min read (Ken Huang's article — the only security-focused analysis published so far)
**Category:** Security — The Assessment Your BCG Clients Will Demand

### Why This Is Relevant

Yesterday's digest (Digest #40) framed the functional comparison: MLflow gives you tool-level depth; dreaming gives you cross-session breadth. The recommendation was a hybrid stack. But that comparison missed the dimension that matters most for enterprise adoption: **security.**

Ken Huang — CEO of DistributedApps.ai and a recognized expert in AI security — published a security analysis of dreaming, outcomes, and multiagent orchestration **18 hours ago**. This is the first independent security assessment of these features, and it surfaces attack paths that the functional evaluation didn't consider.

**The security risks specific to dreaming:**

| Risk | What It Means | Your Pipeline Impact |
|------|-------------|---------------------|
| **Memory poisoning** | A compromised or adversarial session transcript could inject misleading patterns into the dream agent's memory store. The dream agent reads past transcripts and extracts "lessons" — if a transcript contains poisoned data, that poison becomes persistent memory. | If your ISP pipeline processes untrusted codebases, a malicious repo could craft file contents that appear in session transcripts and influence what the dream agent learns. |
| **Cross-session information leakage** | Dreaming reads across multiple sessions. If sessions belong to different clients or contain different security classifications, the dream agent may blend information across trust boundaries. | If you run `/reverse-engineer` on multiple ISP clients' codebases, dreaming could leak patterns from Client A's analysis into Client B's agent memory. For BCG, this is a client confidentiality issue. |
| **Prompt injection through transcripts** | Session transcripts contain raw tool outputs — file contents, shell command results, API responses. A dream agent reading these transcripts is exposed to prompt injection embedded in those outputs. | An ISP codebase could contain comments or config values designed to influence any LLM that reads them. Dreaming amplifies this: the injection persists in memory rather than expiring with the session. |
| **Uncontrolled memory drift** | If dreaming runs on auto-update (without review-before-deploy), the memory store evolves without human oversight. Over time, the agent's behavior drifts from its original design intent. | Your carefully tuned agent roles and skill prompts could be silently overridden by dream-generated memories that contradict your instructions. |

**How to mitigate — the four controls Ken Huang recommends:**

1. **Session isolation by trust boundary.** Never let dreaming read across sessions that belong to different clients or security classifications. Scope dream agents to a single engagement or project.
2. **Review-before-deploy for memory updates.** Always set dreaming to produce candidate memories for human review rather than auto-updating the memory store. Read the diff before it ships.
3. **Input sanitization for dream transcripts.** Strip or neutralize raw tool outputs from transcripts before dreaming processes them. The dream agent needs the *pattern* (what the agent did), not the *data* (what was in the files).
4. **Memory store versioning.** Treat the memory store like code — version it, diff it, and roll back if drift is detected.

**Why this matters for your presentation:** Enterprise stakeholders won't ask "does dreaming work?" — they'll ask "is dreaming safe?" Ken Huang's analysis gives you the answer: "Yes, with four controls." That's the enterprise adoption story: you don't reject the capability — you govern it. Add a "Security Guardrails" slide to your Managed Agents section that maps these four controls.

**The Harvey signal:** Harvey (the legal AI company) reported ~6x improvement in agent completion rates with dreaming enabled. This is the strongest production validation published so far — but Harvey operates in a domain where session isolation by client matter is already standard practice. They've already implemented control #1. The question for your ISP pipeline is whether you have equivalent isolation.

### Key Takeaway

Read Ken Huang's article before you enable dreaming for your pipeline. The functional case for dreaming is strong (Digest #40). The security case requires four explicit controls: session isolation, review-before-deploy, input sanitization, and memory versioning. For BCG client work, control #1 (session isolation by trust boundary) is non-negotiable — you cannot let dreaming blend patterns from Client A's ISP analysis into Client B's agent memory. Add these controls to your evaluation comparison from yesterday, and add a "Security Guardrails for Dreaming" slide to your presentation. The London conference is the place to ask Angela Jiang whether these controls are supported natively or require custom implementation.

## Resource 3: This Week's Claude Code Releases — Plugin, Pipeline, and Observability Updates

**Source:** [Claude Code Changelog — Official Docs](https://code.claude.com/docs/en/changelog)
**Also:** [Claude Code Updates May 2026 — Releasebot](https://releasebot.io/updates/anthropic/claude-code)
**Also:** [Claude Code Releases — GitHub](https://github.com/anthropics/claude-code/releases)
**Time:** ~4 min read (changelog entries + Releasebot summary)
**Category:** Platform — What Shipped This Week That Affects Your Pipeline

### Why This Is Relevant

While you were focused on the Managed Agents announcement (Digest #40), Claude Code shipped several incremental updates that directly affect your plugin packaging, pipeline observability, and daily workflow.

**1. `--plugin-dir` now accepts `.zip` archives**

In Digest #38, you learned about `--plugin-url` for loading plugins from a URL. This week's update extends `.zip` support to `--plugin-dir` as well. The practical impact: you can distribute your `/reverse-engineer` plugin as a `.zip` archive that works with both flags — `--plugin-url` for remote loading and `--plugin-dir` for local installation. One artifact, two distribution paths.

**For your team marketplace:**
```bash
# Remote: colleague loads from internal server
claude --plugin-url https://internal.bcg.com/plugins/reverse-engineer.zip

# Local: colleague loads from downloaded archive
claude --plugin-dir ./reverse-engineer.zip
```

No more extracting `.zip` files manually before loading local plugins. This reduces the friction in your distribution workflow from Digest #38.

**2. `CLAUDE_CODE_SESSION_ID` environment variable in Bash subprocess**

Every Bash tool call now has access to `CLAUDE_CODE_SESSION_ID` as an environment variable. This is a pipeline observability feature: your PostToolUse hooks and validation scripts can now correlate their logs with the specific Claude Code session that triggered them.

**For your MLflow tracing setup:**
```bash
# In your PostToolUse validation hook:
echo "Session $CLAUDE_CODE_SESSION_ID: Validating output schema" >> /var/log/pipeline.log
```

When you're debugging a failed Agent Teams run with 5 agents (5 sessions), this env var lets you trace which agent's session produced the validation failure. Combined with MLflow's span trees, you now have session-level correlation on top of tool-level tracing.

**3. `/mcp` now shows tool count per server**

The `/mcp` command now displays how many tools each connected MCP server exposes, and flags servers that connected with 0 tools. This is an operational visibility improvement: if your pipeline relies on an MCP server that silently connected without its tools (a startup race condition the auto-retry from Digest #36 partially solved), you'll now see the problem immediately in `/mcp` output rather than discovering it when an agent fails to find a tool mid-analysis.

**4. Bare `/color` picks a random session color**

Minor but useful for Agent Teams: when you're running multiple Claude Code sessions side-by-side (lead + 4 teammates), assigning each a distinct color makes it easier to visually track which session is which. `/color` without arguments now randomizes — run it once per session at startup.

### Key Takeaway

Update your plugin distribution workflow: your `.zip` archive now works with both `--plugin-url` (remote) and `--plugin-dir` (local), so you only need to build one artifact. Then add `CLAUDE_CODE_SESSION_ID` to your PostToolUse validation hook's logging — when a pipeline run fails, you'll be able to trace the failure to the specific agent session that produced it without digging through interleaved terminal output.
