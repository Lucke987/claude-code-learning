## Resource 1: Claude Agent SDK Production Patterns Guide — The Five Patterns Your Pipeline Needs Before London

**Source:** [Claude Agent SDK: Complete Production Patterns Guide 2026 — DigitalApplied](https://www.digitalapplied.com/blog/claude-agent-sdk-production-patterns-guide)
**Also:** [Claude Agent SDK in Production: A Studio's Playbook — Autoolize](https://autoolize.com/blog/claude-agent-sdk-production-playbook/)
**Also:** [Agent SDK Overview — Claude Code Docs](https://code.claude.com/docs/en/agent-sdk/overview)
**Time:** ~6 min read (DigitalApplied guide + skim Autoolize for case study context)
**Category:** Production — The Missing Layer Between Your Prototype and Your Demo

### Why This Is Relevant

Your pipeline has four layers: domain logic (the `/reverse-engineer` skill), orchestration (Agent Teams with 5 agents), governance (hard deny + auto mode + PostToolUse hooks), and automation (routines). What it doesn't yet have is **production hardening** — the patterns that prevent your pipeline from failing expensively, silently, or in ways that embarrass you during a live demo at London.

DigitalApplied's guide identifies the five production patterns that separate prototypes from production agents. Each maps directly to a gap in your current architecture:

**1. State Persistence — Don't Trust the Context Window**

| Your Current Approach | The Production Pattern |
|----------------------|----------------------|
| Agent state lives in the context window; if a session crashes, work is lost | Treat the SDK session as ephemeral. Persist state to Postgres, Redis, or object storage. The conversation log is the source of truth. |

For your pipeline: if your dependency mapper agent crashes mid-analysis after discovering 30 service dependencies, those 30 discoveries should survive the crash. Today they don't — they're in the context window. Adding a checkpoint mechanism (write intermediate results to a JSON file after each major discovery) gives your pipeline crash recovery without adding infrastructure.

**2. Cost Governance — Per-Task Caps, Not Monthly Alerts**

| Risk | Mitigation |
|------|-----------|
| A single pipeline run with 5 agents could consume your entire daily budget if one agent loops | Add per-task, per-agent cost caps in your harness. Hard caps protect margin *before* a runaway loop eats it. |

For your pipeline: your conductor agent delegates to 4 domain specialists + 1 synthesis agent. If the billing domain agent encounters an unusually complex service cluster, it could loop for 20+ iterations burning tokens. A per-agent cap of (e.g.) $2 per domain agent and $5 for the synthesis agent gives you a predictable ceiling of ~$13 per pipeline run. Set these in your Agent Teams configuration.

**3. Circuit Breakers — Fail Fast, Not Slow**

Production agents fail slowly and expensively. A circuit breaker pattern detects when an agent is making no progress (consecutive failed tool calls, repeated identical outputs, context window approaching capacity) and halts it before it wastes more resources.

For your pipeline: define three circuit-breaker conditions:
- **Repetition detector:** If an agent produces the same output 3 times consecutively, halt it
- **Error rate threshold:** If >50% of tool calls in the last 10 fail, halt
- **Context budget alarm:** If an agent's context window is >80% full, force a checkpoint and compact

**4. Eval Pipelines — Offline + Online, From Day One**

| Eval Type | When It Runs | What It Catches |
|----------|-------------|----------------|
| **Offline** | Before deployment, against golden files | Regressions — did your prompt change break a previously working cluster? |
| **Online** | Every production run, via PostToolUse hooks | Drift, prompt injection, hallucinated tool calls |

You already have the online layer (PostToolUse hooks with `updatedToolOutput` and `$CLAUDE_EFFORT`). The offline layer — golden file comparison — is what you need for the London demo. Create 2-3 reference outputs from known clusters, then validate every skill prompt change against them before deploying.

**5. Deployment Architecture — Match Runtime to Agent Profile**

Your pipeline runs long (multi-minute agent analysis, file-heavy I/O). This rules out serverless (Lambda/Vercel Functions have timeout and cold-start constraints). The guide recommends long-running containers or dedicated VMs for agent workloads that exceed 60 seconds. For your routine-based automation (Digest #43), Anthropic's cloud infrastructure handles this — but for local development and demo runs, ensure your environment doesn't have aggressive process timeouts.

**For your presentation:** These five patterns are your "Production Guardrails" slide. The narrative: "We don't just build agents — we ship them with state persistence, cost caps, circuit breakers, eval pipelines, and appropriate deployment architecture. Here's how each one works in our ISP pipeline." The audience hears governance, not just capability.

### Key Takeaway

Implement two of these five patterns before London: (1) **checkpoint persistence** — have each domain agent write intermediate results to a JSON file after each major discovery, so a crash doesn't lose work; and (2) **golden file evals** — create 2-3 reference outputs from known clusters and validate your skill against them before every prompt change. These two give you crash recovery and regression detection — the minimum viable production hardening for a live demo. The cost caps and circuit breakers are important but can wait until after London.

## Resource 2: 7 Claude Code Features You Likely Missed in the Last 10 Days

**Source:** [I Tested 7 Claude Code (New) Features You Likely Missed (In the Last 10 Days) — Joe Njenga, Medium](https://medium.com/@joe.njenga/i-tested-7-claude-code-new-features-you-likely-missed-in-the-last-10-days-87629ab086c7)
**Also:** [Claude Code Changelog — Official Docs](https://code.claude.com/docs/en/changelog)
**Also:** [Claude Code Updates May 2026 — Releasebot](https://releasebot.io/updates/anthropic/claude-code)
**Time:** ~5 min read (Joe Njenga's walkthrough + changelog cross-reference)
**Category:** Workflow — The Features Hiding in Plain Sight

### Why This Is Relevant

You've been focused on high-level architecture (Managed Agents, routines, governance models) for the last six digests. Meanwhile, Claude Code shipped incremental features that improve your *daily* workflow — and you may have missed them. Joe Njenga tested the most notable ones from the May 2–12 window. Here are the ones that matter for your work:

**1. Cross-Project Prompt History (Ctrl+R)**

Ctrl+R reverse-search now defaults to prompts across *all* projects, not just the current one. Press Ctrl+S while searching to narrow back to the current project or session.

**Why this matters for you:** You work across multiple repos — your ISP pipeline, your presentation materials, your learning digest repo. When you remember writing a great prompt two days ago but can't recall which project it was in, Ctrl+R now finds it everywhere. This is particularly valuable for reusing prompts you've refined across 43 digests of iteration.

**2. `claude plugin prune` — Clean Up Orphaned Dependencies**

New command that removes orphaned plugin dependencies. After 9 weeks of installing, testing, and removing plugins (financial services templates, community skills), your environment likely has accumulated artifacts.

```bash
claude plugin prune
```

**3. `alwaysLoad` for MCP Server Config**

MCP servers can now be configured with `alwaysLoad: true` to skip tool-search deferral. If your pipeline relies on an MCP server whose tools must be available immediately (not lazily loaded), this eliminates the startup race condition where an agent tries to use a tool before its server has finished loading.

```json
{
  "mcpServers": {
    "your-server": {
      "command": "your-mcp-server",
      "alwaysLoad": true
    }
  }
}
```

**4. Faster `/resume` (Up to 67% Faster on Large Sessions)**

Sessions over 40MB — which your multi-hour pipeline debugging sessions likely are — now resume up to 67% faster. If you've been avoiding `/resume` because of lag, retry it.

**5. Image Resize Fix (2000px Max, Not 2576px)**

Images are now correctly resized to 2000px maximum instead of 2576px. If your pipeline processes architecture diagrams or screenshots during reverse-engineering, this means less context budget consumed per image — more room for the analysis that matters.

**6. Type-to-Filter in `/skills`**

The `/skills` command now has a search box. With your growing collection of custom skills, you can type `/skills` then filter by name instead of scrolling. Minor but saves seconds on every invocation.

**7. Faster MCP Startup with Multiple Servers**

If you have multiple MCP servers configured (Transcript Library, custom connectors for your pipeline), they now start faster in parallel. Combined with `alwaysLoad`, your pipeline's MCP dependencies are both faster and more reliable.

**The meta-pattern:** Each of these features is small individually. Together, they reduce friction in your daily workflow by 5-10 minutes per session. Over the 7 days before London, that's 35-70 minutes recovered — enough time for one more demo rehearsal.

### Key Takeaway

Run `claude plugin prune` today to clean up 9 weeks of accumulated plugin artifacts. Then add `alwaysLoad: true` to any MCP server your pipeline agents depend on at startup — this eliminates the lazy-loading race condition that causes intermittent "tool not found" failures. These two changes take 2 minutes and remove two sources of flaky behavior before your London demo.

## Quick Win: Create Golden File Evals for Your Pipeline (5 min)

**Time: 5 minutes**

Your PostToolUse hooks validate output quality in real-time. Golden file evals validate it *before deployment* — catching regressions before they reach a demo or production run.

**Step 1:** Pick one cluster your pipeline has successfully reverse-engineered. Copy its output to a golden file:

```bash
mkdir -p .claude/evals/golden
cp output/payments-cluster/api-contracts.json .claude/evals/golden/payments-api-contracts.json
cp output/payments-cluster/dependency-map.json .claude/evals/golden/payments-dependency-map.json
```

**Step 2:** Create a simple eval script that diffs pipeline output against the golden files:

```python
import json, sys

def compare_schemas(golden_path, actual_path):
    with open(golden_path) as f:
        golden = json.load(f)
    with open(actual_path) as f:
        actual = json.load(f)

    golden_keys = set(golden.keys())
    actual_keys = set(actual.keys())

    missing = golden_keys - actual_keys
    extra = actual_keys - golden_keys

    if missing:
        print(f"REGRESSION: Missing keys: {missing}")
        return False
    if extra:
        print(f"INFO: New keys (review needed): {extra}")
    return True

if __name__ == "__main__":
    golden = sys.argv[1]
    actual = sys.argv[2]
    passed = compare_schemas(golden, actual)
    sys.exit(0 if passed else 1)
```

**Step 3:** Run the eval after every skill prompt change:

```bash
python3 .claude/evals/eval_golden.py \
  .claude/evals/golden/payments-api-contracts.json \
  output/payments-cluster/api-contracts.json
```

**Why now:** You're 7 days from London. Every skill prompt change between now and then needs a safety net. Golden file evals are that net — they take 5 minutes to set up and catch regressions instantly. Combined with your PostToolUse hooks (online eval) and `$CLAUDE_EFFORT`-aware validation (Digest #43), you now have three layers of quality assurance: golden files catch regressions before deployment, PostToolUse hooks catch quality issues during execution, and effort-aware validation scales checking depth to context. Your pipeline doesn't just run — it runs *correctly*, and you can prove it.
