## Resource 2: Cost Control for Agent Teams — Model Mixing, Token Budgets, and the /usage Baseline

**Source:** [Manage costs effectively — Claude Code Official Docs](https://code.claude.com/docs/en/costs)
**Also:** [Claude Code Token Limits Cost Optimization Guide — Branch8](https://branch8.com/posts/claude-code-token-limits-cost-optimization-apac-teams)
**Also:** [Claude Code Pricing 2026: Plans, Token Costs, and Real Usage Estimates — Verdent](https://www.verdent.ai/guides/claude-code-pricing-2026)
**Time:** ~5 min read (official docs + skim Branch8)
**Category:** Operations — Cost Predictability for Autonomous Pipelines

### Why This Is Relevant

Your ISP pipeline runs 5 agents on Opus 4.7 xhigh. Agent Teams use approximately 7x more tokens than standard sessions — each teammate maintains its own context window and runs as a separate Claude instance. As you move toward scheduled autonomous execution via Dispatch, you need to know: what does a full pipeline run actually cost, and how do you make that number predictable?

**The cost levers you can pull today:**

**Model mixing per teammate role.** This was mentioned in John Kim's tips (Digest #30), but the official docs make it concrete: use `/model` to switch models mid-session, or configure different models per agent. The strategy for your ISP pipeline:

| Agent Role | Recommended Model | Why |
|-----------|------------------|-----|
| Lead orchestrator | Opus 4.7 xhigh | Synthesis quality — merging 4 cluster reports into a coherent architecture map requires deep reasoning |
| Domain cluster analysts (4) | Opus 4.7 standard or Sonnet 4.6 | Service-level analysis is more constrained; Sonnet handles most coding analysis well at ~60% lower cost |
| Validation agent (if added) | Sonnet 4.6 | JSON schema checking and cross-cluster consistency don't require Opus-level reasoning |

**Thinking token management.** Extended thinking tokens are billed as output tokens — the most expensive token type. The default budget can be tens of thousands of tokens per request. For teammate agents doing straightforward service analysis (not complex architectural synthesis), reducing the thinking budget saves significantly:

```bash
# In teammate agent configuration or environment
MAX_THINKING_TOKENS=8000
# Or use /effort to lower effort level for simpler analysis phases
```

For the lead agent doing cross-cluster synthesis, keep the full thinking budget. For teammates scanning individual services, lower it — the analysis task is constrained enough that deep reasoning chains aren't needed.

**Subagent delegation for expensive operations.** Running tests, fetching documentation, or processing log files consumes significant context. The official docs recommend delegating these to subagents so verbose output stays in the subagent's context while only a summary returns to your main conversation. For your pipeline: if a teammate agent needs to read a large configuration file or trace a complex dependency chain, spawn a subagent for that specific task rather than loading it all into the teammate's primary context.

**The /usage command for baselining.** Run `/usage` after your next full Agent Teams pipeline run. It shows detailed token usage statistics for the current session. Record the numbers for each cluster analysis and use them as your cost baseline. Once you have baselines, you can set meaningful token caps per workflow type (as the headless playbook from yesterday recommended).

**Enterprise cost benchmarks for context:**

| Metric | Enterprise Average | Your Pipeline (Estimated) |
|--------|-------------------|--------------------------|
| Cost per developer per active day | ~$13 | ~$40-80 (5 agents, xhigh) |
| Cost per developer per month | $150-250 | ~$500-1000 at current cadence |
| 90th percentile daily cost | <$30 | Depends on run frequency |

These numbers matter for your GenAI in SDLC presentation's ROI story. If a full ISP architecture recovery costs $200-500 in API tokens and takes hours instead of weeks of senior architect time, the ROI is obvious — but you need the actual numbers.

### Key Takeaway

Run `/usage` after your next Agent Teams pipeline execution and record the per-cluster token cost. Then experiment with model mixing: drop your 4 domain-cluster teammates from Opus 4.7 xhigh to Opus 4.7 standard (or even Sonnet 4.6 for a test run) while keeping the lead agent on xhigh. Compare analysis quality against cost — you may find that Sonnet teammates produce 90% of the analysis quality at 40% of the cost.

## Resource 3: Opik Claude Code Plugin — Zero-Config Tracing for Agent Systems

**Source:** [Announcing the Opik Claude Code Plugin — Comet ML Blog](https://www.comet.com/site/blog/opik-claude-code-plugin/)
**Also:** [comet-ml/opik-claude-code-plugin — GitHub](https://github.com/comet-ml/opik-claude-code-plugin)
**Also:** [OpenObserve + Claude Code: End-to-End AI Observability — Owen Zanzal, Medium](https://medium.com/devops-ai/openobserve-claude-code-end-to-end-ai-observability-984afcaeba36)
**Time:** ~4 min read
**Category:** Operations — The "Easy Button" for Agent Observability

### Why This Is Relevant

Resource 1 (Doneyli's Langfuse setup) is the DIY approach to observability — powerful but requires running a 6-service Docker stack. The Opik Claude Code Plugin is the managed alternative: automatic tracing of Claude Code sessions with a single command, no infrastructure to maintain.

**How Opik traces Agent Teams sessions:**

**Session → Trace, Turn → Span, Subagent → Nested Span.** Each Claude Code conversation becomes an Opik trace. Each conversation turn becomes a span within that trace. Tool calls, reasoning steps, and responses become child spans. Critically, subagent invocations — including Agent Teams teammate sessions — are nested under their parent task span. This means your 5-agent ISP pipeline produces a single trace with the lead agent as the root, and each teammate's entire session nested as a child span.

**The `/opik:instrument` command.** In roughly 95% of cases, running `/opik:instrument` in a Claude Code session produces the correct trace structure on the first attempt. The traces reflect the *logical steps* of the agent (analyze service → extract contracts → identify coupling) rather than the incidental code structure — which makes the traces actually useful for understanding what happened.

**Auto-instrumentation for existing code.** If you have Python or JavaScript agents, Opik adds tracing with minimal manual effort — it anchors traces at the entry point and wires providers automatically. For your ISP pipeline, this means: you don't refactor your `/reverse-engineer` skill. You instrument it, and the observability layer appears.

**When to use Opik vs. Langfuse (Resource 1):**

| Factor | Doneyli's Langfuse | Opik Plugin |
|--------|-------------------|-------------|
| Setup effort | Docker stack, ~30 min | Single command, ~5 min |
| Infrastructure | Self-hosted, you control data | Cloud-hosted (Comet) or self-hosted |
| Customization | Full control over dashboards | Opik's standard trace viewer |
| Data privacy | Everything stays local | Depends on hosting choice |
| Best for | Production pipeline with strict data requirements | Quick start, iterate on what to observe |

**For your ISP engagement:** If the ISP codebase contains sensitive client data that can't leave your machine, use the Langfuse self-hosted approach (Resource 1). If you want to get observability running in 5 minutes to validate the concept before committing to infrastructure, start with Opik.

### Key Takeaway

Start with Opik (`/opik:instrument`) for immediate, zero-infrastructure observability of your next Agent Teams run. Use the traces to identify which agents take longest, which services cause the most token consumption, and where errors occur. Once you've validated what you want to observe, decide whether to stay with Opik or move to self-hosted Langfuse for production.

## Quick Win: Run /usage and Establish Your Agent Teams Cost Baseline (3 min)

**Time: 3 minutes**

After your next Agent Teams pipeline run (or during the next one), run:

```
/usage
```

Record three numbers:
1. **Total session tokens** (input + output + thinking)
2. **Estimated cost** for this session
3. **Which cluster** this session covered
